## 决策（2026-08-12 定）

**全部在本机运行。CI/CD 的代码照写、照 review，但不接真实算力、不做真实远程部署。**

原因：找不到合适的公网机器资源（Oracle Always Free 注册受阻，内网机无公网 IP 且是公司在用的机器）。

这个取舍是合理的 —— 本机 24GB 内存足够把整套架构跑起来，
**架构原理、配置能力、故障排查这三样，本机模拟一点都不打折**。
真正学不到的东西列在第五节，不遮掩。

| 原计划 | 改为 | 打折了吗 |
|--------|------|---------|
| 云主机部署 | 本机 Docker Compose 多容器 | ❌ 不打折 |
| 云上 K8s | 本机 k3d / kind 集群 | ❌ 不打折 |
| Nginx 负载均衡到多台机器 | Nginx 负载均衡到多个本机容器 | ❌ 不打折（原理与配置完全一致） |
| GHCR 镜像仓库 | 本机 `registry:2` 容器 | ❌ 不打折 |
| 真实域名 + Let's Encrypt | 本地域名 + mkcert 本地 CA | ⚠️ 少了 DNS/ACME/备案环节 |
| GitHub Actions 真实运行 | workflow 照写，可选用 `act` 本机跑 | ⚠️ 少了云端集成体验 |
| 跨机网络 | 本机 Docker 网络 | ⚠️ 少了真实网络延迟与分区 |

> 顺带一个真实的架构习惯：**先算资源，再起服务**。
> 生产环境的容量评估就是这张表的放大版，只是单位从 GB 变成机器数。

### 架构差异：本机 arm64

Mac 是 arm64。这带来两个必须知道的点：

1. **有些镜像没有 arm64 版本**，会退化成 QEMU 模拟运行，慢到没法用（Elasticsearch 老版本、部分国产中间件）。
   遇到 `no matching manifest for linux/arm64` 就是这个问题
2. **构建镜像时要意识到平台**。`docker build` 默认出 arm64 镜像。虽然现在全在本机跑不受影响，
   但 Dockerfile 和 workflow 里要按多架构写（`docker buildx --platform linux/amd64,linux/arm64`），
   这是正确写法，将来换机器不用改

### 网络：需要代理才能访问 GitHub

```bash
export https_proxy=http://127.0.0.1:7890
export http_proxy=http://127.0.0.1:7890
export all_proxy=socks5://127.0.0.1:7890
```

用的是**非系统代理模式**（要同时访问公司内网资源），所以：

- 代理不是全局生效，每个终端会话/工具都要单独处理
- 我执行访问 GitHub 的命令时会显式带上这些变量
- Git 走代理建议**只对 github.com 生效**，不影响公司内网 Git：
  ```bash
  git config --global http.https://github.com/.proxy http://127.0.0.1:7890
  ```
- Docker 拉境外镜像要在 Docker Desktop 的 Proxies 设置里单独配，**它不读 shell 环境变量**
- 拉 Docker 镜像慢的话配国内镜像加速器，但注意：加速器对 `ghcr.io` 通常无效

> 按域名分流而不是全局代理，这个思路和后面配 Nginx 上游、K8s NetworkPolicy 是同一套逻辑：
> **精确控制流量的作用域**。

## 三、本机"模拟生产"拓扑

关键设计：**dev 环境和 prod 环境用两套独立的 compose，不是一套配置改参数。**
这是真实项目的做法，也是为了让你亲身体会两者的差异。

```
┌─ 开发环境（compose.dev.yml）──────────────────┐
│  MySQL:3306  Redis:6379   ← 端口直接暴露      │
│  app 在 IDEA 里跑，热重载，DEBUG 日志         │
│  ddl-auto 可用，测试数据随便造                 │
└──────────────────────────────────────────────┘

┌─ 模拟生产（compose.prod.yml）─────────────────┐
│                                               │
│   Nginx :8443 (HTTPS, mkcert 证书)            │
│     ├── /          静态资源                    │
│     ├── /api/      ──┐                        │
│     └── /admin-api/ ─┤                        │
│                      ▼                        │
│        ┌─────────────────────────┐            │
│        │ app-1  app-2  app-3     │ ← 多实例    │
│        │ (同一镜像，负载均衡)      │   验证无状态 │
│        └───────────┬─────────────┘            │
│                    │                          │
│      ┌─────────────┴──────────┐               │
│   MySQL              Redis                    │
│   ★ 只在内部网络，不暴露端口到宿主机            │
│   ★ 数据卷持久化 + 定时备份脚本                 │
│   ★ 每个容器设 mem_limit + 日志轮转            │
│   ★ 配置全部来自环境变量/.env（不进仓库）        │
└──────────────────────────────────────────────┘

镜像流转：本机 build → 推本机 registry:2 (localhost:5000) → prod compose 从 registry 拉
         （刻意绕一道，为的是走通"构建产物与运行分离"的流程，而不是直接用本地镜像）
```

**为什么多实例这件事必须做**：单实例跑起来的应用，很多问题永远不会暴露 ——
本地缓存不一致、Session 存内存、定时任务重复执行、文件上传到本地磁盘。
起三个实例 + Nginx 一挡，这些坑当场现形。这是 M05 的核心价值，比学 Nginx 语法重要得多。

## 四、CI/CD：代码保留，不真实运行

### 4.1 具体怎么做

| 产出 | 写不写 | 跑不跑 |
|------|-------|-------|
| `Dockerfile`（多阶段构建） | ✅ 写 | ✅ 本机真跑 |
| `compose.dev.yml` / `compose.prod.yml` | ✅ 写 | ✅ 本机真跑 |
| `nginx.conf` | ✅ 写 | ✅ 本机真跑 |
| `.github/workflows/ci.yml`（构建+测试+镜像） | ✅ 写，我 review | ❌ 不接 GitHub 算力 |
| `.github/workflows/deploy.yml`（远程部署） | ✅ 写，我 review | ❌ 不真实部署 |
| `deploy.sh` / `Makefile` | ✅ 写 | ✅ 本机跑（目标改成本机 prod compose） |
| K8s manifest / Helm chart | ✅ 写 | ✅ 本机 k3d 真跑 |

### 4.2 防止 workflow 被意外触发

代码推到 GitHub 后，workflow 可能自动跑起来（虽然额度免费，但会失败刷一堆红叉）。
两道保险：

1. 触发条件只留手动：
   ```yaml
   on:
     workflow_dispatch:      # 只能手动触发
     # push:                 # 暂不启用，留着说明设计意图
     #   branches: [main]
   ```
2. fork 仓库的 Actions **默认就是禁用的**，不去手动启用即可

> 注释掉而不是删掉 push 触发 —— 保留设计意图，将来有资源了取消注释就能用。

### 4.3 可选：用 act 在本机跑 workflow

```bash
brew install act
act -l                          # 列出 workflow 里的 job
act -j build --container-architecture linux/amd64
```

`act` 用 Docker 起一个 runner 镜像来执行 workflow，**能在本机验证 YAML 语法和 job 编排**。
标为可选是因为 runner 镜像不小（几百 MB，走代理要等）。
不装也不影响 —— workflow 我会做静态 review。

## 五、已知能力缺口（诚实记录，将来补）

本机模拟学不到的，只有这些。**知道自己缺什么，比假装什么都学到了重要。**

| 缺口 | 为什么本机学不到 | 将来怎么补 |
|------|----------------|-----------|
| 域名 + DNS 解析 | 本地用 `/etc/hosts`，绕过了真实 DNS | 买域名（约 ¥30/年），只做 DNS 解析也能练 |
| ACME 证书自动签发与续期 | mkcert 是本地 CA，不走 ACME 协议 | 有公网机后用 certbot / Caddy 自动签 |
| ICP 备案 | 国内特有流程 | 买国内轻量服务器时走一遍 |
| 真实网络延迟、丢包、分区 | Docker 网络近乎零延迟 | 可用 `tc netem` 在本机**人为注入延迟和丢包**（推荐，M10 做混沌实验） |
| 云安全组 / VPC / 公网暴露面 | 无公网 IP | 概念可讲，操作等有机器 |
| 多机真实分布式（跨物理机） | 全在一台机上 | k3d 多节点是逻辑多节点，够练调度和亲和性 |
| 云托管服务（RDS、云 Redis、SLB） | 无账号 | 概念对照讲：自建 vs 托管的成本与责任边界 |
| 生产事故的真实压力 | 没有真实用户 | 用压测 + 故障注入模拟（M10） |

其中 **`tc netem` 注入延迟丢包** 值得单独提一句：它能让你在本机复现
"下游服务变慢导致线程池打满、雪崩" 这类真实生产故障。这是本机模拟里性价比最高的一项，M10 会做。
