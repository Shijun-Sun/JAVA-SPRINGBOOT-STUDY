## 一、NULL 的陷阱 ⭐（最坑，务必动手）

**坑 1：NULL 不能用 `=` 比较**
```sql
SELECT NULL = NULL;      -- 结果是 NULL，不是 1！
SELECT NULL = 0;         -- NULL
SELECT NULL <> NULL;     -- NULL
```
- 为什么：NULL 表示"未知"，"未知 = 未知"结果仍是未知。
- 正确：判空只能用 `IS NULL` / `IS NOT NULL`。
- 动手：`SELECT * FROM spu WHERE description = NULL;`（查不出任何行）对比 `WHERE description IS NULL;`。

**坑 2：`NOT IN (子查询)` 遇到 NULL 全军覆没**
```sql
-- 如果子查询结果里有一个 NULL，整个 NOT IN 可能返回空集
SELECT * FROM spu WHERE id NOT IN (SELECT category_id FROM spu WHERE category_id IS NULL);
```
- 为什么：`id NOT IN (1,2,NULL)` 会因为和 NULL 比较得 NULL 而整体失效。
- 正确：用 `NOT EXISTS` 或先在子查询里过滤掉 NULL。

**坑 3：`COUNT(列)` 会漏掉 NULL 行**
```sql
SELECT COUNT(*) AS 全部行, COUNT(description) AS 有描述的行 FROM spu;
```
- 为什么：`COUNT(*)` 数所有行；`COUNT(列)` 只数该列非 NULL 的行。
- 记住：**要总行数永远用 `COUNT(*)`**；`COUNT(1)` 和 `COUNT(*)` 等价（别纠结谁快，InnoDB 里基本一样）。

## 二、隐式类型转换导致索引失效 ⭐（用 explain 数据）

**坑 4：字符串列用数字查**
```sql
EXPLAIN SELECT * FROM sku WHERE sku_code = 202609\G     -- key=NULL，全表扫！
EXPLAIN SELECT * FROM sku WHERE sku_code = '202609'\G   -- 走索引
```
- 为什么：`sku_code` 是 `VARCHAR`，用数字比会把**每行的列值转成数字**（等于对列做函数）→ 索引失效。
- 正确：查询值类型和列类型**永远对齐**。

## 三、金额与浮点

**坑 5：浮点算钱会错**
```sql
SELECT 0.1 + 0.2;                                        -- 0.3（DECIMAL 字面量，精确）
SELECT CAST(0.1 AS DOUBLE) + CAST(0.2 AS DOUBLE);        -- 0.30000000000000004
```
- 正确：金额列用 `DECIMAL`，Java 端用 `BigDecimal`，别用 `float/double`。

## 四、UPDATE / DELETE 不带 WHERE（生产头号事故）⭐

**坑 6：忘了 WHERE = 改/删全表**
```sql
-- UPDATE sku SET price = 0;      -- 灾难：所有 SKU 价格清零
-- DELETE FROM spu;               -- 灾难：整表清空
```
- 预防习惯：
  1. 先写 `SELECT` 确认 `WHERE` 命中的行，再把 `SELECT` 换成 `UPDATE/DELETE`；
  2. 生产可开 `sql_safe_updates`：`SET sql_safe_updates=1;`（没带 key 列的 WHERE 会被拒）；
  3. 重要操作放事务里，`SELECT` 核对后再 `COMMIT`（事务 M02-05 讲）。
- 动手体验保护：`SET sql_safe_updates=1;` 后执行 `UPDATE sku SET stock=0;`（应被拒）。

## 五、LIMIT / 分页

**坑 7：`LIMIT` 不带 `ORDER BY`，顺序不保证**
```sql
SELECT * FROM spu LIMIT 5;   -- 返回哪 5 行、什么顺序，都不保证稳定
```
- 为什么：不排序时返回顺序由存储/执行决定，换个执行计划就变。
- 正确：分页/取 TopN 一定带 `ORDER BY`（且排序列最好唯一，否则并列行顺序仍不定）。

**坑 8：深分页 `LIMIT 大偏移`（用 explain 数据）**
```sql
EXPLAIN ANALYZE SELECT * FROM spu ORDER BY id LIMIT 50000, 10\G   -- 扫 5 万行再丢弃
```
- 正确：延迟关联或键集分页（见练习 04 题 5）。

## 六、GROUP BY

**坑 9：`SELECT` 了没在 `GROUP BY` 里、也不是聚合的列**
```sql
-- 8.0 默认开 ONLY_FULL_GROUP_BY，下面这条会报错
SELECT category_id, name, COUNT(*) FROM spu GROUP BY category_id;
```
- 为什么：一个 `category_id` 组里有多个 `name`，选哪个？MySQL 8 默认不允许这种歧义。
- 正确：要么把列放进 `GROUP BY`，要么用聚合函数（`MAX(name)` 等），要么想清楚你到底要什么。

**坑 10：想"每组取极值所在的整行"，却写错**
```sql
-- 错误：MIN(price) 和 sku_code 可能不是同一行！
SELECT spu_id, sku_code, MIN(price) FROM sku GROUP BY spu_id;
```
- 为什么：聚合和非聚合列不保证来自同一行。
- 正确：用窗口函数 `ROW_NUMBER() OVER (PARTITION BY spu_id ORDER BY price)` 取 rn=1，或关联子查询。

## 七、JOIN

**坑 11：JOIN 后行数"膨胀"**
```sql
-- 一个 spu 有多个 sku，JOIN 后 spu 的信息会重复多行
SELECT s.name, k.sku_code FROM spu s JOIN sku k ON k.spu_id=s.id WHERE s.id=1;
```
- 现象：`spu.name` 出现 3 次（因为 spu 1 有 3 个 sku）。这不是 bug，是一对多的正常结果，但**做 `COUNT`/`SUM` 时容易算重**。
- 正确：聚合前想清楚粒度；必要时先在子查询里聚合再 JOIN。

**坑 12：`LEFT JOIN` 的过滤条件写错位置**
```sql
-- 把右表条件写在 WHERE，LEFT JOIN 会退化成 INNER JOIN
SELECT s.name, k.sku_code FROM spu s LEFT JOIN sku k ON k.spu_id=s.id WHERE k.status=1;
```
- 为什么：没匹配到 sku 的 spu，`k.status` 是 NULL，被 `WHERE k.status=1` 过滤掉，左表就不"全保留"了。
- 正确：想保留左表全部，右表条件放 `ON` 里：`... ON k.spu_id=s.id AND k.status=1`。
- 动手对比两种写法的行数差异（用 basic 数据，spu 7 里有的没 sku）。

## 八、字符集 / 时区

**坑 13：命令行中文乱码**
```bash
docker exec mysql84 mysql ... -e "SELECT '中文别名' ..."   # 可能乱码
```
- 为什么：客户端字符集不对。数据没坏，只是显示问题。
- 正确：加 `--default-character-set=utf8mb4`，或用 IDEA/DBeaver 看。

**坑 14：`utf8` 不是真 UTF-8**
- MySQL 里 `utf8`（=`utf8mb3`）最多 3 字节，存不了 emoji、部分生僻字。
- 正确：一律用 `utf8mb4`（我们的库就是）。

**坑 15：时区**
- `NOW()` 依赖会话/服务器时区；容器我们设了 `TZ=Asia/Shanghai`。
- 应用连接串注意 `serverTimezone`，避免存进去的时间差 8 小时（M02-08 接持久层时重点核对）。

## 九、索引/性能杂项

**坑 16：`SELECT *` 拿一堆用不到的列**
- 代价：多传输、可能破坏覆盖索引（本可 `Using index` 的变回表）。正确：只查需要的列。

**坑 17：以为建了索引就一定走**
- 优化器按成本选，选择性差/数据量小/负向条件时可能"有索引也不走"，这是对的。用 `EXPLAIN` 确认，别想当然。

**坑 18：`OR` 一边没索引拖垮整条**
```sql
EXPLAIN SELECT * FROM spu WHERE category_id=3 OR name='x'\G   -- name 没索引 → 可能全表扫
```
- 正确：能改 `IN`/`UNION` 就改，或给两边都建合适索引。
