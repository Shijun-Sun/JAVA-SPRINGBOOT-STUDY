# 商品域库表设计说明

> 对应作业：M02-01 · 商品域库表设计与 DDL 实战（任务三）
> 对应 DDL：`schema-product.sql`、`schema-category.sql`、`schema-spu.sql`、`schema-sku.sql`
> 版本基线：MySQL 8.4 LTS、InnoDB、`utf8mb4` / `utf8mb4_0900_ai_ci`

本文说明商品域建模的关键决策，每条都给「为什么 + 代价」，并保证与实际 DDL 一致。

---

## 一、表清单与关系

| 表 | 角色 | 关键关系 |
|----|------|----------|
| `product` | 单品过渡表（M01 `ProductEntity` 原样落库） | 独立，暂不参与 SPU/SKU |
| `category` | 分类树（邻接表） | `parent_id` 指向自身 |
| `spu` | 商品抽象（标题层） | `category_id` → `category.id` |
| `sku` | 可下单最小单位（价格/库存层） | `spu_id` → `spu.id` |

关系图：

```
category(id, parent_id)         ← 分类树，parent_id=0 为顶级
   ▲ category_id（逻辑外键）
spu(id, category_id, ...)       ← 一个 SPU 挂在一个分类下
   ▲ spu_id（逻辑外键，一对多）
sku(id, spu_id, price, stock)   ← 一个 SPU 带多个 SKU，价格库存在这
```

---

## 二、关键设计决策

### 1. 为什么价格和库存放在 `sku` 而不是 `spu`？

- **为什么**：SPU 是「商品」的抽象（如「iPhone 15 Pro」），SKU 才是可下单、可扣库存的最小单位（如「256G 黑色」）。同一个 SPU 下不同规格的价格和库存本就不同（256G ¥7999、512G ¥9999），价格/库存天然属于 SKU 这一层。放到 SPU 上就无法表达「同商品不同规格不同价、不同库存」。
- **代价**：查询「一个商品的价格区间」需要聚合它下面所有 SKU（`MIN/MAX(price)`），比直接读单字段多一步；商品详情页要同时查 SPU 和其 SKU 列表。这是规范拆分换来的必要成本，可接受。

### 2. 分类树为什么用邻接表，而不是其它树模型？

- **为什么**：邻接表（每行存自己的 `id` 和 `parent_id`）写入和改动都简单——加一个分类只插一行、移动子树只改一个 `parent_id`。电商分类层级一般不深（3~4 级），邻接表完全够用。
- **代价**：查「某分类的所有后代」需要递归（MySQL 8 用 `WITH RECURSIVE` 递归 CTE 解决，见作业任务四）。相比路径枚举、闭包表等模型，查子树更费一点，但换来了写入简单、结构直观。层级不深的场景下这个取舍划算，不做过度设计。

### 3. 销售属性选了 JSON 还是独立规格表？各自代价是什么？

- **本次选择：`sku.spec_json` JSON 列**（如 `{"容量":"256G","颜色":"黑色"}`）。
- **为什么选 JSON**：本阶段销售属性只用于「展示 + 区分同 SPU 下的 SKU」，不需要按「颜色=黑色」做全站筛选、排序、统计。结构不固定的展示型附加信息正是 JSON 列的适用场景（讲义 4.8），一列搞定，无需额外建表和 JOIN。
- **JSON 的代价**：不便于按单个属性建索引、精确筛选和聚合；属性名/值散落在 JSON 里，缺乏约束，容易写脏（大小写、单位不统一）。
- **独立规格表方案（备选）**：例如 `sku_spec(id, sku_id, attr_name, attr_value)` 一行一个属性。优点是能对属性建索引、支持「按颜色/容量筛选」的商品筛选页，约束更强；代价是查一个 SKU 的完整规格要 JOIN + 多行拼装，写入也更繁琐。
- **切换时机**：一旦出现「按销售属性筛选商品」这类查询需求（如京东左侧的规格筛选栏），再从 JSON 演进到独立规格表 / 属性字典表。当前不预先过度设计。

> 注：原提交里用的是单个 `sale_property_id` 外键，无法表达一个 SKU 同时有「容量 + 颜色」多个属性，且引用的规格表未定义。已改为 `spec_json`，理由如上。

### 4. 为什么用逻辑外键、不加物理外键约束？

- **为什么**：`spu.category_id`、`sku.spu_id` 只用字段名表达关系，不写 `FOREIGN KEY`。物理外键在高并发写入时会带来额外的锁和约束检查开销（子表写入要回查父表），且**分库分表后跨库外键根本无法维护**（M08 会遇到）。互联网实践普遍在应用层维护引用关系。
- **代价**：数据库不再帮你兜底完整性——出现「`sku.spu_id` 指向一个不存在的 spu」这种脏数据时库不会拦，需要应用层保证插入顺序（先插 SPU 拿到 id，再插 SKU）和删除时的级联处理。这个责任从数据库转移到了代码，是有意识的权衡。

### 5. `product` 过渡表和规范的 `spu/sku` 是什么关系？第 10 章打算怎么平滑迁移？

- **关系**：`product` 是 M01「无规格单品」模型的原样落库（一行同时有 `name/sku/price/category`），本质是「SPU 和 SKU 揉在一起、分类还是字符串」。它和规范的 `spu/sku/category` 是**同一批商品数据的两种建模**，过渡期并存。
- **第 10 章迁移思路**：
  1. 先让 `product-service` 的内存实现平滑落到 `product` 表，接口和测试基本不动（先「搬家」）；
  2. 再写一次性迁移：每条 `product` → 生成 1 个 `spu`（`category` 字符串按名称匹配/补建到 `category` 树，回填 `category_id`）+ 1 个 `sku`（`sku`→`sku_code`、`price`、初始 `stock`）；
  3. 读写切到 `spu/sku`，`product` 表保留一段时间做灰度回退，确认无误后下线（先「搬家」再「重构」，分步降低风险）。

## 三、字段类型选型（对照讲义第四节）

| 场景 | 选型 | 理由 |
|------|------|------|
| 主键 | `BIGINT UNSIGNED AUTO_INCREMENT` | 数据量大不溢出、无业务含义、顺序递增对聚簇索引友好 |
| 金额 | `DECIMAL(10,2)` | 定点数精确，浮点会算错钱（对应 Java `BigDecimal`） |
| 时间 | `DATETIME` + `ON UPDATE CURRENT_TIMESTAMP` | 无 2038 问题、行为直观，时区在应用层统一 |
| 状态 | `TINYINT` + 应用层枚举 | 加状态只改代码不改表，不用 MySQL `ENUM` |
| 库存 | `INT UNSIGNED` | 非负、上限约 42 亿，单 SKU 库存够用 |
| 字符集 | `utf8mb4` / `utf8mb4_0900_ai_ci` | 完整 4 字节 UTF-8，能存 emoji/生僻字 |
| 销售属性 | `JSON` | 结构不固定、仅展示用，见决策 3 |

**工程标配**：每张表都带审计字段（`created_at/by`、`updated_at/by`）、软删除（`deleted_at`）、乐观锁 `version`、完整 `COMMENT`；命名统一小写下划线；唯一键前缀 `uk_`。

## 四、索引说明

> 主键 / 唯一键在 01 章已定：`product.uk_sku`、`sku.uk_sku_code`。
> 普通查询索引在 **03 章**结合最左前缀、覆盖索引，面向真实高频查询统一设计，记录如下。

### 4.0 面向的三条高频查询

```sql
-- Q1 分类页：某分类的直接子分类，按 sort 排序
SELECT id, name FROM category WHERE parent_id = ? ORDER BY sort;
-- Q2 商品列表：某分类下、上架的商品，按创建时间倒序
SELECT id, name FROM spu WHERE category_id = ? AND status = 1 ORDER BY created_at DESC;
-- Q3 商品详情：某 SPU 下的所有 SKU
SELECT * FROM sku WHERE spu_id = ?;
```

### 4.1 新增索引清单（与 DDL 完全一致）

| 表 | 索引 | 列（顺序） | 服务查询 |
|----|------|-----------|----------|
| `category` | `idx_parent_sort` | `(parent_id, sort)` | Q1 |
| `spu` | `idx_category_status_created` | `(category_id, status, created_at)` | Q2 |
| `sku` | `idx_spu_id` | `(spu_id)` | Q3 |

### 4.2 列顺序的理由（等值在前、范围在后、排序进前缀）

- **`category.idx_parent_sort (parent_id, sort)`**
  - `parent_id` 是等值条件（`= ?`），放最前面定位到"某个父分类下的所有子分类"这一段连续记录。
  - `sort` 放第二列：定位到同一 `parent_id` 段后，该段内部按 `sort` 已经有序，`ORDER BY sort` 直接顺着索引读，**不需要 filesort**。
  - 若只建 `(parent_id)`，定位没问题但排序要额外做 filesort；把 `sort` 纳入前缀是"排序进前缀"的典型应用。

- **`spu.idx_category_status_created (category_id, status, created_at)`**
  - `category_id`、`status` 都是等值条件（`= ?`、`= 1`），两个等值列放前面，把结果锁定到"某分类 + 上架"这一段。
  - `created_at` 放最后：前两列等值确定后，这一段记录内部按 `created_at` 有序。`ORDER BY created_at DESC` 只是把这段有序数据**反向读**，B+ 树叶子是双向链表，正读倒读都不触发 filesort。
  - 顺序不能换：如果把 `created_at` 提到 `status` 前面（`category_id, created_at, status`），一旦对 `created_at` 用范围/排序，后面的 `status` 就用不上索引定位了——等值列必须排在参与排序/范围的列之前。

- **`sku.idx_spu_id (spu_id)`**
  - 只有 `spu_id` 一个等值过滤条件，没有附带排序，单列索引即可，不需要联合。

### 4.3 覆盖索引：这次做了吗？

- **Q1（`category`）**：查 `id, name`。`name` 不在 `idx_parent_sort` 里，取 `name` 需回表；也可以把 `name` 拼进索引做覆盖，但分类表数据量小（通常几百到几千行）、回表代价可忽略，**不为它加宽索引**，避免徒增索引体积和写入成本。
- **Q2（`spu`）**：查 `id, name`。同理 `name` 需回表。是否覆盖取决于列表页字段规模，当前只回表取 `name`，代价可控，**暂不做覆盖**；若列表页字段稳定且查询压力大，第 04 章可再评估把常用列纳入覆盖。
- **Q3（`sku`）**：`SELECT *` 注定要整行数据，**无法覆盖**，回表是必然的。为一行完整数据强行做覆盖（把所有列塞进二级索引）没有意义，代价远大于收益。

### 4.4 为什么不给 `status` 单独建索引（选择性视角）

- `status` 只有 `0/1` 两个值，**选择性极低**（区分度差）。单独给它建索引，优化器多半会因为"过滤后仍剩大量行、回表成本高于全表扫"而放弃使用，索引白建还拖慢写入。
- 正确做法是让 `status` 作为**联合索引的一列**出现（如 `spu.idx_category_status_created` 的第二列），借助前面高选择性的 `category_id` 先把范围缩小，`status` 只在小范围内再过滤。

### 4.5 关于软删除列 `deleted_at`

- 本次索引按作业给定的 Q1/Q2/Q3 设计，未把 `deleted_at IS NULL` 纳入。真实上线时列表/详情查询通常都带 `deleted_at IS NULL`，届时可评估是否把 `deleted_at` 纳入联合索引或改用"逻辑删除 + 状态位"策略；这属于第 10 章落地时结合真实查询再定，此处先记录、不预先过度设计。

### 4.6 与后续章节的关系

- 这些索引是第 **04 章 `EXPLAIN`** 的观察对象：会用执行计划验证"走没走上索引、`type` 是 `ref` 还是 `ALL`、`Extra` 有没有 `Using index` / `Using filesort`"。
- 第 **10 章落地改造**把 `product-service` 换成 MySQL 时，列表页 / 详情页 / 分类页的查询会直接依赖这三个索引，它们是正式项目能力，不是演示。

## 五、样例数据（示意，说明关系如何对上；本章未实际在 MySQL 执行）

```sql
-- 三级分类：手机数码(1) → 手机(2) → 智能手机(3)
INSERT INTO category (id, parent_id, name, level) VALUES
  (1, 0, '手机数码', 1),
  (2, 1, '手机',     2),
  (3, 2, '智能手机', 3);

-- 1 个 SPU 挂在三级分类「智能手机」(id=3) 下
INSERT INTO spu (id, category_id, name, brand) VALUES
  (1, 3, 'iPhone 15 Pro', 'Apple');

-- 该 SPU 带 3 个 SKU（价格/库存/销售属性在 SKU 层）
INSERT INTO sku (spu_id, sku_code, price, stock, spec_json) VALUES
  (1, 'IP15P-256-BLK', 7999.00, 100, JSON_OBJECT('容量','256G','颜色','黑色')),
  (1, 'IP15P-256-WHT', 7999.00,  80, JSON_OBJECT('容量','256G','颜色','白色')),
  (1, 'IP15P-512-BLK', 9999.00,  30, JSON_OBJECT('容量','512G','颜色','黑色'));

-- 验证「一个 SPU 带哪些 SKU」
SELECT s.name AS spu名称, k.sku_code, k.price, k.stock, k.spec_json
FROM spu s
JOIN sku k ON k.spu_id = s.id
WHERE s.id = 1;
```

> 说明：`spu_id = 1` 依赖先插入 SPU 拿到其 `id` —— 逻辑外键需应用层保证插入顺序，数据库不做校验（见决策 4）。
