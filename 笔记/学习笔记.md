## 环境与工具

### Java 文件运行方式
> 来源问题：如何像 node a.js 一样运行 Java 文件？

- **Java 11+ 单文件直接运行**：`java base5.java`，无需手动编译，适合学习阶段
- **传统两步运行**：
  1. `javac base5.java` → 编译，生成 `base5.class` 字节码文件
  2. `java base5` → 运行（注意不带 `.java` 后缀，JVM 执行 `.class`）
- Java 与 Node.js 对比：Node 直接解释执行 JS；Java 本质是编译型语言，`java xxx.java` 是 Java 11 提供的快捷方式，底层仍会编译再运行
- 多文件项目必须用 `javac` 手动编译，不能用单文件直接运行方式

## 注解与反射

### 注解（Annotation）基础
> 来源问题：生成 2.7 注解与反射学习文件

- 注解是附加在代码元素上的"元数据标签"，本身不影响程序逻辑，由编译器或框架在运行时读取处理
- 内置常用注解：`@Override`（验证重写）、`@Deprecated`（标记过时）、`@SuppressWarnings`（压制警告）、`@FunctionalInterface`
- 自定义注解语法：`@interface 注解名 { 类型 属性名() default 默认值; }`
- 注解属性类型只能是：基本类型、String、Class、枚举、注解、以上类型的数组

### 元注解（Meta-Annotation）
> 来源问题：生成 2.7 注解与反射学习文件

- `@Target`：指定注解作用位置（`TYPE` / `METHOD` / `FIELD` 等）
- `@Retention`：指定注解保留阶段
  - `SOURCE`：仅源码阶段，编译后丢弃（如 `@Override`）
  - `CLASS`：编译进 `.class`，运行时不可见（默认）
  - `RUNTIME`：运行时可见，可通过反射读取（框架最常用）
- `@Documented`：让注解出现在 Javadoc 中
- `@Inherited`：子类会继承父类的该注解
- **记忆口诀**：想让反射读到注解，必须加 `@Retention(RUNTIME)`

### 反射（Reflection）基础
> 来源问题：生成 2.7 注解与反射学习文件

- 反射允许在运行时动态获取类结构信息并操作对象
- 核心类：`Class`、`Field`、`Method`、`Constructor`
- 获取 Class 对象三种方式：
  1. `类名.class` — 编译期已知类型
  2. `对象.getClass()` — 已有对象实例
  3. `Class.forName("全限定类名")` — 运行时按字符串加载（最灵活）
- 访问私有成员需调用 `setAccessible(true)` 打破访问限制

### 动态代理基础
> 来源问题：生成 2.7 注解与反射学习文件

- 动态代理在不修改原类的情况下，在方法调用前/后增加逻辑（AOP 基础）
- JDK 动态代理三要素：目标接口、目标实现类、`InvocationHandler`（拦截逻辑）
- 使用 `Proxy.newProxyInstance(classLoader, interfaces[], handler)` 创建代理对象
- JDK 代理基于接口；CGLIB 代理基于继承（Spring 底层使用）

## 并发基础

### Java synchronized 隐式锁 vs Go 显式锁的设计哲学
> 来源问题：为什么 Java 不像 Go 那样显式拿锁/放锁，而是把锁内置在对象里？

- **Java "万物皆对象"**：数据住在对象里，锁也属于对象，天然对应，无需额外声明一个 `Mutex` 变量
- **安全优先**：`synchronized` 由 JVM 保证——无论方法正常返回还是抛出异常，锁都会自动释放，不会死锁
- **Go `sync.Mutex`** 是独立变量，需要手动 `Lock()` / `Unlock()`，控制更灵活但必须自己保证释放（通常用 `defer mu.Unlock()`）
- **Java 也有显式锁**：`ReentrantLock`（Java 5+），用法接近 Go，支持超时/中断/公平锁等高级特性，但需要在 `finally` 中手动 `unlock()`
- **一句话对比**：
  - Java `synchronized` = **安全优先**，JVM 兜底，适合初学和常规场景
  - Go `Mutex` / Java `ReentrantLock` = **控制优先**，灵活但责任自负

### 可见性（Visibility）与原子性（Atomicity）
> 来源问题：volatile 的可见性和原子性分别是什么意思？

**可见性（Visibility）**
- 根因：多核 CPU 每个核有独立缓存，线程 A 的修改可能只在核 A 的缓存里，线程 B 读不到
- `volatile` 解决：写操作强制刷新到主内存，读操作强制从主内存读，保证 A 的修改 B 一定可见
- 典型场景：`volatile boolean stopFlag` 作为多线程停止标志位

**原子性（Atomicity）**
- 根因：`count++` 实际是三步（读→+1→写），三步之间可以被其他线程打断，导致结果错误
- `volatile` **不能**解决原子性，它只保证可见性
- 解决方案：
  - `synchronized`：加锁，三步整体不可打断（通用，适合复杂逻辑）
  - `AtomicInteger`：基于 CAS 硬件指令，"比较+替换"一步完成，性能优于 synchronized（适合简单计数）

**CAS（Compare And Swap）原理**
- 伪代码：`if (当前值 == 期望值) { 写入新值; return true; } else { return false; }` — 由硬件保证这个判断+写入是原子的
- 失败时自动重试（自旋），直到成功

**总结对比**

| | 解决可见性 | 解决原子性 |
|---|---|---|
| `volatile` | ✅ | ❌ |
| `synchronized` | ✅ | ✅ |
| `AtomicInteger` | ✅ | ✅ |

### 线程池优雅关闭：shutdown + awaitTermination
> 来源问题：pool.shutdown() 后，等待所有任务完成应该怎么写？

- `shutdown()`：发出关闭信号，不再接收新任务，已提交任务继续执行，**不阻塞**
- `awaitTermination(n, unit)`：**阻塞**当前线程，等待线程池所有任务完成，最多等 n 秒；返回 `true` 表示任务全完成，`false` 表示超时
- `shutdownNow()`：强制中断所有线程（发送 interrupt 信号），用于超时后兜底

**为什么必须先 shutdown 再 awaitTermination？**
- 不先调 `shutdown()`，线程池状态是"运行中"，`awaitTermination` 会一直等到超时，毫无意义

**生产环境标准模板：**
```java
pool.shutdown();
if (!pool.awaitTermination(5, TimeUnit.SECONDS)) {
    pool.shutdownNow();                          // 超时强制中断
    pool.awaitTermination(5, TimeUnit.SECONDS); // 等待中断完成
}
```

### Java 注解 vs TypeScript 装饰器：为什么注解没有行为？
> 来源问题：为何注解不在定义阶段就决定它要干什么？TS 装饰器就是定义阶段绑定行为的。

- **Java 注解本质是纯元数据**，本身不含可执行逻辑；行为由"读取方"（框架/处理器）决定
- **TS 装饰器本质是高阶函数**，语法糖展开后是立即执行的函数调用，定义即执行
- Java 这样设计的好处：**同一注解可被不同框架赋予不同行为**（如 `@Column` 可被 Hibernate、MyBatis、自定义工具分别解读）
- 对比表：

| | Java 注解 | TS 装饰器 |
|---|---|---|
| 本质 | 元数据标记 | 高阶函数 |
| 行为定义时机 | 读取时（框架处理） | 定义时（立即执行） |
| 灵活性 | 高（一个注解多种解读） | 低（绑定了具体逻辑） |

- Java 中若要"定义时绑定行为"，需配套写**注解处理器**：
  - 编译期：`AbstractProcessor`（Lombok 的 `@Data` 原理）
  - 运行期：Spring AOP（扫描到 `@Transactional` 动态生成代理类）
- 注解和处理器在 Java 中是**分开的两个文件**，TS 是合并在一起的

## 开发环境

### Java 版本管理：jabba

> 来源问题：忘记了 Java 版本管理工具名称，以及如何切换版本

**工具名：[jabba](https://github.com/shyiko/jabba)**，macOS 上通过 shell 函数注入，安装目录在 `~/.jabba/`。

---

#### 查看已安装版本

```bash
jabba ls
# 输出示例：
# 21-custom
# 17
```

---

#### 查看当前正在使用的版本

```bash
jabba current
# 若未激活任何版本则无输出

java -version
# 直接看 JDK 版本号
```

---

#### 切换版本（临时，仅当前终端会话）

```bash
jabba use 17
jabba use 21-custom

# 切换后验证
java -version
```

> `jabba use` 只修改当前 shell 的 `PATH` 和 `JAVA_HOME`，关闭终端后失效。

---

#### 设置默认版本（新终端自动生效）

```bash
# 设置默认
jabba alias default 17
# 或
jabba alias default 21-custom

# 查看当前默认是哪个
jabba alias default

# 取消默认
jabba unalias default
```

> 设置后，新打开的终端会自动 `use` 该版本（需要 `~/.zshrc` 或 `~/.bash_profile` 里已配置 jabba 初始化脚本）。

---

#### 查看可安装的远程版本列表

```bash
# 列出所有可安装版本（列表很长）
jabba ls-remote

# 筛选常用发行版
jabba ls-remote | grep "^openjdk@"          # OpenJDK 官方
jabba ls-remote | grep "^amazon-corretto@"  # Amazon Corretto
jabba ls-remote | grep "^zulu@"             # Azul Zulu
jabba ls-remote | grep "^graalvm@"          # GraalVM
jabba ls-remote | grep "^adopt@"            # AdoptOpenJDK（旧名，现为 Temurin）
```

> jabba 版本号格式是 `发行版@1.大版本.小版本`，例如 `openjdk@1.21.0` 对应 Java 21。

---

#### 安装指定版本

```bash
# 安装 OpenJDK 17（最新补丁）
jabba install openjdk@1.17.0

# 安装 OpenJDK 21
jabba install openjdk@1.21.0

# 安装 Amazon Corretto 17
jabba install amazon-corretto@1.17.0-0.35.1

# 安装时使用 ~ 模糊匹配（安装 >=1.17.0 且 <1.18.0 中最新的）
jabba install "~1.17"

# 安装并立即切换使用
jabba install openjdk@1.21.0 && jabba use openjdk@1.21.0
```

---

#### 卸载版本

```bash
jabba uninstall openjdk@1.17.0
```

---

#### 查看某版本的实际安装路径

```bash
jabba which 17
# /Users/sunshijun/.jabba/jdk/17

jabba which 21-custom
# /Users/sunshijun/.jabba/jdk/21-custom
```

> 这个路径就是 `JAVA_HOME`，可以直接配给 IDE（IntelliJ IDEA 等）。

---

#### 自定义别名（alias）

jabba 支持给已安装的版本起别名，方便记忆：

```bash
# 给 openjdk@1.21.0 起别名 "21"
jabba alias 21 openjdk@1.21.0

# 之后就可以用别名切换
jabba use 21

# 查看所有别名
jabba alias

# 删除别名
jabba unalias 21
```

> 你目前的 `21-custom` 就是一个别名，指向实际安装的 Java 21 路径。

---

#### 关闭 jabba 的影响（还原 PATH）

```bash
jabba deactivate
```
