## 二、InnoDB 的逻辑存储结构：表空间 → 段 → 区 → 页 → 行

InnoDB 把数据存在磁盘文件里（默认每张表一个 `.ibd` 文件，叫**独立表空间**）。但它不是"一个字节一个字节"地读写，而是分了几个层次来管理空间。从大到小：

```
表空间 Tablespace   ← 一张表的所有数据（一个 .ibd 文件）
  └─ 段 Segment      ← 按用途分：数据段（聚簇索引叶子）、索引段（非叶子）等
       └─ 区 Extent  ← 一组连续的页，1 个区 = 64 个页 = 1MB
            └─ 页 Page ← ⭐ 磁盘 IO 的基本单位，默认 16KB
                 └─ 行 Row ← 我们插入的一条条记录
```

前面三层（表空间、段、区）是 InnoDB 管理和分配空间用的，了解即可，别陷进去。**真正天天要用的核心概念是"页"和"行"**。

### 2.1 "页（Page）"是磁盘 IO 的最小单位 ⭐

这是全章最重要的一句话：**InnoDB 读写磁盘，最小单位不是"一行"，而是"一页"（默认 16KB）。**

也就是说，哪怕你只 `SELECT` 一行数据，InnoDB 也会把这行所在的**整个 16KB 页**从磁盘读进内存（缓冲池 Buffer Pool）。为什么这么设计？

- **磁盘 IO 太贵**：一次磁盘随机 IO 是毫秒级，而内存访问是纳秒级，差了百万倍。既然读一次磁盘这么贵，就干脆一次多读一点（16KB），赌"你接下来大概率还要用附近的数据"（局部性原理）。
- **减少 IO 次数**：把数据按页组织，查询时只要定位到"在哪一页"，一次 IO 就把这一页的几十上百行全拿到内存了。

> 记死这条：**磁盘 IO 的单位是页（16KB），不是行。一次查询快不快，本质看它要读几个页（几次磁盘 IO）。** 后面讲 B+ 树"树高即 IO 次数"，讲的就是这个。

页大小可以查：

```sql
SHOW VARIABLES LIKE 'innodb_page_size';   -- 默认 16384，即 16KB
```

### 2.2 一个数据页内部长什么样

一个 16KB 的数据页，内部大致分这几块（从上到下）：

```
┌─────────────────────────────┐
│ File Header 文件头（38B）     │ ← 存本页页号、上一页/下一页的页号（页之间靠这个串成双向链表）
├─────────────────────────────┤
│ Page Header 页头             │ ← 本页有多少行、空闲空间在哪等
├─────────────────────────────┤
│ Infimum + Supremum          │ ← 两个虚拟行：本页最小/最大边界（哨兵）
├─────────────────────────────┤
│ User Records 用户记录         │ ← ⭐ 我们真正插入的行，按主键从小到大用单向链表串起来
│   row1 → row2 → row3 → ...   │
├─────────────────────────────┤
│ Free Space 空闲空间          │
├─────────────────────────────┤
│ Page Directory 页目录         │ ← ⭐ 页内的"目录/索引"，让页内查找能二分，不用逐行扫
├─────────────────────────────┤
│ File Trailer 文件尾（8B）     │ ← 校验页有没有写坏
└─────────────────────────────┘
```

三个要记住的关键点：

1. **页内的行按主键顺序串成单向链表**：行与行之间不是物理挨着的，而是每行记录里存了"下一行的位置"，按主键从小到大链起来。所以"按主键顺序遍历"很快，跟着链表走就行。

2. **页目录（Page Directory）让页内查找能二分** ⭐：如果页内有 100 行，找某个主键难道从头挨个比 100 次？不。InnoDB 把页内的行分成若干"槽（slot）"，每个槽指向一小组记录里最大的那条，页目录就是这些槽的数组。查找时**先在页目录里二分**定位到大致哪个槽，再在那一小组里顺着链表找几条即可。这就是"为什么页内查找快"。

3. **页之间是双向链表**：每个页的文件头里存了"上一页页号"和"下一页页号"，所有叶子页串成一个双向链表。所以**范围查询**（`WHERE price BETWEEN ... AND ...`）很高效：定位到起点页后，顺着双向链表一页页往后读就行。这也是 B+ 树比 B 树更适合数据库的原因之一（后面讲）。

> 一句话：**页内靠"单向链表 + 页目录二分"快速定位一行；页间靠"双向链表"支持高效范围扫描。**

## 三、行格式与行溢出：01 章"大字段拆表"的根因 ⭐

上一章有个结论："TEXT / BLOB 大字段建议单独拆表，避免拖慢主表行扫描。"当时只给了结论，现在从存储层解释清楚。

### 3.1 行格式（Row Format）

InnoDB 把一行数据在页里怎么摆，叫**行格式**。MySQL 8 默认是 `DYNAMIC`。行里除了你定义的字段值，还有一些额外信息（变长字段长度列表、NULL 值列表、记录头、以及隐藏列如事务 ID `DB_TRX_ID`、回滚指针 `DB_ROLL_PTR`——这两个隐藏列在第 05 章讲 MVCC 时是主角）。

现在只需要记住一个关键约束：**一个 16KB 的页，至少要能放下 2 行**。这意味着**理论上单行不能超过约 8KB**（16KB / 2）。那问题来了：`VARCHAR(1000)`、`TEXT`、`JSON` 这种可能很长的字段，一行放不下怎么办？

### 3.2 行溢出（Row Overflow）⭐

答案是**行溢出**：当一行数据太大、当前页放不下时，InnoDB 会把**大字段的大部分内容挪到专门的"溢出页（overflow page）"**里存，原来的行里只留一个 **20 字节的指针**，指向溢出页。

```
数据页里的行：
┌──────────────────────────────────────────────┐
│ id | name | price | ... | description(前缀+指针) │──┐
└──────────────────────────────────────────────┘  │ 20B 指针
                                                    ▼
                              ┌──────────────────────────┐
                              │ 溢出页：description 的完整内容 │
                              │ （可能跨多个溢出页）          │
                              └──────────────────────────┘
```

- `DYNAMIC` 行格式对大字段**几乎只在行内留指针**，大字段值整体挪到溢出页（这也是 8.0 默认它的原因，主页更紧凑）。

### 3.3 为什么大字段拖慢主表扫描

现在能解释 01 章的结论了。假设 `spu` 表里直接存了一个很长的 `description`（商品详情富文本，几 KB）：

- **大字段留在主表**：即使有溢出页，主表页里每行仍占更多空间（指针 + 可能的前缀），**一个 16KB 页能放的行数变少**。而全表扫描、范围扫描是**按页读**的——一页放的行少了，读同样多的行就要读更多页，也就是**更多次磁盘 IO**，扫描自然变慢。
- **很多查询根本不需要 description**：商品列表页只要 `id/name/price`，却因为 `description` 撑大了行、稀释了每页行数，连带把列表查询也拖慢了。

**拆表后**：把 `description` 拆到 `spu_detail(spu_id, description)`，主表 `spu` 的行变小、每页能放更多行，列表/范围查询扫的页数大幅减少；只有真正打开商品详情页时才去 `spu_detail` 查那一行大字段。这就是"大字段拆表"的存储层根因。

> 记住因果链：**大字段 → 行变大 → 每页行数变少 → 同样查询要读更多页 → 更多磁盘 IO → 变慢**。拆表就是为了让主表的行尽量小、每页尽量密。

## 四、为什么索引用 B+ 树：核心是"树高 = 磁盘 IO 次数" ⭐

现在数据按页存好了。可全表有几百万行、几万个页，查一行怎么快速定位到"在哪个页"？答案是**索引**，而 InnoDB 索引的数据结构是 **B+ 树**。为什么偏偏是它？用排除法看。

### 4.1 为什么不用二叉查找树 / 平衡二叉树（如红黑树）

二叉树每个节点只有 2 个孩子。数据量一大，**树就变得很高**。比如 100 万行，平衡二叉树高度约 `log₂(1,000,000) ≈ 20` 层。

关键问题：**树的每一层，通常意味着一次磁盘 IO**（要读一个新的页进内存）。20 层就是最多 20 次磁盘 IO，每次毫秒级——太慢了。**树越高，IO 越多。** 二叉树的"瘦高"结构对磁盘极不友好。

### 4.2 为什么不用哈希表

哈希表**等值查询**（`WHERE id = 5`）确实快，O(1)。但它有致命短板：

- **不支持范围查询**：`WHERE price BETWEEN 100 AND 200`、`ORDER BY`、`>` `<`，哈希全都用不上（哈希把顺序彻底打散了）。
- **不支持最左前缀匹配**（联合索引，第 03 章讲）。

电商查询大量是范围、排序、区间筛选，哈希满足不了。所以哈希索引只在特定场景用（InnoDB 有"自适应哈希索引"是内部优化，不用你管）。

### 4.3 B 树 vs B+ 树：为什么最终选 B+ 树 ⭐

B 树和 B+ 树都是"矮胖"的多叉树——**一个节点能放很多个孩子**，所以同样的数据量，树高比二叉树低得多（通常 3～4 层）。它们的区别，正是 B+ 树胜出的原因：

| 对比点 | B 树 | B+ 树（InnoDB 用这个） |
|---|---|---|
| 数据存哪 | 非叶子节点**也存数据** | **数据只存在叶子节点**，非叶子只存索引键 + 指针 |
| 非叶子节点能放多少 key | 少（因为还要放数据，占空间） | 多（只放 key + 指针，一个页能放上千个）→ **树更矮** |
| 范围查询 | 要在树里中序遍历，跳来跳去 | **叶子节点用双向链表串起来**，定位起点后顺链扫，极快 |
| 查询稳定性 | 有的数据在上层、有的在叶子，快慢不一 | 所有数据都在叶子，**任何查询都走到叶子，路径长度一致** |

两个决定性优势：

1. **非叶子节点不存数据 → 一个页能塞进更多"key + 指针" → 扇出（fan-out）更大 → 树更矮 → IO 更少。** 这是核心。
2. **叶子节点串成双向链表 → 范围查询、排序天然高效。** 这正好接上第二节讲的"页间双向链表"。

### 4.4 一棵 B+ 树能存多少行？为什么只要 3～4 层 ⭐

来算一笔账，感受"矮胖"有多夸张（数字是数量级估算，不用背精确值）：

- 一个页 16KB。**非叶子节点**里存的是"索引键 + 指向下层页的指针"。假设主键 `BIGINT`（8B）+ 指针（约 6B）≈ 14B 一条，一个页能放 `16KB / 14B ≈ 1000` 多个，取整算 **1000 个指针**（即扇出约 1000）。
- **叶子节点**存的是整行数据。假设一行 1KB，一个页能放 `16KB / 1KB ≈ 16` 行。

那么：

| 树高 | 能覆盖的数据量 | 估算 |
|---|---|---|
| 2 层（1 个根 + 叶子） | 1000 × 16 | ≈ 1.6 万行 |
| 3 层 | 1000 × 1000 × 16 | ≈ 1600 万行 |
| 4 层 | 1000 × 1000 × 1000 × 16 | ≈ 160 亿行 |

**结论**：一棵 3 层的 B+ 树就能存上千万行，4 层能存百亿行。也就是说，**电商绝大多数表，查一行只要 3～4 次磁盘 IO 就能定位到**。而且——

- **根节点常驻内存**：树的根页（甚至上层几层）会一直待在缓冲池里，实际磁盘 IO 往往只有 1～2 次。

这就是"加了索引为什么快"的最终答案：**把"扫几百万行"变成了"走 3～4 层树、读 3～4 个页"。**

> 一句话：**B+ 树矮胖（扇出大、树高 3~4 层），树高约等于磁盘 IO 次数，所以千万级表点查也只要几次 IO——这就是索引快的根本。**

## 五、聚簇索引与二级索引：数据本身就是一棵树 ⭐

InnoDB 有个和很多人直觉不同的设计：**表数据本身就是按主键组织成的一棵 B+ 树**。这棵树叫**聚簇索引（Clustered Index，也叫主键索引）**。理解这一点，才能理解"回表"。

### 5.1 聚簇索引（主键索引）：叶子节点存整行 ⭐

- InnoDB 的**表数据和主键索引是同一个东西**：整张表就是一棵以主键为 key 的 B+ 树，**叶子节点里存的是完整的一整行数据**。
- 所以"按主键查"是最快的——顺着这棵树走到叶子，整行数据就在那里，**不需要任何额外查找**。

主键从哪来？InnoDB 的规则：

1. 有主键 → 用主键当聚簇索引的 key；
2. 没主键 → 找第一个**非空唯一索引**；
3. 都没有 → InnoDB 偷偷生成一个 6 字节的隐藏行 ID 当聚簇索引。

**所以每张 InnoDB 表都有且只有一个聚簇索引**（数据只能按一种顺序物理组织）。这也是 01 章强调"一定要有主键"的深层原因——你不给，InnoDB 也会造一个，不如自己控制。

### 5.2 为什么自增主键对 InnoDB 友好：页分裂 ⭐

01 章说"自增主键顺序递增对聚簇索引友好"，现在能讲透了。

聚簇索引的叶子页是**按主键从小到大排列**的。插入新行时：

- **主键自增（顺序插入）**：新行的主键总是比现有的都大，永远**追加到最后一个叶子页的末尾**。当前页满了就开一个新页接在链表后面，简单高效。
- **主键随机（比如用 UUID、或业务字符串当主键）**：新行可能要插到**中间某个已经满了的页**里。这个页放不下，InnoDB 就得**页分裂（Page Split）**：把这个满页的一半数据挪到一个新页去，腾出空间。页分裂的代价：
  - 额外的 IO 和数据搬移；
  - 页被拆得半满，**空间利用率下降、碎片变多**；
  - 影响插入性能。

这就是"自增主键友好"的真相：**顺序追加，几乎不触发页分裂；随机主键频繁页分裂，又慢又占空间。** 也是"别用 UUID 当聚簇主键"的核心论据（要用 UUID，也建议用有序的 UUIDv7 或雪花 ID）。

### 5.3 二级索引（非主键索引）：叶子节点存主键值 ⭐

除了主键，你在别的列上建的索引（比如 01 章 `sku` 表的 `uk_sku_code`、后面要建的 `idx_category_id`）都叫**二级索引（Secondary Index）**，也叫辅助索引。

二级索引也是一棵 B+ 树，但**叶子节点里存的不是整行，而是"索引列的值 + 主键值"**。

```
聚簇索引（主键 id）              二级索引（sku_code）
     [非叶子: id]                    [非叶子: sku_code]
          │                               │
     ┌────┴────┐                     ┌────┴────┐
   叶子页                           叶子页
  id=1 → 整行(name,price,...)      'A001' → id=5
  id=2 → 整行(...)                 'A002' → id=1     ← 只存 sku_code + 主键 id
  id=3 → 整行(...)                 'A003' → id=3
```

为什么二级索引的叶子只存主键、不存整行？**因为整行数据只在聚簇索引里存一份**——如果每个二级索引都存整行，有 5 个索引就存 5 份整行，浪费空间且更新时要改 5 处。存主键值，就能"拿主键再回聚簇索引查整行"，只存一份数据。这就引出了"回表"。

### 5.4 回表（Back to Table）⭐⭐

**回表**：用二级索引查询时，如果需要的列在二级索引里没有，就得拿着二级索引叶子里的**主键值，再回到聚簇索引查一次，拿到整行**。这个"二次查找"就叫回表。

以 `SELECT * FROM sku WHERE sku_code = 'A002'` 为例，走 `uk_sku_code` 二级索引：

1. **第一步**：在 `sku_code` 二级索引这棵树里查 `'A002'`，走到叶子，拿到 `id = 1`；
2. **第二步（回表）**：拿 `id = 1` 回到聚簇索引那棵树里查，走到叶子，拿到整行 `(id, spu_id, sku_code, price, stock, ...)`。

**一次二级索引查询 = 走两棵 B+ 树**。回表是有成本的（多走一棵树、多几次 IO），所以第 03 章会讲**覆盖索引**——如果查询要的列，二级索引叶子里全都有（`sku_code + id`），就不用回表了，这叫"覆盖"。

> 记死这两句：
> - **聚簇索引叶子存整行；二级索引叶子存"索引列 + 主键值"。**
> - **回表 = 二级索引查到主键后，再回聚簇索引取整行；避免回表靠覆盖索引（第 03 章）。**

### 5.5 一张对照表收尾

| | 聚簇索引（主键） | 二级索引 |
|---|---|---|
| 一张表有几个 | 有且仅 1 个 | 可以有多个 |
| 叶子节点存什么 | **整行数据** | 索引列的值 + **主键值** |
| 查询代价 | 走一棵树直接拿到整行 | 走一棵树拿到主键，可能**回表**再走聚簇索引 |
| 谁决定 | 主键 / 第一个非空唯一键 / 隐藏行 ID | 你 `CREATE INDEX` 建的 |

## 六、把这一章接回商品表：一次查询到底发生了什么

拿 01 章的 `sku` 表串一遍，把抽象落到具体：

**场景 1：按主键查** `SELECT * FROM sku WHERE id = 100`
- 走聚簇索引，从根页 → 中间页 → 叶子页，3~4 次 IO（上层常驻内存，实际更少），叶子页里直接是整行。**最快的查法。**

**场景 2：按唯一键查** `SELECT * FROM sku WHERE sku_code = 'IP15P-256-BLK'`
- 先走 `uk_sku_code` 二级索引 → 拿到主键 `id` → **回表**走聚簇索引 → 拿整行。比场景 1 多走一棵树。

**场景 3：只查索引里有的列** `SELECT id FROM sku WHERE sku_code = 'IP15P-256-BLK'`
- 走 `uk_sku_code` 二级索引，叶子里就有 `sku_code + id`，要的 `id` 已经拿到，**不用回表**（覆盖索引，第 03 章展开）。

**场景 4：没有索引的列** `SELECT * FROM sku WHERE stock = 0`（`stock` 没建索引）
- 没有可用的树来定位，只能**全表扫描**：把聚簇索引的所有叶子页一页页读进来，逐行比对 `stock = 0`。数据量大就是灾难——这正是第 03、04 章要解决的"慢 SQL"。

> 这四个场景就是后面 EXPLAIN 里 `type` 列的现实映射（`const`/`ref`/`ALL` 等），第 04 章会把它们和执行计划一一对上。

## 七、常见坑与误区 ⚠️

| 坑 / 误区 | 真相 |
|---|---|
| 以为 InnoDB 按"行"读磁盘 | 按**页（16KB）**读，一次 IO 读一整页 |
| 以为索引是"另存一份指向行的指针列表" | 索引是 **B+ 树**；聚簇索引本身就是数据 |
| 用 UUID / 无序字符串当主键 | 随机插入触发**页分裂**，碎片多、插入慢；用自增或有序 ID |
| 以为"走了索引"就一定不回表 | 二级索引通常要**回表**取整行；不回表要靠覆盖索引 |
| `SELECT *` 无所谓 | `*` 几乎必然回表、还可能带出大字段撑大 IO；只查需要的列 |
| 大字段（TEXT/长 VARCHAR）留主表 | 行变大、每页行数变少，全表/范围扫描更慢；考虑**拆表** |
| 以为表越大树就高得吓人、查询就慢很多 | B+ 树很矮，千万行也就 3~4 层，点查 IO 差别很小 |
| 以为哈希索引什么都快 | 哈希不支持范围、排序、最左前缀，用途有限 |

## 八、小结

| 知识点 | 记住这一句 |
|---|---|
| 磁盘 IO 单位 | InnoDB 按**页（16KB）**读写，不是按行；快不快看读几个页 |
| 页内结构 | 行按主键串成单向链表，靠**页目录二分**快速定位 |
| 页间结构 | 叶子页用**双向链表**相连，范围查询顺链扫 |
| 行溢出 | 大字段挪到**溢出页**，行内留 20B 指针；大字段撑大行、稀释每页行数 |
| 为什么 B+ 树 | 矮胖、扇出大、**树高≈IO 次数**；叶子双向链表利于范围查询 |
| 树高 | 3 层≈千万行，4 层≈百亿行，点查只需几次 IO |
| 聚簇索引 | 表数据就是一棵按主键的 B+ 树，**叶子存整行**，每表仅 1 个 |
| 自增主键友好 | 顺序追加不页分裂；随机主键频繁**页分裂**、碎片多 |
| 二级索引 | 叶子存"索引列 + 主键值"，不存整行 |
| 回表 | 二级索引拿到主键后回聚簇索引取整行；避免靠**覆盖索引**（03 章） |
