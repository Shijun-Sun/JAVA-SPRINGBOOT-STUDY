# M02-02 · 死记硬背

> 标 ⭐ 是面试高频，标 ⚠️ 是容易踩的坑。原理以[主讲义](./02-InnoDB存储结构与B+树.md)为准，这份只放能直接背、直接答的结论。

---

## 一句话总纲 ⭐

> InnoDB 按**页（16KB）**读磁盘；表数据本身就是一棵按主键的 **B+ 树（聚簇索引，叶子存整行）**；B+ 树矮胖，**树高≈磁盘 IO 次数**，千万行也才 3~4 层；二级索引叶子只存"索引列 + 主键"，查整行要**回表**，避免回表靠**覆盖索引**。

---

## 存储结构五层（从大到小）

```
表空间 → 段 → 区（64 页=1MB） → 页（16KB，IO 单位）→ 行
```

- 前三层是空间管理，**只记"页"和"行"**。
- **页是磁盘 IO 的最小单位**，默认 16KB（`SHOW VARIABLES LIKE 'innodb_page_size'`）。哪怕只查一行，也读整页进内存。

---

## 页内 / 页间结构 ⭐

| 位置 | 怎么组织 | 作用 |
|---|---|---|
| 页**内**的行 | 按主键从小到大串成**单向链表** | 顺序遍历快 |
| 页**内**查找 | **页目录（Page Directory）** 分槽，先二分再顺链 | 页内定位不用逐行扫 |
| 页**间** | 叶子页之间**双向链表**相连 | **范围查询**顺链一页页扫 |

一句话：**页内单向链表 + 页目录二分；页间双向链表利于范围扫。**

---

## 行溢出：为什么大字段要拆表 ⭐

- 一页至少放 2 行 → 单行不能超约 8KB。
- 大字段（TEXT/BLOB/长 VARCHAR/JSON）放不下 → **行溢出**：大字段挪到**溢出页**，行内只留 **20B 指针**。
- 因果链背下来：**大字段 → 行变大 → 每页行数变少 → 同样查询读更多页 → 更多 IO → 变慢**。
- 所以：**大字段拆独立表**（`spu_detail`），让主表行小、每页密。

---

## 为什么用 B+ 树（排除法）⭐⭐

| 结构 | 为什么不用 |
|---|---|
| 平衡二叉树 | 太"瘦高"，100 万行约 20 层 → 最多 20 次磁盘 IO，慢 |
| 哈希 | 不支持**范围查询 / 排序 / 最左前缀**，只快等值 ⚠️ |
| B 树 | 非叶子**也存数据** → 每页放的 key 少 → 树更高；范围查询要中序遍历跳来跳去 |
| **B+ 树** ✅ | 非叶子**只存 key+指针**→扇出大、树矮；数据全在叶子；**叶子双向链表**利于范围查询 |

两个决定性优势：**① 非叶子不存数据 → 扇出大 → 树矮 → IO 少；② 叶子双向链表 → 范围/排序快。**

---

## 树高估算（数量级，不背精确值）⭐

- 非叶子页：一条 ≈ key(8B)+指针(6B) → 一页放约 **1000** 个（扇出≈1000）。
- 叶子页：一行约 1KB → 一页约 **16** 行。

| 树高 | 数据量 |
|---|---|
| 2 层 | ≈ 1.6 万行 |
| 3 层 | ≈ 1600 万行 |
| 4 层 | ≈ 160 亿行 |

**结论**：3~4 层就能存千万到百亿行；根/上层常驻内存，点查实际 IO 常只 1~2 次。**树高≈IO 次数**就是"索引快"的根。

---

## 聚簇索引 vs 二级索引 ⭐⭐

| | 聚簇索引（主键） | 二级索引 |
|---|---|---|
| 数量 | 每表**有且仅 1 个** | 可多个 |
| 叶子存 | **整行数据** | 索引列值 + **主键值** |
| 查询 | 走一棵树直接拿整行 | 走一棵树拿主键，可能**回表** |
| 谁定 | 主键 → 第一个非空唯一键 → 隐藏 6B 行 ID | 你 `CREATE INDEX` 建的 |

- **表数据本身就是聚簇索引这棵 B+ 树**（不是"另存的指针表"）。
- 二级索引叶子不存整行，是为了**整行只存一份**，省空间、更新只改一处。

---

## 回表 ⭐⭐（面试必问）

> **回表** = 二级索引查到**主键值**后，再回**聚簇索引**取整行的第二次查找。

`SELECT * FROM sku WHERE sku_code='A002'`：
1. 走 `sku_code` 二级索引 → 拿到 `id=1`；
2. **回表**：拿 `id=1` 回聚簇索引 → 取整行。
→ **一次二级索引查询 = 走两棵 B+ 树**。

避免回表 = **覆盖索引**（第 03 章）：要查的列二级索引叶子里全有，就不回表。
- `SELECT id FROM sku WHERE sku_code=?` → 叶子已有 `sku_code+id` → **不回表** ✅
- `SELECT * FROM sku WHERE sku_code=?` → 要整行 → **回表** ⚠️

---

## 页分裂：为什么自增主键友好 ⭐

- 叶子页按主键从小到大排。
- **自增主键**：新行主键最大 → 永远**追加到末尾** → 基本不分裂，紧凑。
- **随机主键（UUID/业务串）**：插到中间满页 → **页分裂**（挪一半数据到新页）→ IO 多、碎片多、空间利用率低、插入慢 ⚠️。
- 结论：**主键用自增或有序 ID（雪花/UUIDv7），别用随机 UUID/业务字符串当聚簇主键。**

---

## 四个查询场景速记（对应 04 章 EXPLAIN 的 type）⭐

| SQL | 发生什么 | 快慢 |
|---|---|---|
| `WHERE id=100`（主键） | 走聚簇索引直接拿整行 | 最快 |
| `WHERE sku_code=?`（唯一二级索引）+ `SELECT *` | 二级索引 → **回表** | 次之 |
| `SELECT id ... WHERE sku_code=?` | 二级索引**覆盖**，不回表 | 快 |
| `WHERE stock=0`（无索引列）+ `SELECT *` | **全表扫描**逐页逐行比 | 慢 ⚠️ |

---

## 常见坑速查 ⚠️

- InnoDB 按**页**读，不是按行。
- 索引是 **B+ 树**；**聚簇索引本身就是数据**，不是指针列表。
- `SELECT *` 几乎必回表、还可能带出大字段撑大 IO → **只查需要的列**。
- "走了索引" ≠ "不回表"；不回表要**覆盖索引**。
- UUID 当主键 → 页分裂、碎片；用自增/有序 ID。
- 大字段留主表 → 每页行数少、扫描慢 → 拆表。

---

## 自问自答（合上讲义答）

1. IO 单位？→ 页，16KB，不是行。
2. B+ 树为什么快？→ 矮胖、扇出大、树高≈IO 次数，3~4 层存千万~百亿行。
3. 回表是什么？→ 二级索引拿主键后回聚簇索引取整行；避免靠覆盖索引。
4. 自增主键为什么友好？→ 顺序追加不页分裂；随机主键频繁分裂、碎片多。
5. 聚簇/二级叶子各存什么？→ 聚簇存整行；二级存索引列+主键值。
