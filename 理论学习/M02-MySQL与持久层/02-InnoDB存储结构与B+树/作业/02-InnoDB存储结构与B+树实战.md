### 任务二：判断四条 SQL 各自会发生什么

> - 性质：知识点实验（理解巩固）

对下面四条 SQL，分别判断：**走哪个索引 / 全表扫描？要不要回表？为什么？**（`sku` 表：主键 `id`，唯一索引 `uk_sku_code`，`stock` 无索引）

```sql
-- A
SELECT * FROM sku WHERE id = 100;
-- B
SELECT * FROM sku WHERE sku_code = 'IP15P-256-BLK';
-- C
SELECT id FROM sku WHERE sku_code = 'IP15P-256-BLK';
-- D
SELECT * FROM sku WHERE stock = 0;
```

**验收标准：**

- A：走聚簇索引，直接拿整行，**不回表**；
- B：走 `uk_sku_code` 二级索引，**回表**取整行；
- C：走 `uk_sku_code` 二级索引，要的 `id` 在叶子里就有，**不回表**（覆盖）；
- D：`stock` 无索引，**全表扫描**，逐页逐行比对；
- 每条都要写"为什么"，不能只写结论。

### 任务三：估算 `sku` 表的 B+ 树高度与容量

> - 性质：知识点实验（理解巩固）
> - 实现位置：`homework/experimental/innodb-index-lab/树高估算.md`
> - 级别：必做
> - 是否阻塞推进：否
> - 前置交付：任务一
> - 验证方式：估算过程合理、数量级正确

按讲义第 4.4 节的方法，对 `sku` 表做一次数量级估算（不要求精确，讲清思路即可）：

1. 假设主键 `BIGINT`（8B）+ 页内指针（约 6B），估算**非叶子页的扇出**（一个页能放多少个"key + 指针"）；
2. 假设 `sku` 一行约 1KB，估算**一个叶子页能放多少行**；
3. 据此估算：2 层、3 层的 B+ 树分别能存多少行？`sku` 表要到什么数据量级才会长到 4 层？
4. 用一句话回答：**为什么"表变大"并不会让点查慢很多？**

**验收标准：**

- 体现"非叶子扇出大（约上千）、叶子放几十行"的数量级；
- 得出"3 层就能存千万级、点查只需几次 IO（上层还常驻内存）"的结论；
- 第 4 问答到点子上：树高增长极慢，IO 次数≈树高，所以数据量涨点查代价基本恒定。

### B. `EXPLAIN`：看一条 SQL 打算怎么执行 ⭐

`EXPLAIN` 放在 `SELECT` 前面，MySQL **不会真跑这条查询**，而是告诉你它**打算**怎么执行——走不走索引、要不要回表、要扫多少行。这是第 04 章的主角，本章先认识两列：

```sql
EXPLAIN SELECT * FROM demo_sku WHERE sku_code = 'A-002';   -- 会回表
EXPLAIN SELECT id FROM demo_sku WHERE sku_code = 'A-002';  -- 覆盖索引，不回表
EXPLAIN SELECT * FROM demo_sku WHERE id = 1;               -- 主键直查
EXPLAIN SELECT * FROM demo_sku WHERE stock = 0;            -- 无索引，全表扫描
```

读输出先看两列：

- **`type`**：访问类型，好坏排序（部分）：`const`（主键/唯一键等值，最好）> `ref`（普通索引等值）> `range`（范围）> `index`（扫整个索引）> `ALL`（全表扫描，最差 ⚠️）。
- **`Extra`**：附加信息。看到 **`Using index`** 表示**用了覆盖索引、不回表**（好）；看到 `Using where` 表示在存储层之上还要过滤。

> 本章只要能区分：`const`/`ref`（走了索引）vs `ALL`（全表扫描）；`Using index`（不回表）vs 没有它（可能回表）。更系统的 `EXPLAIN` 解读在第 04 章。
