## 一、我们在解决什么问题：内存存储撑不住什么

回顾 M01，`product-service` 的数据存在 `InMemoryProductRepository` 里，本质是一个内存 `Map<Long, ProductEntity>`。它在教学阶段够用，但一进真实场景就全面崩掉：

| 内存存储的问题 | 后果 | 关系库怎么解决 |
|---|---|---|
| 进程重启数据全丢 | 上线部署一次，商品全没了 | 数据持久化到磁盘 |
| 多实例各存各的 | M05 起多实例后，A 实例创建的商品 B 实例查不到 | 数据集中存一处，多实例共享 |
| 没有复杂查询能力 | "按分类+价格区间+销量排序分页"要手写一堆 Java 循环 | SQL + 索引，声明式查询 |
| 没有并发控制 | 两个请求同时扣库存，扣成负数 | 事务 + 锁（第 05、06 章） |
| 没有统计分析 | "本月各分类销售额" 无从查起 | 聚合查询、关联查询 |

所以换 MySQL 不是"为了用数据库而用"，而是**内存模型解决不了持久化、共享、查询、并发这四件事**。

但代价也真实存在，得心里有数：

- **多了一层网络 + 磁盘 IO**：内存读是纳秒级，一次数据库查询是毫秒级，慢好几个数量级——这就是后面要学索引优化、连接池、缓存的根本原因；
- **多了对象与表的映射成本**：Java 对象和数据库行不是一回事，中间要做 ORM 映射（第 08 章）；
- **schema 变更有成本**：内存里加个字段改行代码就行，数据库改表结构要考虑存量数据、迁移脚本（第 09 章 Flyway）。

> 一句话：**关系库用"慢一点、复杂一点"换来了"数据不丢、能共享、能查询、能保证一致性"**。这笔账在任何有状态的系统里都必须算。

## 二、电商核心概念：SPU、SKU、分类 —— 先把业务理清再建表 ⭐

建表之前，**必须先把业务概念理清**。电商建模最经典、也最容易一开始就搞错的，就是 SPU 和 SKU 的关系。

### 2.1 SPU 与 SKU

- **SPU（Standard Product Unit，标准产品单元）**：一个"商品"的抽象，是你在商品详情页看到的那个标题。比如"iPhone 15 Pro"就是一个 SPU。
- **SKU（Stock Keeping Unit，库存量单位）**：SPU 下**具体到可下单、可扣库存的最小单位**。"iPhone 15 Pro 256G 原色钛金属"是一个 SKU，"iPhone 15 Pro 512G 黑色钛金属"是另一个 SKU。

关键点：**价格和库存挂在 SKU 上，不是挂在 SPU 上**。

```
SPU：iPhone 15 Pro                         ← 一个商品（标题、描述、品牌、分类）
 ├─ SKU：256G 原色钛金属   ¥7999   库存 120  ← 可下单的最小单位（价格、库存在这里）
 ├─ SKU：256G 黑色钛金属   ¥7999   库存 88
 ├─ SKU：512G 原色钛金属   ¥9999   库存 30
 └─ SKU：512G 黑色钛金属   ¥9999   库存 0（可售罄）
```

这就是"一个 SPU 对多个 SKU"的一对多关系。SKU 之间靠**销售属性**（容量、颜色）区分。

> M01 的 `ProductEntity` 其实是把 SPU 和 SKU 揉在了一起（一个 `product` 既有 `name` 又有 `price` 和 `sku` 字段）——这在只卖"无规格单品"时能用，但一旦商品有多规格就不够了。本章先把概念讲清，作业里会让你设计**规范的 SPU/SKU 拆分**，同时保留一张能平滑过渡的商品表。

### 2.2 分类（Category）

分类通常是**树形结构**：一级分类"手机数码" → 二级"手机" → 三级"智能手机"。树形结构在关系库里最常用的存法是**邻接表模型**：每行存自己的 `id` 和 `parent_id`。

```
category(id=1, name='手机数码', parent_id=0)
category(id=2, name='手机',     parent_id=1)
category(id=3, name='智能手机', parent_id=2)
```

`parent_id=0`（或 NULL）表示顶级。这种存法写简单、改简单，缺点是"查某节点的所有后代"要递归（MySQL 8 支持递归 CTE `WITH RECURSIVE` 能解决）。电商分类层级一般不深（3~4 级），邻接表足够。

> 还有 路径枚举、嵌套集、闭包表 等更复杂的树模型，适合层级很深或频繁查子树的场景。电商分类用邻接表即可，其它作为知识储备，别过度设计。

### 2.3 本章范围

完整电商域还有订单、库存流水、用户、购物车、优惠券等，会在后续模块逐步建。**本模块（M02）聚焦商品域**：SPU、SKU、分类，把这块的建模和落地吃透，其它域用同样的方法论展开。

## 三、范式与反范式：什么时候拆表，什么时候故意冗余 ⭐

### 3.1 三大范式，一句话版本

- **第一范式（1NF）**：每个字段都是**不可再分的原子值**。反例：把"256G,512G"塞进一个字段用逗号分隔——违反 1NF，查询和更新都是噩梦。
- **第二范式（2NF）**：非主键字段必须依赖**整个主键**，不能只依赖主键的一部分（针对联合主键）。
- **第三范式（3NF）**：非主键字段之间不能有传递依赖。反例：`sku` 表里存了 `category_name`，而 `category_name` 其实由 `category_id` 决定——分类改名要改一堆 SKU 行，且容易不一致。

范式的核心目的：**消除冗余，避免更新异常**。一份数据只存一处，改的时候只改一处，不会出现"这里改了那里没改"的不一致。

### 3.2 反范式：为性能故意冗余

严格遵守范式会导致查询要 `JOIN` 很多表。电商高并发场景下，`JOIN` 是性能杀手。所以实践中经常**故意冗余**，用空间和一致性维护成本换查询性能：

- 商品列表页要显示"分类名"，如果每次都 `JOIN category` 表，列表查询就变慢——可以在 `product` 表冗余一个 `category_name`；
- 订单表里冗余下单时的"商品名称、单价、SKU 规格"——因为订单是**历史快照**，商品后来改名改价，已生成的订单不能跟着变。这种冗余不仅是为性能，更是**业务语义要求**。

反范式的代价：**冗余字段要在源头变化时同步更新**（分类改名要同步 `product.category_name`），否则数据不一致。所以反范式是一个**有意识的权衡**，不是偷懒。

> 架构判断原则：**先按范式设计，识别出明确的性能瓶颈或历史快照需求后，再有针对性地反范式**。一上来就冗余一堆，等于给自己埋一致性的雷。

### 3.3 关联关系怎么落表

| 关系 | 落表方式 | 例子 |
|---|---|---|
| 一对多 | "多"的一方存外键 | SKU 存 `spu_id` 指向 SPU |
| 多对多 | 中间关联表 | 商品与标签：`product_tag(product_id, tag_id)` |
| 一对一 | 共用主键 或 一方存唯一外键 | 商品与商品详情大字段拆表 |

**注意**：互联网大厂实践里，很多团队约定**不建物理外键约束**（不写 `FOREIGN KEY`），只在应用层维护关系。原因：物理外键在高并发下会带来额外的锁和检查开销，且分库分表后外键根本没法用。这一点后面第 05、06 章讲锁、M08 讲分库分表时会更有体会。**本课程建模时表达"逻辑外键"（字段叫 `xxx_id`），但默认不加物理 `FOREIGN KEY` 约束**，并在作业里说明这个取舍。

## 四、字段类型选型：细节里全是坑 ⭐

字段类型选错，轻则浪费空间、影响索引效率，重则算错钱、丢数据。这一节每一条都要记住。

### 4.1 金额：只能用 DECIMAL，绝不能用 float/double ⭐

```sql
price DECIMAL(10, 2) NOT NULL   -- 总共 10 位，小数 2 位，最大 99999999.99
```

- `float` / `double` 是**二进制浮点数**，无法精确表示十进制小数（`0.1 + 0.2 != 0.3`）。用它存金额，累加、对账迟早算错——这是财务事故，不是小 bug。
- `DECIMAL(M, D)` 是**定点数**，精确存储，`M` 是总位数，`D` 是小数位数。金额用 `DECIMAL(10,2)` 或按业务需要调整。
- Java 侧对应 `BigDecimal`（M01 的 `ProductEntity.price` 已经是 `BigDecimal`，选对了）。

> 记死这条：**钱用 DECIMAL + BigDecimal，任何时候都不用浮点。**

### 4.2 主键：BIGINT UNSIGNED

```sql
id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY
```

- 用 `BIGINT`（8 字节）而不是 `INT`（4 字节，最大约 21 亿）：电商数据量大，`INT` 的上限在订单、流水这种表上真的会撑爆，主键溢出是灾难。空间换安全，值得。
- `UNSIGNED` 无符号，主键不会为负，范围翻倍。
- 主键策略见第五节。

### 4.3 时间：DATETIME vs TIMESTAMP

```sql
created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

- `DATETIME`：8 字节（MySQL 5.6.4 起小数秒另算），范围 1000～9999 年，**存的是字面值，不随时区变**。
- `TIMESTAMP`：4 字节，范围 1970～2038（有 **2038 年问题**），存 UTC 时间戳、读取时按连接时区转换。
- 电商建议用 `DATETIME`：不受 2038 限制，行为更直观。时区问题在**应用层统一处理**（比如全站用 UTC 存、展示层转）。
- `ON UPDATE CURRENT_TIMESTAMP` 让 `updated_at` 自动维护，省心。Java 侧对应 `LocalDateTime`（`ProductEntity` 已经在用）。

### 4.4 字符串：CHAR / VARCHAR / TEXT

- `VARCHAR(n)`：变长，最常用。`n` 是字符数（`utf8mb4` 下），按需给足即可，别一律 `VARCHAR(255)` 也别抠太死。
- `CHAR(n)`：定长，适合长度固定的值（如国家码、固定位数的状态码）。
- `TEXT` / `LONGTEXT`：大文本（商品详情富文本）。**注意**：`TEXT` 大字段建议**单独拆表**，避免拖慢主表的行扫描（第 02 章讲 InnoDB 行存储时会更清楚为什么）。
- `sku` 编码这种：`VARCHAR(64)` 足够，并且要加**唯一索引**（M01 的业务规则就是 SKU 不能重复）。

### 4.5 字符集：一律 utf8mb4 ⭐

```sql
DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_0900_ai_ci
```

- MySQL 的 `utf8`（即 `utf8mb3`）是**残缺的 UTF-8，最多 3 字节，存不了 emoji 和部分生僻字**。商品名、评论里一个 emoji 就能让插入报错或截断。
- 一律用 `utf8mb4`（真正的 4 字节 UTF-8）。排序规则 MySQL 8 默认 `utf8mb4_0900_ai_ci`（基于 Unicode 9.0，`ai` 不区分重音、`ci` 不区分大小写）。

### 4.6 状态/枚举：用 TINYINT + 应用层枚举，不用 MySQL 的 ENUM

```sql
status TINYINT NOT NULL DEFAULT 1 COMMENT '1-上架 0-下架'
```

- 不建议用 MySQL 的 `ENUM` 类型：改枚举值要改表结构、跨库迁移麻烦、ORM 支持不一。
- 推荐 `TINYINT`（1 字节）存状态码，含义在**应用层用 Java 枚举**维护，并在字段 `COMMENT` 里写清对照。这样加状态只改代码不改表。

### 4.7 布尔：TINYINT(1)

MySQL 没有真正的布尔类型，`BOOLEAN` 是 `TINYINT(1)` 的别名。用 `TINYINT(1)`，0/1 表示真假即可。

### 4.8 JSON 类型：能用但别滥用

MySQL 5.7+ 支持原生 `JSON` 类型，适合存**结构不固定、不需要单独索引/查询**的附加信息（如商品的扩展规格参数）。但：**需要频繁按某个属性查询、排序、统计的字段，不要塞进 JSON**，该拆成独立列或独立表。JSON 是"半结构化数据的容器"，不是偷懒不建模的借口。

## 五、主键策略：自增 vs 业务键 vs 分布式 ID

### 5.1 自增主键（AUTO_INCREMENT）

最常用。优点：简单、占空间小、**顺序递增对 InnoDB 聚簇索引友好**（新行总是追加到 B+ 树末尾，减少页分裂——第 02 章展开）。

缺点：
- **分库分表后会主键冲突**（每个库都从 1 开始自增）；
- 顺序递增会**暴露业务量**（竞对看你订单号就知道你一天多少单）；
- 不适合分布式环境下多节点同时生成。

### 5.2 不要用"有业务含义的字段"当主键

比如拿 `sku` 编码当主键。问题：业务字段可能会变（改编码规则），主键一变，所有引用它的外键、缓存 key 全要跟着改，是灾难。**主键应该无业务含义、稳定不变**。`sku` 是业务唯一键，给它加 `UNIQUE` 索引即可，但主键还是用独立的 `id`。

### 5.3 分布式 ID（预告）

分库分表、多服务后，需要全局唯一且趋势递增的 ID。常见方案：**雪花算法（Snowflake）**——用"时间戳 + 机器号 + 序列号"拼一个 64 位 long，既全局唯一又大致有序。这块在 **M08 分布式** 展开，本模块先用自增主键，知道有这么回事即可。

> 本模块选型：**商品域先用 `BIGINT UNSIGNED AUTO_INCREMENT`**，够用且简单。等 M08 拆服务时再引入分布式 ID，并讲清迁移成本——这也是一次真实的架构演进。

## 六、实操：把 ProductEntity 落成一张 MySQL 表

M01 的 `ProductEntity` 字段：`id, name, sku, price, category, createdAt, updatedAt`。先把它**原样**落成一张规范的 MySQL 表（作为落地改造的过渡），再讨论怎么演进到 SPU/SKU。

### 6.1 商品表 DDL（过渡版，对应现有单品模型）

```sql
CREATE TABLE `product` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  `name`        VARCHAR(100)    NOT NULL                COMMENT '商品名称',
  `sku`         VARCHAR(64)     NOT NULL                COMMENT 'SKU 编码，业务唯一',
  `price`       DECIMAL(10,2)   NOT NULL                COMMENT '价格，单位元',
  `category`    VARCHAR(50)     NOT NULL                COMMENT '分类名称（过渡字段，后续改为 category_id）',
  `status`      TINYINT         NOT NULL DEFAULT 1      COMMENT '1-上架 0-下架',
  `created_at`  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP                    COMMENT '创建时间',
  `updated_at`  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_sku` (`sku`)
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COLLATE = utf8mb4_0900_ai_ci
  COMMENT = '商品表（单品过渡模型）';
```

逐条对照本章知识点：

- `id BIGINT UNSIGNED AUTO_INCREMENT` + `PRIMARY KEY`：无业务含义的自增主键（5.1、5.2）；
- `price DECIMAL(10,2)`：金额定点数（4.1）；
- `sku VARCHAR(64)` + `UNIQUE KEY uk_sku`：业务唯一键加唯一索引，落实 M01 的"SKU 不能重复"规则；
- `status TINYINT`：状态用 TINYINT + 应用层枚举（4.6）；
- `created_at` / `updated_at DATETIME` + 自动维护（4.3）；
- `ENGINE=InnoDB`、`utf8mb4`：引擎和字符集（4.5，InnoDB 原因第 02 章讲）。

> `category VARCHAR(50)` 是**过渡妥协**：现有 `ProductEntity` 就是存分类名字符串。规范做法是拆分类表用 `category_id` 外键，作业里会让你设计规范版。这里保留字符串，是为了第 10 章落地时能**平滑替换内存实现、测试不大改**——真实项目里的迁移也常是分步走，先搬家再重构。

### 6.2 演进方向：SPU / SKU / 分类拆分（作业要做的规范版）

规范的多规格模型大致是：

```
category (id, parent_id, name, level, ...)                  ← 分类树
spu      (id, name, category_id, brand, description, ...)   ← 商品（SPU）
sku      (id, spu_id, sku_code, price, stock, spec_json, ...) ← 库存单位（价格/库存在这）
```

- `spu.category_id` 逻辑外键指向分类；
- `sku.spu_id` 逻辑外键指向 SPU（一对多）；
- 价格、库存落在 `sku`；
- `spec_json` 存销售属性（如 `{"容量":"256G","颜色":"黑色"}`），不需要单独查询的规格用 JSON（4.8），需要按属性筛选的场景则要另建规格表——这是一个权衡点，作业里会让你说明选择。

> 索引怎么加（`spu_id`、`category_id`、`sku_code` 唯一索引等）在**第 03 章**展开——本章先把表结构和字段类型定下来，索引单独一章讲透。

## 七、约束、默认值与几个工程约定

- **NOT NULL 尽量给**：可空字段会让查询和索引更复杂（`NULL` 的比较、索引行为都有特殊性）。能给默认值、能非空的就别留空。
- **软删除**：电商很少物理删除数据（要留痕、要对账）。常用 `is_deleted TINYINT DEFAULT 0` 或 `deleted_at DATETIME NULL` 做**软删除**，查询时带上 `WHERE is_deleted = 0`。代价：所有查询都要记得带这个条件（框架层可统一处理，第 08 章 MyBatis-Plus 的逻辑删除会讲）。
- **审计字段**：`created_at` / `updated_at` 几乎每张表都要有；再往上还有 `created_by` / `updated_by`（谁操作的），做后台管理时很有用。
- **COMMENT 写全**：每个表、每个字段都写清 `COMMENT`。库表是团队资产，注释是最省事的文档。
- **命名规范**：表名、字段名统一小写 + 下划线（`category_id` 而不是 `categoryId`）；索引名有前缀约定（主键 `PRIMARY`、唯一 `uk_`、普通 `idx_`）。

## 八、常见坑 ⚠️

| 坑 | 现象 | 正确做法 |
|---|---|---|
| 金额用 float/double | 累加、对账算错钱 | `DECIMAL` + `BigDecimal` |
| 字符集用 utf8(mb3) | emoji/生僻字插入报错或截断 | 一律 `utf8mb4` |
| 主键用 INT | 数据量涨上去主键溢出 | `BIGINT UNSIGNED` |
| 拿业务字段当主键 | 业务规则一变，主键和所有引用全崩 | 独立无意义主键 + 业务键加唯一索引 |
| 一个字段塞逗号分隔的多值 | 违反 1NF，查询/更新噩梦 | 拆行或拆表，或用 JSON（谨慎） |
| 一上来就大量反范式冗余 | 数据不一致，改一处漏一处 | 先范式，识别瓶颈后再定向冗余 |
| TEXT 大字段和主表混在一起 | 主表行变大，扫描变慢 | 大字段拆独立表 |
| 时间用 TIMESTAMP | 2038 年问题、时区行为绕 | `DATETIME`，时区应用层统一 |
| 该有的审计/软删除字段没留 | 出问题无法追溯、误删无法恢复 | 标配 `created_at/updated_at/is_deleted` |

## 九、小结

| 知识点 | 记住这一句 |
|---|---|
| 为什么上关系库 | 内存解决不了持久化、共享、查询、并发这四件事 |
| SPU vs SKU | SPU 是商品抽象，SKU 是可下单最小单位，**价格库存在 SKU** |
| 分类 | 树形用邻接表（`id` + `parent_id`），层级不深够用 |
| 范式 | 先按范式消冗余，识别瓶颈后再定向反范式 |
| 逻辑外键 | 表达 `xxx_id` 关系，但默认不加物理 `FOREIGN KEY` |
| 金额 | `DECIMAL` + `BigDecimal`，永远不用浮点 |
| 主键 | `BIGINT UNSIGNED AUTO_INCREMENT`，无业务含义 |
| 时间 | `DATETIME`，别用 `TIMESTAMP` |
| 字符集 | 一律 `utf8mb4` |
| 状态枚举 | `TINYINT` + 应用层 Java 枚举，不用 MySQL `ENUM` |
| 工程标配 | 审计字段、软删除、COMMENT、小写下划线命名 |
