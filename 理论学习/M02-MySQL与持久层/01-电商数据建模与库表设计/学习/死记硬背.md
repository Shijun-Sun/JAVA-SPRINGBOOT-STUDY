## 递归 CTE：查分类子树的标准写法 ⭐（本章重点，务必背下模板）

邻接表（`id` + `parent_id`）存树，**查某节点的所有后代要递归**。MySQL 8 之前只能在应用层用循环一层层查，8.0 起有了 `WITH RECURSIVE`，一条 SQL 搞定。

### 先记这个模板（改表名/字段就能用）

```sql
WITH RECURSIVE category_tree AS (
    -- ① 锚成员（anchor）：递归的起点，只执行一次
    SELECT id, name, parent_id, 1 AS depth
    FROM category
    WHERE name = '手机数码'          -- 起点条件，也可以写 WHERE id = 1

    UNION ALL

    -- ② 递归成员：反复执行，直到查不出新行为止
    SELECT c.id, c.name, c.parent_id, ct.depth + 1
    FROM category c
    JOIN category_tree ct ON c.parent_id = ct.id
)
SELECT * FROM category_tree ORDER BY depth, id;
```

### 一行行拆开看它在干什么

这段 SQL 别当成"一条查询"，把它理解成一个**会自己滚动的循环**：

1. `WITH RECURSIVE category_tree AS (...)`
   定义一个临时结果集（叫 CTE，Common Table Expression），名字是 `category_tree`。加了 `RECURSIVE` 关键字，它就**允许在定义里引用自己**。最后那句 `SELECT * FROM category_tree` 才是真正取结果。

2. **锚成员**（`UNION ALL` 上面那段）
   递归的"第 0 步"。这里查出起点——"手机数码"那一行。它**只跑一次**，结果先放进 `category_tree`。

3. `UNION ALL`
   把锚成员和递归成员的结果**拼起来**（用 `ALL` 不去重，效率高，树里 id 本来也不重复）。

4. **递归成员**（`UNION ALL` 下面那段）
   关键在 `JOIN category_tree ct`——它拿**上一轮**刚查出来的结果，去 `category` 表里找"谁的 `parent_id` 等于上一轮某行的 `id`"，也就是找**下一层子节点**。
   - 第 1 轮：拿"手机数码"（id=1），找出 parent_id=1 的行 → 二级分类"手机";
   - 第 2 轮：拿上一轮的"手机"，找出它的子节点 → 三级"智能手机";
   - 一直滚到**某一轮查不出新行**（叶子节点没有子节点了），递归自动停止。

5. `depth` 列是自己加的**层级计数**：锚成员写死 `1`，递归成员每滚一层 `+1`。它不是必须的，但能让你看清"查到第几层了"，也方便按层排序。

### 三个必须记住的点 ⭐

- **结构固定**：`WITH RECURSIVE 名字 AS ( 锚成员 UNION ALL 递归成员 )`，少一块都不行。
- **锚成员是起点，递归成员靠 JOIN 自己滚**，`ON` 条件写的是"父子关系"（`c.parent_id = ct.id`）。
- **递归成员的列数、类型必须和锚成员一致**（都是 `id, name, parent_id, depth` 四列），否则报错。

### 反过来查"某节点的所有祖先"（往上找）

把 `ON` 条件的父子方向调过来即可——从"找我的孩子"变成"找我的父亲"：

```sql
WITH RECURSIVE category_path AS (
    SELECT id, name, parent_id
    FROM category
    WHERE id = 3                       -- 从"智能手机"往上找

    UNION ALL

    SELECT c.id, c.name, c.parent_id
    FROM category c
    JOIN category_path cp ON c.id = cp.parent_id   -- 注意：这里反过来了
)
SELECT * FROM category_path;
```

### 坑与代价 ⚠️

- **无限递归**：如果数据成环（A 的父是 B，B 的父又是 A），递归停不下来。MySQL 有个保险 `cte_max_recursion_depth`（默认 1000 层），超了直接报错中止，不会把库拖死。数据建模时别让分类成环。
- **性能代价**：递归本质是**多轮 JOIN**，层级越深、子树越大越慢。这就是讲义说的"邻接表查子树要递归的代价"。分类树浅（3~4 层）问题不大；如果层级很深、还频繁查整棵子树，才考虑闭包表等其它树模型。
- **版本要求**：`WITH RECURSIVE` 是 MySQL **8.0+** 才有。5.7 及以前只能应用层循环查，或换树模型。

## 面试经典：查"比昨天凉快"的日期（自连接 / 日期相减）⭐

> 就是 LeetCode 197 "Rising Temperature" 的变体。表里存每天的气温，要你查出**当天气温比前一天低**的日期。考点是"同一张表，按相邻日期把今天和昨天拼在一起比"。

假设表长这样：

```
Weather(id, record_date, temperature)   -- 每天一行
```

### 写法一：自连接（Self Join）——最经典，先掌握这个

把**同一张表当成两张用**（起两个别名 `today` / `yesterday`），按"日期差一天"的条件连起来，再比气温：

```sql
SELECT today.id, today.record_date
FROM Weather AS today
JOIN Weather AS yesterday
  ON today.record_date = yesterday.record_date + INTERVAL 1 DAY   -- 今天 = 昨天 + 1 天
WHERE today.temperature < yesterday.temperature;                  -- 比昨天凉快
```

思路拆解：

- `Weather AS today` 和 `Weather AS yesterday` 是**同一张表的两个别名**——这就是"自连接"，把表复制一份和自己拼。
- `ON` 条件表达"这两行是相邻的两天"：`today` 的日期正好等于 `yesterday` 的日期加一天。
- 拼好之后每一行就同时有了"今天"和"昨天"的气温，`WHERE` 里直接比大小。查凉快就用 `<`，查升温就改成 `>`。

### 写法二：窗口函数 `LAG`（MySQL 8+，更现代）

`LAG(x) OVER (ORDER BY 日期)` 的意思是"按日期排好序后，取**上一行**的 x 值"，等于直接把昨天的数据拉到今天这一行旁边：

```sql
SELECT id, record_date
FROM (
    SELECT id, record_date, temperature,
           LAG(temperature)  OVER (ORDER BY record_date) AS prev_temp,   -- 昨天的气温
           LAG(record_date)  OVER (ORDER BY record_date) AS prev_date    -- 上一行的日期
    FROM Weather
) t
WHERE temperature < prev_temp
  AND DATEDIFF(record_date, prev_date) = 1;    -- 确认上一行真的是"昨天"，不是隔了好几天
```

### 唯一的大坑 ⚠️（当年面试没做出来多半栽在这）

**别用 `id` 去比相邻，要用日期。** 很多人第一反应写 `today.id = yesterday.id + 1`——错。`id` 是自增主键，**不保证和日期顺序一致，也可能有断号**（中间删过数据）。相邻的两天靠**日期**判断，不是靠 id。

- 日期差一天的两种写法：`record_date = 昨天 + INTERVAL 1 DAY`，或 `DATEDIFF(今天, 昨天) = 1`。
- 用 `LAG` 时也要补一句 `DATEDIFF(...) = 1`，因为如果某天没记录（日期有缺口），"上一行"未必就是"昨天"。

### 一句话记住

> 相邻行比较（比昨天凉快、比上月增长）= **自连接按日期相减** 或 **`LAG` 窗口函数取上一行**；判断"相邻"永远用日期，绝不用 id。

## 字段类型选型速查 ⭐

| 场景 | 用什么 | 为什么 / ⚠️ |
|---|---|---|
| 金额 | `DECIMAL(10,2)` | 定点数精确；`float/double` 会算错钱 ⚠️ |
| 主键 | `BIGINT UNSIGNED AUTO_INCREMENT` | `INT` 会溢出；无业务含义 |
| 时间 | `DATETIME` | 不受 2038 限制；`TIMESTAMP` 有时区坑 ⚠️ |
| 短字符串 | `VARCHAR(n)` | 变长，按需给长度 |
| 大文本 | `TEXT`，且**拆独立表** | 混主表会拖慢行扫描 ⚠️ |
| 状态/枚举 | `TINYINT` + 应用层 Java 枚举 | 别用 MySQL 的 `ENUM`，改值要改表 |
| 布尔 | `TINYINT(1)` | MySQL 没有真布尔 |
| 不固定的附加属性 | `JSON` | 但要按属性查/排序的字段别塞 JSON ⚠️ |
| 字符集 | `utf8mb4` | `utf8`(mb3) 存不了 emoji/生僻字 ⚠️ |

一句话：**钱用 DECIMAL、主键用 BIGINT UNSIGNED、时间用 DATETIME、字符集用 utf8mb4**。

## FLOAT vs DECIMAL：一眼看穿为什么金额不能用浮点 ⭐

```sql
-- FLOAT 累加会出现精度误差
SELECT 0.1 + 0.2;                 -- 结果不是干净的 0.3
SELECT CAST(0.1 AS DECIMAL(10,2)) + CAST(0.2 AS DECIMAL(10,2));  -- 精确 0.30
```

浮点是二进制存十进制小数，天生存不准；金额累加、对账迟早算错。**记死：钱用 `DECIMAL` + Java `BigDecimal`，任何时候不用浮点。**

## SPU / SKU / 分类 ⭐

| 概念 | 是什么 | 价格库存在哪 |
|---|---|---|
| SPU | 商品抽象（"iPhone 15 Pro"） | ❌ |
| SKU | 可下单最小单位（"256G 黑色"） | ✅ 价格、库存都挂 SKU |
| 分类 | 树形，邻接表 `id`+`parent_id` | — |

- SPU 一对多 SKU，**"多"的一方（SKU）存 `spu_id`**。
- 关系用**逻辑外键**（字段 `xxx_id`），默认**不加物理 `FOREIGN KEY`**（高并发下锁/检查开销，分库分表用不了）。

---

## 主键三条铁律 ⭐

1. 用 `BIGINT UNSIGNED AUTO_INCREMENT`，别用 `INT`（会溢出）。
2. **别拿业务字段当主键**（如 `sku_code`）——业务规则一变，主键和所有引用全崩。
3. 业务唯一（如 `sku_code` 不能重复）→ 给它加 `UNIQUE` 索引，主键仍用独立 `id`。

## 工程标配（每张表都要有）

- 审计字段：`created_at` / `updated_at`（`ON UPDATE CURRENT_TIMESTAMP` 自动维护）。
- 软删除：`is_deleted TINYINT DEFAULT 0`，查询带 `WHERE is_deleted = 0`；电商很少物理删除（要留痕对账）。
- 每个表/字段写 `COMMENT`；命名一律小写下划线（`category_id` 不是 `categoryId`）。
- 引擎 `InnoDB`，字符集 `utf8mb4`。

---

## 一句话总结

> 邻接表存树、查子树靠 `WITH RECURSIVE`（锚成员起点 + 递归成员 JOIN 自己往下滚）；建表时**钱用 DECIMAL、主键用 BIGINT UNSIGNED、时间用 DATETIME、字符集 utf8mb4、状态用 TINYINT**，关系用逻辑外键不加物理约束，审计/软删除/COMMENT 是标配。
