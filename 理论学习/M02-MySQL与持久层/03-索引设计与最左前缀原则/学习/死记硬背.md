# M02-03 · 死记硬背

> 标 ⭐ 是面试高频，标 ⚠️ 是容易踩的坑。原理以[主讲义](./03-索引设计与最左前缀原则.md)为准，这份只放能直接背、直接答的结论。

---

## 一句话总纲 ⭐

> 联合索引 = **先按第 1 列排、相等再按第 2 列排**；能不能命中由**最左前缀**决定（缺最左列 / 范围列之后 → 断）；查询要的列索引里全有就**覆盖索引**（`Using index`）**免回表**；对索引列做**函数/运算/隐式转换/`%`开头/选择性差**会**失效**。

---

## 联合索引排序模型 ⭐⭐

`idx(a, b, c)`：**先按 a 排，a 相等按 b 排，b 相等按 c 排**。
→ a 全局有序；b 只在"a 固定"时有序；c 只在"a、b 都固定"时有序。
→ 所以**左边不固定，右边就是乱的**，用不上定位。

---

## 最左前缀速查表（`idx(a,b,c)`）⭐⭐

| WHERE | 用到 | 备注 |
|---|---|---|
| `a=1` | a | ✅ |
| `a=1 AND b=2` | a,b | ✅ |
| `a=1 AND b=2 AND c=3` | a,b,c | ✅ 全中 |
| `b=2` / `b=2 AND c=3` | 无 | ❌ 缺最左列 a |
| `a=1 AND c=3` | a | ⚠️ 缺 b，c 用不上定位（ICP 可下推过滤） |
| `a=1 AND b>2 AND c=3` | a,b | ⚠️ **范围列 b 之后 c 停用** |

两条铁律：
- **缺最左列 → 整个索引用不上。**
- **范围列（`>` `<` `between` `like 'x%'`）会截断它右边的列。**

> `WHERE` 里列的**书写顺序不影响**，索引里列的顺序才关键（优化器会调条件顺序）。

---

## 列顺序设计口诀 ⭐

> **等值列在前 → 范围列在后 → 排序列进前缀 → 高选择性靠左。**

`ORDER BY` 也吃最左前缀：排序列是索引前缀 → 免 `Using filesort`。

---

## 覆盖索引 ⭐⭐

- 二级索引叶子 = **索引所有列 + 主键值**。
- 查询要的列（SELECT + WHERE + ORDER BY）**全在索引里** → 只读索引、**不回表** → `EXPLAIN` 出 **`Using index`**。
- 例（`idx(category_id,status)`，叶子含 category_id,status,id）：
  - `SELECT id FROM spu WHERE category_id=? AND status=?` → ✅ 覆盖（id 是主键）
  - `SELECT id,name ...` → ❌ name 不在索引 → 回表
- 代价 ⚠️：索引变宽 → 每页条目少、树更大、写入更重、占内存 → **只给高频小查询做**，别把大字段/所有列塞进去。

---

## 索引下推 ICP ⭐

- `Using index condition`：把"不能用于定位、但在索引里有值"的条件**下推到引擎层**先过滤，**减少回表次数**。
- ⚠️ 和覆盖区分：
  - `Using index` = **覆盖，完全不回表**；
  - `Using index condition` = **ICP，仍回表，只是回得更少**。
- 默认开启（5.6+）。

---

## 索引失效场景速查 ⚠️⭐⭐

根因一句话：**任何让索引列"原始值"失去有序性/可比性的操作都失效。**

| 场景 | 例 | 修 |
|---|---|---|
| 列上函数 | `DATE(created_at)='...'` | 改范围 `>= 当天 AND < 次日` |
| 列上运算 | `price+100>8000` | `price>7900` |
| 隐式转换 | `sku_code=123456`（列是 VARCHAR） | `sku_code='123456'` |
| `%` 开头 | `name LIKE '%手机'` | `LIKE '手机%'`；包含搜索用 ES |
| `OR` 一边无索引 | `category_id=3 OR status=1` | 拆 `UNION` / 给两边都建 |
| 负向条件 | `!=` `NOT IN` `IS NOT NULL` | 命中太多，优化器多半全表扫 |
| 缺最左列 / 范围后列 | 见上表 | 调整索引列顺序 |
| 选择性差 | `status`(0/1) 单列索引 | 别单建，放联合索引非最左位 |

---

## 选择性 ⭐

- **选择性 = 不重复值数 / 总行数**，越接近 1 越值得建索引。
- 低基数列（状态 / 性别 / 软删标记）选择性差 → 单建索引优化器**多半不走**（走了要回表一大半，不如全表扫）。
- "有索引不走"很多时候是优化器**按成本**做的正确选择，不是 bug。

---

## 商品域索引设计（本章交付结论）⭐

| 表 | 索引 | 为哪条查询 |
|---|---|---|
| `category` | `idx_parent_sort (parent_id, sort)` | `WHERE parent_id=? ORDER BY sort` 定位+免排序 |
| `spu` | `idx_cat_status_created (category_id, status, created_at)` | `WHERE category_id=? AND status=1 ORDER BY created_at DESC` |
| `sku` | `idx_spu_id (spu_id)` | `WHERE spu_id=?` 查某 SPU 的 SKU（要整行，注定回表，不覆盖） |

- 已有唯一键 `sku.uk_sku_code` / `product.uk_sku` 本身是索引，`WHERE sku_code=?` 已能走，不重复建。
- 设计通用清单：**先有查询再建索引 → 联合索引复用最左前缀 → 高频小查询才覆盖 → 低选择性列不单建 → 索引不是越多越好（写入/空间成本）。**

## 自问自答（合上讲义答）

1. 联合索引怎么排？→ 先按第 1 列、相等再按第 2 列……左边不定右边乱。
2. `WHERE b=?`（缺 a）能走 `idx(a,b)` 吗？→ 不能，最左前缀断。
3. 范围列后面的列能定位吗？→ 不能，范围截断右边列。
4. 覆盖索引是什么标志？→ `Using index`，查询列全在索引里、不回表。
5. `Using index` vs `Using index condition`？→ 前者覆盖不回表；后者 ICP 减少回表。
6. `DATE(created_at)=?` 为什么失效？→ 列被函数包住，索引存原始值、对不上；改范围。
7. 为什么不给 status 单建索引？→ 选择性差，命中太多，优化器不走。
