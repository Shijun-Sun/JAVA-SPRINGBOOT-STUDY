## 一、我们在解决什么问题：从"有主键/唯一键"到"查询怎么走得快"

02 章我们钻进 InnoDB，搞清了两件事：

- 表数据本身是一棵**聚簇索引** B+ 树，叶子存整行；
- 你另建的**二级索引**是另一棵 B+ 树，叶子存"索引列 + 主键"，查整行要**回表**。

但 01 章的商品域表，二级索引只建了**唯一键**（`sku.uk_sku_code`、`product.uk_sku`），普通查询索引**明确留到了本章**。因为真实查询长这样：

```sql
-- 商品详情页：查某 SPU 下的所有 SKU
SELECT * FROM sku WHERE spu_id = 100;
-- 分类页：查某分类的直接子分类
SELECT * FROM category WHERE parent_id = 5 ORDER BY sort;
-- 后台列表：某分类下、上架的商品，按创建时间倒序
SELECT id, name FROM spu WHERE category_id = 3 AND status = 1 ORDER BY created_at DESC;
```

这些列（`spu_id`、`parent_id`、`category_id`、`status`）**都没索引**——按 02 章的模型，它们只能**全表扫描**（`type=ALL`），逐页逐行比对。数据量一大就是慢 SQL。

本章要解决的就是：**给这些查询设计合适的索引，让它们从"扫全表"变成"走树几次 IO"。** 而设计索引不是"哪列查得多就给哪列加一个"这么简单——多列一起查时要用**联合索引**，联合索引能不能命中由**最左前缀原则**决定，能不能不回表由**覆盖索引**决定。这三块是本章的主线。

> 一句话定位：**02 章讲"索引这棵树长什么样"，03 章讲"这棵树该怎么建、一条 SQL 怎么才能走上它"。** 这是从"懂原理"到"会设计"的一步。

## 二、单列索引的局限：为什么需要联合索引

先看一个最朴素的想法：查询用到哪列，就给哪列单独建一个索引。

```sql
-- 需求：WHERE category_id = 3 AND status = 1
CREATE INDEX idx_category_id ON spu (category_id);
CREATE INDEX idx_status      ON spu (status);
```

这样建了两个**单列二级索引**。执行 `WHERE category_id = 3 AND status = 1` 时会发生什么？

- MySQL 通常**只会挑一个**它认为最省的索引去走（比如 `idx_category_id`），用它过滤出 `category_id = 3` 的一批主键，**回表**取整行后，再在内存里逐行判断 `status = 1`。
- 另一个索引 `idx_status` 大概率用不上（`status` 只有 0/1 两个值，几乎没有过滤能力，走它还不如扫描——这叫**选择性差**，第七节讲）。

问题：如果 `category_id = 3` 命中了 10 万行，就要回表 10 万次、再逐行过滤 `status`，代价很高。

> MySQL 有个叫 **index merge（索引合并）** 的优化，某些情况下能同时用两个单列索引再取交集。但它有额外成本、也不总是被选中，**不能替代一个设计良好的联合索引**。生产里的经验是：明确的多列条件，优先设计联合索引，而不是堆一堆单列索引指望 index merge。

正确做法是建一个**联合索引（复合索引）**，把这两列放进同一棵树：

```sql
CREATE INDEX idx_category_status ON spu (category_id, status);
```

要理解它为什么更好，得先看联合索引在 B+ 树里怎么排。

## 三、联合索引在 B+ 树里怎么排序 ⭐

联合索引 `(category_id, status)` 不是"两个索引"，而是**一棵 B+ 树**，它的 key 是"两列拼起来的组合值"，**排序规则是：先按第一列排，第一列相等再按第二列排**——和 Excel 里"先按 A 列排序，A 相同再按 B 列排序"一模一样。

假设 `spu` 表有这些数据，联合索引 `(category_id, status)` 的叶子节点大致这样排（叶子还带主键 `id`）：

```
(category_id, status) → id
─────────────────────────────
(3, 0) → 12
(3, 1) → 5          ← category_id 相同(=3)，再按 status 从小到大
(3, 1) → 8
(5, 0) → 20
(5, 1) → 3          ← category_id=5 这一段，内部又按 status 排
(5, 1) → 7
(7, 1) → 15
```

看这张排序表，能得出几个关键结论：

1. **第一列 `category_id` 是全局有序的**：整棵树从上到下，`category_id` 从小到大。所以 `WHERE category_id = 5` 能快速在树里定位到 `category_id=5` 那一段——**第一列可以直接用来查找**。

2. **第二列 `status` 只在"第一列相等"的小范围内有序**：`status` 在全局是乱的（`0,1,0,1,1,1`），只有在 `category_id` 固定为某个值时，它才有序。所以：
   - `WHERE category_id = 5 AND status = 1`：先定位 `category_id=5`，在这一小段里 `status` 有序，能继续用 `status` 缩小范围——**两列都用上了** ✅。
   - `WHERE status = 1`（不给 `category_id`）：`status` 在全局乱序，**没法用这棵树定位**——这棵索引帮不上忙 ❌。

这就是**最左前缀原则**的物理根源：**联合索引的排序是"从左到右依次"的，你必须先固定左边的列，右边的列才有序、才能用来查找。**

> 一句话记死：**联合索引 = 先按第 1 列排，第 1 列相等再按第 2 列排，以此类推。左边不固定，右边就是乱的。**

## 四、最左前缀原则：一条 WHERE 能走到第几列 ⭐⭐

有了上面的排序模型，就能判断任意一条 SQL 能不能走联合索引、走到哪一列。

**规则**：对联合索引 `(a, b, c)`，从最左列 `a` 开始，`WHERE` 里**连续、等值**地命中了几列，索引就能用到第几列；一旦断掉（缺列，或遇到范围），后面的列就用不上索引来定位了。

以 `idx (a, b, c)` 为例，逐条判断：

| WHERE 条件 | 用到索引的哪几列 | 说明 |
|---|---|---|
| `a = 1` | a | 命中最左列 ✅ |
| `a = 1 AND b = 2` | a, b | 连续命中 ✅ |
| `a = 1 AND b = 2 AND c = 3` | a, b, c | 全部命中 ✅ |
| `b = 2` | 用不上 | 缺最左列 a，`b` 全局乱序 ❌ |
| `b = 2 AND c = 3` | 用不上 | 同样缺 a ❌ |
| `a = 1 AND c = 3` | 只用到 a | 缺 b，`c` 在"a 固定"下仍是乱的，c 用不上定位 ⚠️ |
| `a = 1 AND b > 2 AND c = 3` | a, b（c 用不上定位） | **范围列 `b` 之后的 `c` 停用** ⭐ |

两个最容易考、最容易错的点：

### 4.1 中间缺列：后面的列断掉

`a = 1 AND c = 3`：只能用 `a` 定位。因为跳过了 `b`，而 `c` 只有在"`a` 和 `b` 都固定"时才有序，现在 `b` 没固定，`c` 在这段里是乱的，用不上索引来定位（但 8.0 的**索引下推**能在扫描时顺带过滤 `c`，减少回表，见第六节——注意"下推过滤"和"用索引定位"是两回事）。

### 4.2 范围列之后停止：`>` `<` `BETWEEN` `LIKE 'x%'` ⭐

`a = 1 AND b > 2 AND c = 3`：`a`、`b` 用得上，但 **`c` 用不上索引定位**。为什么？

回到排序模型：`c` 只有在"`a` 和 `b` 都相等"的小段里才有序。可这里 `b > 2` 是个**范围**，它匹配的是 `b=3, b=4, b=5...` 好多个不同的 `b` 值，**每个 `b` 值对应的那段里 `c` 各自有序，但跨 `b` 值之间 `c` 是乱的**。所以过了范围列 `b`，`c` 就没法再用索引定位了。

> 这条叫 **"范围列之后失效"**，是联合索引设计的黄金法则：**把等值查询的列放左边，范围查询的列放右边。** 因为范围列会"截断"它右边的列。

### 4.3 `WHERE` 里的顺序不重要，索引里列的顺序才重要

初学者常问：`WHERE b = 2 AND a = 1` 和 `WHERE a = 1 AND b = 2`，前者把 `a` 写在后面，会不会走不了 `idx(a,b)`？

**不会有区别。** MySQL 的优化器会自动帮你调整条件顺序去匹配索引。**决定能不能用索引的，是"索引里列的排列顺序"，不是"你 WHERE 里写的顺序"。** 你要操心的是 `CREATE INDEX (a, b, c)` 里 `a b c` 的先后，而不是 SQL 里的书写先后。

### 4.4 排序也吃最左前缀：`ORDER BY` 能不能用索引 ⭐

联合索引的有序性不只服务 `WHERE`，也服务 `ORDER BY` / `GROUP BY`。因为索引叶子本身就是排好序的，如果 `ORDER BY` 的列正好是索引的前缀，就能**省掉排序**（避免 `Using filesort`）。

对 `idx (category_id, status, created_at)`：

```sql
-- ✅ 用索引排序：category_id 等值定位后，created_at 在该段内有序……
--    但注意中间隔了个 status，见下面说明
SELECT * FROM spu WHERE category_id = 3 ORDER BY status, created_at;   -- ✅ 前缀连续
SELECT * FROM spu WHERE category_id = 3 AND status = 1 ORDER BY created_at;  -- ✅
-- ⚠️ 需要 filesort：跳过了 status 直接按 created_at 排
SELECT * FROM spu WHERE category_id = 3 ORDER BY created_at;   -- created_at 跨不同 status 是乱的
```

规则和 `WHERE` 一致：**`ORDER BY` 要用上索引，也得满足最左前缀的连续性**（前面等值命中的列 + 排序列拼起来是索引前缀）。这也是设计索引时要把"排序列"考虑进列顺序的原因。

## 五、覆盖索引：彻底消除回表 ⭐⭐

02 章讲过：走二级索引一般要**回表**（拿主键回聚簇索引取整行）。**覆盖索引（Covering Index）** 就是消除回表的手段。

**定义**：如果一条查询**要用到的所有列**（`SELECT` 的列 + `WHERE`/`ORDER BY` 用到的列），在某个二级索引的叶子里**全都有**，那 MySQL 只读这个索引就够了，**不用回表**——这个索引"覆盖"了这条查询。`EXPLAIN` 的 `Extra` 会显示 **`Using index`**。

回忆二级索引叶子存什么：**索引的所有列 + 主键值**。所以：

```sql
-- 索引：idx_category_status (category_id, status)，叶子含 category_id, status, id(主键)
-- ✅ 覆盖：要的 id 是主键（叶子里有）、category_id/status 是索引列 → 不回表
SELECT id FROM spu WHERE category_id = 3 AND status = 1;
-- ✅ 覆盖：category_id、status 都在索引里
SELECT category_id, status FROM spu WHERE category_id = 3;
-- ❌ 不覆盖：要 name，但 name 不在这个索引里 → 回表取整行
SELECT id, name FROM spu WHERE category_id = 3 AND status = 1;
```

如果 `SELECT id, name FROM spu WHERE category_id = 3 AND status = 1` 是高频查询，可以把 `name` **也放进索引**做成覆盖索引：

```sql
CREATE INDEX idx_cat_status_name ON spu (category_id, status, name);
-- 现在叶子里有 category_id, status, name, id，上面那条查询不用回表了 ✅
```

这就是覆盖索引的威力：**用"索引里多带一列"的空间，换"免掉回表"的时间。**

### 5.1 覆盖索引的代价与边界 ⚠️

覆盖索引不是免费的，也不是"把所有列都塞进索引"：

- 索引越宽（列越多、越长），**每个索引页能放的条目越少**，索引这棵树越大，占磁盘、占内存缓冲池，**写入时维护成本也高**（每次增删改都要更新索引）。
- 把大字段（长 `VARCHAR`、`TEXT`）放进索引尤其糟——直接把索引撑爆。
- 所以覆盖索引针对的是**高频、且返回列不多**的查询，有的放矢，不是无脑加列。

> 一句话：**覆盖索引 = 查询要的列索引里全有 → 不回表（`Using index`）；代价是索引变宽、写入变重，只给高频小查询做。**

## 六、索引下推（ICP）：减少回表的次数 ⭐

**索引条件下推（Index Condition Pushdown, ICP）** 是 MySQL 5.6+ 的优化，默认开启。它专治"最左前缀断了、但条件里还有索引列"的情况。

还是 `idx (a, b, c)`，查询 `WHERE a = 1 AND b LIKE '张%' AND c = 5`：

- `a = 1` 能定位；`b LIKE '张%'` 是范围（前缀匹配），能用；`c` 因为在范围列后，**不能用来定位**。
- **没有 ICP 时**：引擎层用 `a=1 AND b LIKE '张%'` 找出一批记录 → **每条都回表**取整行 → 在 Server 层再判断 `c = 5`。回表次数多。
- **有 ICP 时**：`c = 5` 这个条件**被"下推"到引擎层**，在**二级索引里就先过滤掉 `c ≠ 5` 的**（因为 `c` 的值就在索引叶子里，不用回表也能看到），**只对 `c = 5` 的记录才回表**。回表次数大幅减少。

`EXPLAIN` 的 `Extra` 出现 **`Using index condition`** 就是用了 ICP。

> 区分清楚：**`Using index`（覆盖，完全不回表）≠ `Using index condition`（下推，减少回表但仍要回表）。** ICP 不能消除回表，只是让回表更少。

## 七、索引失效：为什么明明有索引却不走 ⚠️⭐⭐

"建了索引却走全表扫描"是面试和线上排查的高频问题。**根因几乎都是同一个：索引 B+ 树是按"列的原始值"排序的，任何让"列的原始值失去有序性/可比性"的操作，都会让索引没法用来定位。** 逐个看：

### 7.1 对索引列做函数 / 运算 ❌

```sql
-- ❌ 失效：对 created_at 用了函数，索引存的是 created_at 原始值，不是 DATE(created_at) 的值
SELECT * FROM spu WHERE DATE(created_at) = '2026-09-10';
-- ✅ 改写成范围，让 created_at 保持"裸列"
SELECT * FROM spu WHERE created_at >= '2026-09-10 00:00:00'
                    AND created_at <  '2026-09-11 00:00:00';
```

```sql
-- ❌ 失效：对索引列做运算
SELECT * FROM sku WHERE price + 100 > 8000;
-- ✅ 把运算挪到常量侧
SELECT * FROM sku WHERE price > 7900;
```

根因：索引树里排的是 `created_at`、`price` 的**原始值**，不是 `DATE(created_at)`、`price+100` 的值。一旦列被函数/运算包起来，树的有序性对不上了，只能全表逐行算。

### 7.2 隐式类型转换 ❌

```sql
-- sku_code 是 VARCHAR，却用数字去比 → MySQL 把每行的 sku_code 转成数字再比 = 对列做了函数 → 失效
SELECT * FROM sku WHERE sku_code = 123456;
-- ✅ 类型对齐，用字符串
SELECT * FROM sku WHERE sku_code = '123456';
```

> 反过来"数字列用字符串查"（`WHERE id = '100'`）通常**不失效**，因为 MySQL 是把字符串转成数字、不是对列转换。但**别依赖这种细节，始终让查询值和列类型一致**最稳妥。

### 7.3 `LIKE` 以通配符开头 ❌

```sql
SELECT * FROM spu WHERE name LIKE '%手机';     -- ❌ 前面是 %，等于"后缀匹配"，索引的前缀有序性用不上
SELECT * FROM spu WHERE name LIKE '手机%';     -- ✅ 前缀确定，能用索引定位（相当于范围）
```

根因：索引按字符串**从左到右**排序，`'手机%'` 能定位到"以手机开头"那一段；`'%手机'` 要求匹配任意开头，树帮不上忙。真要做"包含"搜索，用全文索引或搜索引擎（ES，M09 会讲）。

### 7.4 `OR` 连接的条件有一边没索引 ❌

```sql
-- status 没索引 → 整条退化成全表扫描
SELECT * FROM spu WHERE category_id = 3 OR status = 1;
```

`OR` 要求两边都能走索引才可能用索引（且往往走 index merge）；只要有一边没索引，就得全表扫。能用 `UNION`/`IN` 改写时优先改写。

### 7.5 `!=` / `NOT IN` / `IS NOT NULL` 等负向条件

这类"排除型"条件通常匹配大部分行，优化器算下来**走索引回表还不如直接全表扫**，于是放弃索引。这不算 bug，是优化器基于**选择性**做的成本选择（见 7.7）。

### 7.6 最左前缀没满足（第四节已讲）

缺最左列、或范围列右边的列，都用不上索引定位。

### 7.7 选择性太差，优化器主动放弃 ⭐

**选择性 = 不重复值的个数 / 总行数**，越接近 1 越好（区分度高）。

- `status` 只有 0/1 → 选择性极低（约 2/总行数）。就算建了索引，`WHERE status = 1` 可能命中一半的行，走索引要回表一半的行，**还不如全表扫一遍**。优化器会算这笔账，主动不走。
- 所以**别给性别、状态、是否删除这种低基数列单独建索引**——它们更适合放在联合索引的**非最左位置**辅助过滤，或靠 ICP。

> 记这条判断：**索引走不走，最终由优化器按成本（要扫多少行、回多少次表）决定；选择性差的列，优化器可能"有索引也不走"，这是对的。**

一句话收束失效：**让索引列保持"裸列 + 类型一致 + 前缀确定"，满足最左前缀，且列有足够选择性——否则索引就是摆设。**

## 八、给商品域设计索引：把前七节用起来 ⭐

现在回到 01 章的 `category` / `spu` / `sku`，按真实查询设计普通二级索引。**方法论**：先列出高频查询，再为每类查询设计能命中的（联合）索引，并考虑排序和覆盖。

### 8.1 `category`（分类树）

高频查询：查某分类的直接子分类，按 `sort` 排序。

```sql
SELECT id, name FROM category WHERE parent_id = 5 ORDER BY sort;
```

设计：`parent_id` 等值 + `sort` 排序 → 联合索引把排序列带上，既能定位又能免 filesort：

```sql
CREATE INDEX idx_parent_sort ON category (parent_id, sort);
```

### 8.2 `spu`（商品）

高频查询：
```sql
-- Q1：某分类下、上架的商品，按创建时间倒序（后台/前台列表）
SELECT id, name FROM spu WHERE category_id = ? AND status = 1 ORDER BY created_at DESC;
```

设计：等值列 `category_id`、`status` 在前，排序列 `created_at` 在后：

```sql
CREATE INDEX idx_cat_status_created ON spu (category_id, status, created_at);
```

- `category_id`、`status` 等值定位；`created_at` 在该段内有序，`ORDER BY created_at DESC` 顺着索引反向扫，免 filesort。
- 若 `SELECT` 长期只要 `id, name`，可再评估是否把 `name` 也纳入做覆盖（权衡索引宽度，见 5.1）。本章交付**先不盲目加宽**，把这一步的取舍写进设计说明。

### 8.3 `sku`（库存单位）

高频查询：查某 SPU 下的所有 SKU（商品详情页必然用到）。

```sql
SELECT * FROM sku WHERE spu_id = ?;
```

设计：`spu_id` 单列（或联合）索引。由于详情页往往要整行（价格、库存、规格），这里注定要回表取整行，覆盖意义不大，单列索引即可：

```sql
CREATE INDEX idx_spu_id ON sku (spu_id);
```

> 已有的唯一键 `uk_sku_code`、`product.uk_sku` 本身就是索引，`WHERE sku_code = ?` 已经能走，无需重复建。

### 8.4 设计索引的通用清单（背下来当模板）

1. **先有查询，再有索引**：不看查询凭空建索引都是浪费。列出 Top 几条高频/慢查询。
2. **联合索引列顺序**：`等值列在前 → 范围列在后 → 排序列参与前缀`；把**选择性高**的等值列尽量靠左。
3. **能覆盖就覆盖**（高频小查询）：让 `SELECT` 的列落在索引里，免回表。
4. **别给低选择性列单独建索引**（性别、状态、软删标记）。
5. **索引不是越多越好**：每个索引都增加写入成本和空间；能用一个联合索引覆盖多条查询就别拆成多个。
6. **最左前缀复用**：`idx(a,b,c)` 天然能服务 `WHERE a`、`WHERE a,b`、`WHERE a,b,c`，不用再为 `a`、`(a,b)` 单独建。

## 九、常见坑与误区 ⚠️

| 坑 / 误区 | 真相 |
|---|---|
| 每个查询列都单独建一个索引 | 多列条件应建**联合索引**；一堆单列索引常只用到一个 |
| 以为 `WHERE` 里列的书写顺序决定能否走索引 | 决定因素是**索引里列的顺序**，优化器会自动调条件顺序 |
| 联合索引 `(a,b,c)` 用 `WHERE b=?` 也能走 | ❌ 缺最左列 `a`，走不了（最左前缀） |
| 范围列后面的列还能用索引定位 | ❌ 范围列（`>`/`between`/`like 'x%'`）会**截断**右边的列 |
| "走了索引"就一定不回表 | 一般仍回表；不回表要**覆盖索引**（`Using index`） |
| 把所有列塞进索引做覆盖 | 索引变宽、写入变重、占内存；只给**高频小查询**覆盖 |
| 对索引列用函数 / 运算 / 隐式转换 | 索引**失效**，退化全表扫；保持"裸列 + 类型一致" |
| `LIKE '%x'` 也能走索引 | ❌ 通配符开头用不上前缀有序；`'x%'` 才行 |
| 给 status/性别等低基数列建索引 | **选择性差**，优化器多半不走；放联合索引非最左位辅助 |
| `Using index` 和 `Using index condition` 一样 | 前者是**覆盖不回表**，后者是**ICP 减少回表**，不同 |

## 十、小结

| 知识点 | 记住这一句 |
|---|---|
| 联合索引排序 | 先按第 1 列排，第 1 列相等再按第 2 列，左边不定右边乱 |
| 最左前缀 | 从最左列起连续命中到哪列，就用到哪列；缺列/范围列后断掉 |
| 列顺序设计 | **等值列在前、范围列在后、排序列进前缀、高选择性靠左** |
| WHERE 书写顺序 | 不影响；索引里的列顺序才关键 |
| 覆盖索引 | 查询要的列索引里全有 → 不回表（`Using index`），代价是索引变宽 |
| 索引下推 ICP | `Using index condition`：在索引层先过滤，**减少回表**但不消除 |
| 索引失效 | 函数/运算/隐式转换/`%`开头/`OR`一边无索引/选择性差 |
| 选择性 | 低基数列（状态/性别）单建索引多半不走，优化器按成本选择 |
| 索引不是越多越好 | 每个索引增加写入与空间成本；用联合索引复用最左前缀 |
