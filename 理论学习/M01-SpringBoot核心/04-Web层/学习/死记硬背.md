## HTTP 方法与状态码速查

### 方法语义

| HTTP 方法 | 语义 | 是否幂等 | 典型 URL |
|---|---|---|---|
| GET | 查询，不改变资源状态 | ✅ | `/products`, `/products/{id}` |
| POST | 创建新资源 | ❌ | `/products` |
| PUT | 整体替换（需要完整数据） | ✅ | `/products/{id}` |
| PATCH | 局部更新（只传变化字段） | ✅ | `/products/{id}` |
| DELETE | 删除 | ✅ | `/products/{id}` |

幂等：多次执行结果相同。`POST /products` 执行两次会创建两条记录，所以不幂等。

### 状态码速查

| 状态码 | 名称 | 什么时候用 |
|---|---|---|
| 200 | OK | 查询成功、更新成功且返回数据 |
| 201 | Created | POST 创建成功 ⭐ |
| 204 | No Content | DELETE 成功，无响应体 ⭐ |
| 400 | Bad Request | 参数非法、格式错误、校验失败 |
| 404 | Not Found | 资源不存在 |
| 409 | Conflict | 业务冲突（SKU 重复等） |
| 422 | Unprocessable Content | 格式合法但语义非法（价格为负） |
| 500 | Internal Server Error | 服务端未预期错误 |

⚠️ **常见错误**：不管什么情况都返回 200，把错误信息放进 `{code: 500}`。这不是 REST，是 RPC 披着 HTTP 的皮。

## 注解速查

### 参数绑定三件套 ⭐

```
请求路径段  →  @PathVariable     →  唯一标识符（ID、slug）
查询参数    →  @RequestParam     →  过滤、分页、排序
请求体      →  @RequestBody      →  业务数据（创建/更新的 DTO）
```

```java
// 完整示例
@GetMapping("/products/{id}")
public Result<ProductVO> findById(
        @PathVariable Long id) { ... }          // /products/1

@GetMapping("/products")
public Result<List<ProductVO>> list(
        @RequestParam(defaultValue = "0") int page,
        @RequestParam(defaultValue = "20") int size,
        @RequestParam(required = false) String keyword) { ... }  // ?page=0&size=20

@PostMapping("/products")
public Result<ProductVO> create(
        @Validated @RequestBody CreateProductRequest req) { ... }
```

### 类级别注解

| 注解 | 等价于 | 说明 |
|---|---|---|
| `@RestController` | `@Controller` + `@ResponseBody` | 返回值序列化为 JSON |
| `@RequestMapping("/api/v1/products")` | — | 类级别公共路径前缀 |

### 方法级别注解

| 注解 | HTTP 方法 |
|---|---|
| `@GetMapping` | GET |
| `@PostMapping` | POST |
| `@PutMapping` | PUT |
| `@PatchMapping` | PATCH |
| `@DeleteMapping` | DELETE |

### 响应控制

```java
@ResponseStatus(HttpStatus.CREATED)   // 固定状态码，简洁
ResponseEntity.created(location)      // 需要设置 Location 响应头时用
ResponseEntity.ok(body)               // 精确控制时用
```

## DTO 分层规则 ⭐⚠️

```
客户端 → CreateProductRequest（请求 DTO）→ Service → ProductEntity（数据库）
                                                   ↓
客户端 ← ProductVO（响应 VO）            ← Service
```

| 类型 | 出现位置 | 命名示例 |
|---|---|---|
| `Entity` | Repository 层，不出现在 API 边界 | `ProductEntity` |
| `Request` / `DTO` | Controller 接收入参 | `CreateProductRequest` |
| `VO` | Controller 返回响应 | `ProductVO` |
| `Query` | 封装复杂查询条件 | `ProductQuery` |

**Entity 不能直接当接口返回值** — 记住这 3 个理由：
1. 过度暴露（创建时间、逻辑删除标志客户端不该看到）
2. 接口和数据库字段强绑定，改数据库就破坏 API
3. 安全漏洞（mass assignment，客户端可能传入不该修改的字段）

## Bean Validation 常用约束 ⭐

| 注解 | 适用类型 | 含义 |
|---|---|---|
| `@NotNull` | 任意 | 不能是 null |
| `@NotBlank` | String | 不能是 null、空串、纯空白 ⭐ |
| `@NotEmpty` | String/集合 | 不能是 null 或空 |
| `@Size(min,max)` | String/集合 | 长度范围 |
| `@Min(n)` / `@Max(n)` | 整数 | 数值范围 |
| `@DecimalMin` / `@DecimalMax` | BigDecimal | 小数范围 |
| `@Positive` | 数值 | 必须 > 0 |
| `@Pattern(regexp)` | String | 正则 |
| `@Email` | String | 邮箱格式 |
| `@Valid` | 对象 | 触发嵌套对象的级联校验 ⭐ |

### `@Validated` 和 `@Valid` 的区别 ⭐

| | `@Validated`（Spring） | `@Valid`（Jakarta） |
|---|---|---|
| 支持分组 | ✅ | ❌ |
| 用在 Controller 方法参数 | ✅ | ✅ |
| 触发嵌套对象级联 | ❌ | ✅ |

**结论**：Controller 方法参数加 `@Validated`，嵌套对象字段上加 `@Valid`，两者各司其职。

### 校验失败抛什么异常

```
@RequestBody + @Validated 失败  →  MethodArgumentNotValidException
@RequestParam + @Validated 失败 →  ConstraintViolationException
@PathVariable 类型转换失败       →  MethodArgumentTypeMismatchException
```

⚠️ 三种异常不同，第 05 章全局处理器要分别捕获。

## 统一响应 `Result<T>`

```java
// 推荐字段
String code;    // 语义字符串，如 "SUCCESS"、"PRODUCT_NOT_FOUND"
String message; // 人读的描述
T data;         // 业务数据，可为 null
```

⚠️ **不要用 HTTP 状态码整数作为 `code` 字段**（`200`、`500`），原因：
- HTTP 层已有状态码，`Result.code` 是业务层的概念，两层混用让人困惑
- 前端要处理具体业务错误时，`"PRODUCT_NOT_FOUND"` 比 `404` 可读性强，也不依赖 HTTP 层

```java
// 常见调用方式
Result.ok(data)                     // 有数据的成功
Result.ok()                         // 无数据的成功（配合 @ResponseStatus(NO_CONTENT) 时直接返回 void）
Result.fail("PRODUCT_NOT_FOUND", "商品不存在")  // 业务失败
```

## 内存 CRUD 分层骨架

```
ProductController          ← HTTP 边界，参数绑定 + 状态码
      ↓ CreateProductRequest（DTO，带校验注解）
ProductService             ← 业务逻辑（SKU 重复检查等）
      ↓ ProductEntity（数据库形态）
InMemoryProductRepository  ← 存储访问（ConcurrentHashMap）
      ↑ ProductVO（响应形态）
```

分层的好处：M02 换 MySQL 时只改 Repository，Controller 和 Service 不动。

## 高频坑 ⚠️

1. **`record` 序列化为 `{}`**：检查 Jackson 版本和 `ParameterNamesModule` 是否自动配置。
2. **POST 返回 200 而不是 201**：忘记加 `@ResponseStatus(HttpStatus.CREATED)`。
3. **`@RequestParam` 未传时 400**：`required` 默认 `true`，可选参数要加 `required = false` 或 `defaultValue`。
4. **嵌套 DTO 校验没触发**：嵌套对象字段上忘加 `@Valid`。
5. **Entity 字段名改了接口挂了**：Entity 混入了 API 边界，该用 VO 隔离。
6. **校验失败返回 500**：没有全局异常处理器（第 05 章解决）。
7. **路径和 URL 含动词**：`/getProducts`、`/createProduct` 都是错的，名词 + 动词分离。

---

## 一句话总结

> URL 是资源（名词），HTTP 方法是操作（动词），状态码说结果，DTO 是边界，校验在入口，统一响应在 Controller 层收口。
