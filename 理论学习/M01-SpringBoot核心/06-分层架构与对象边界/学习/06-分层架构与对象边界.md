## 一、为什么要分层，为什么要隔离对象

### 1.1 一个反例说明问题

假设商品服务有这样一个 Entity：

```java
public record ProductEntity(
    Long id,
    String name,
    String sku,
    BigDecimal price,
    String category,
    String supplierSecret,    // 供应商内部编码，不应对外暴露
    LocalDateTime createdAt,
    LocalDateTime updatedAt,
    boolean deleted           // 逻辑删除标志
) {}
```

如果把 `ProductEntity` 直接用作 Controller 的返回值：

- 客户端会拿到 `supplierSecret`——安全漏洞；
- 客户端会看到 `deleted: false`——接口语义污染；
- 前端代码依赖了 `updatedAt` 字段名，数据库字段改名后接口就破坏了；
- 客户端如果把整个对象 POST 回来，id、createdAt 这些字段会被客户端控制——mass assignment 漏洞。

同样，如果把 Entity 直接用作创建接口的入参：

- 客户端可以传入 `id: 999`，让服务端用指定 ID 插入——数据完整性被破坏；
- 所有字段都要写校验，但 `createdAt`、`deleted` 这些字段本不该由客户端设置。

分层隔离的核心价值不是"写更多的类"，而是**让每一层只能看到它需要看到的内容，每一层的变化不级联影响其他层**。

### 1.2 各层的对象类型

```
HTTP 请求  ──→  Controller ──→  Service ──→  Repository ──→  数据库
               ↑                ↑              ↑
          Request DTO      (内部流转)        Entity
               ↓
          Response VO
               ↓
HTTP 响应
```

| 类型 | 所在包 | 职责 | 谁创建 | 谁使用 |
|---|---|---|---|---|
| `Entity` | `domain/entity` | 映射数据库行，承载持久化状态 | Repository | Service、Repository |
| `Request DTO` | `domain/dto` | 接收客户端入参，携带校验注解 | 客户端（反序列化） | Controller → Service |
| `Response VO` | `domain/vo` | 向客户端输出视图，只含安全字段 | Service（从 Entity 转换） | Controller |
| `Query` | `domain/dto` 或 `domain/query` | 封装查询条件（分页、过滤、排序） | Controller | Service |

## 二、Entity：数据库行的 Java 表示

### 2.1 Entity 的设计原则

Entity 的职责只有一个：忠实映射数据库行。

```java
package com.study.mall.product.domain.entity;

import java.math.BigDecimal;
import java.time.LocalDateTime;

public record ProductEntity(
        Long id,
        String name,
        String sku,
        BigDecimal price,
        String category,
        LocalDateTime createdAt,
        LocalDateTime updatedAt
) {}
```

几个规则：

1. **不加 Bean Validation 注解**——Entity 对应数据库约束，不是 API 边界；
2. **不加 `@JsonIgnore` 或 `@JsonProperty`**——Entity 不参与 JSON 序列化；
3. **不实现业务方法**——计算折扣价、判断是否上架等逻辑属于 Service；
4. **不出现在 Controller 的参数或返回值中**——这是最关键的规则。

### 2.2 record vs class

使用 `record` 的好处：

- 不可变，创建后无法被外部修改——天然防 Entity 被悄悄改掉；
- 自动生成 `equals`、`hashCode`、`toString`——减少样板代码；
- 字段全部 `final`，强制在构造时赋值，不会出现半初始化状态。

换成可变 `class` 的场景：M02 引入 MyBatis-Plus 时，框架可能需要无参构造器和 setter，届时再改。

## 三、DTO：API 边界的入参对象

### 3.1 Request DTO 的职责

Request DTO 承载客户端发来的数据，加 Bean Validation 注解，不包含不应由客户端设置的字段。

```java
package com.study.mall.product.domain.dto;

import jakarta.validation.constraints.DecimalMin;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Pattern;
import jakarta.validation.constraints.Size;
import java.math.BigDecimal;

public record CreateProductRequest(

        @NotBlank(message = "商品名称不能为空")
        @Size(max = 100, message = "商品名称最多 100 个字符")
        String name,

        @NotBlank(message = "SKU 不能为空")
        @Pattern(regexp = "^[A-Z0-9\\-]{1,50}$",
                 message = "SKU 只允许大写字母、数字和连字符")
        String sku,

        @NotNull(message = "价格不能为空")
        @DecimalMin(value = "0.01", message = "价格必须大于 0")
        BigDecimal price,

        @NotBlank(message = "分类不能为空")
        String category

) {}
```

注意 DTO 里没有 `id`、`createdAt`、`updatedAt`——这些字段由服务端生成。

### 3.2 Update DTO 的设计

更新入参只包含**允许修改的字段**。SKU 一旦创建通常不允许修改（业务约定），所以 `UpdateProductRequest` 里没有 `sku`：

```java
public record UpdateProductRequest(
        @NotBlank(message = "商品名称不能为空")
        @Size(max = 100, message = "商品名称最多 100 个字符")
        String name,

        @NotNull(message = "价格不能为空")
        @DecimalMin(value = "0.01", message = "价格必须大于 0")
        BigDecimal price,

        @NotBlank(message = "分类不能为空")
        String category
) {}
```

### 3.3 Partial Update（PATCH）的入参设计

`PUT` 语义是整体替换，`PATCH` 是局部更新。PATCH 的入参需要区分"客户端没传这个字段"和"客户端明确传了 null"：

```java
// 使用 Optional 包装，表示"可能传、可能没传"
public record PatchProductRequest(
        Optional<@Size(max=100) String> name,
        Optional<@DecimalMin("0.01") BigDecimal> price,
        Optional<String> category
) {}
```

这个设计更复杂，本课程暂不要求；了解它的存在，知道 PATCH 和 PUT 的入参设计不同即可。

## 四、VO：API 边界的出参对象

### 4.1 VO 的职责

VO（View Object，也叫 Response DTO）是服务端向客户端输出的视图。只包含对客户端安全、有意义的字段。

```java
package com.study.mall.product.domain.vo;

import java.math.BigDecimal;
import java.time.LocalDateTime;

public record ProductVO(
        Long id,
        String name,
        String sku,
        BigDecimal price,
        String category,
        LocalDateTime createdAt
) {}
```

相比 `ProductEntity`，`ProductVO` 不含 `updatedAt`（内部运维字段）和任何敏感信息。

### 4.2 列表 VO 和详情 VO

当列表接口和详情接口的字段不同时，可以拆成两个 VO：

```java
// 列表页：只需要摘要信息
public record ProductSummaryVO(Long id, String name, BigDecimal price, String category) {}

// 详情页：需要完整信息
public record ProductVO(Long id, String name, String sku, BigDecimal price,
                        String category, LocalDateTime createdAt) {}
```

不要为了减少类而让列表接口返回含大量 null 的详情对象。多一个类，少一堆客户端困惑。

### 4.3 VO 不加校验注解，不实现业务逻辑

VO 是只出不进的对象，它的字段值由服务端保证正确，不需要在 VO 上加 `@NotNull` 等注解。也不要在 VO 里加计算属性方法，那是 Service 的工作。

## 五、Query：封装查询条件

当查询参数超过 3 个时，多个 `@RequestParam` 会让方法签名变长且难以维护。`Query` 对象封装这些条件：

```java
package com.study.mall.product.domain.dto;

public record ProductQuery(
        int page,
        int size,
        String keyword,
        String category
) {
    // 紧凑构造器处理默认值
    public ProductQuery {
        if (page < 0) page = 0;
        if (size <= 0) size = 20;
        if (size > 100) size = 100;
    }
}
```

Controller 里直接绑定（Spring MVC 支持 record 作为查询参数对象，但需要标注或遵循特定约定，详见作业）：

```java
@GetMapping
public Result<Page<ProductVO>> list(ProductQuery query) {
    return Result.ok(productService.list(query));
}
```

## 六、对象转换：在哪里做，怎么做

### 6.1 转换发生在 Service 层

转换规则：

```
Controller 收到 Request DTO
    ↓ 传给 Service（不转换）
Service 把 Request DTO → Entity（创建时）
Service 从 Repository 拿到 Entity → VO（返回给 Controller）
Controller 把 VO 包进 Result<T> 返回给客户端
```

**不要在 Controller 里做 Entity ↔ VO 的转换**——Controller 不应该知道 Entity 的内部结构。  
**不要在 Entity 或 VO 里写 `toVO()` / `fromDTO()` 方法**——对象不应该知道如何转换成另一层的对象。

### 6.2 手写转换方法

最简单、最清晰的做法：在 Service 里写私有方法。

```java
@Service
public class ProductService {

    private final InMemoryProductRepository repository;

    public ProductService(InMemoryProductRepository repository) {
        this.repository = repository;
    }

    public ProductVO create(CreateProductRequest request) {
        if (repository.existsBySku(request.sku())) {
            throw new ResourceConflictException(request.sku());
        }
        LocalDateTime now = LocalDateTime.now();
        ProductEntity entity = toEntity(request, now);
        return toVO(repository.save(entity));
    }

    // ---- 转换方法 ----

    private ProductEntity toEntity(CreateProductRequest req, LocalDateTime now) {
        return new ProductEntity(null, req.name(), req.sku(),
                req.price(), req.category(), now, now);
    }

    private ProductVO toVO(ProductEntity entity) {
        return new ProductVO(entity.id(), entity.name(), entity.sku(),
                entity.price(), entity.category(), entity.createdAt());
    }
}
```

优点：转换逻辑集中、可测试、不引入额外依赖。  
缺点：字段多时有点繁琐。

### 6.3 使用 MapStruct（了解即可，本章不要求）

MapStruct 是编译期代码生成框架，自动生成转换实现：

```java
@Mapper(componentModel = "spring")
public interface ProductMapper {
    ProductVO toVO(ProductEntity entity);
    ProductEntity toEntity(CreateProductRequest request);
}
```

适合字段多、转换频繁的场景。本课程 M01 阶段不引入，字段少时手写转换更直观、无额外学习成本。M02 之后再评估是否引入。

### 6.4 一次转换 vs 延迟转换

**不要让 Entity 流出 Repository 边界后再在 Controller 里转换**：

```java
// ❌ 错误：Controller 知道 Entity 结构
@GetMapping("/{id}")
public Result<ProductVO> findById(@PathVariable Long id) {
    ProductEntity entity = repository.findById(id).orElseThrow(...); // Entity 流出了
    return Result.ok(new ProductVO(entity.id(), ...));  // Controller 做转换
}

// ✅ 正确：Service 完成转换，Controller 只看到 VO
@GetMapping("/{id}")
public Result<ProductVO> findById(@PathVariable Long id) {
    return Result.ok(productService.getById(id));  // Service 返回 VO
}
```

## 七、包结构与命名约定

### 7.1 当前 product-service 包结构

```
com.study.mall.product
├── common/
│   ├── exception/          ← 业务异常体系
│   └── result/             ← 统一响应
├── config/                 ← 配置类（@ConfigurationProperties）
├── controller/             ← HTTP 入口
├── domain/
│   ├── dto/                ← 入参 DTO（Request、Query）
│   ├── entity/             ← 数据库映射对象
│   └── vo/                 ← 出参 VO（Response）
├── repository/             ← 存储访问
└── service/                ← 业务逻辑
```

这个结构在 M01 阶段已经够用。M02 后如果功能增多，可以按业务模块拆分包：

```
com.study.mall.product
├── common/
├── product/           ← 商品模块
│   ├── controller/
│   ├── domain/
│   ├── repository/
│   └── service/
├── category/          ← 分类模块（M02+ 引入）
│   └── ...
└── pricing/           ← 定价模块（M02+ 引入）
    └── ...
```

### 7.2 命名规则

| 类型 | 后缀约定 | 示例 |
|---|---|---|
| 创建入参 | `CreateXxxRequest` | `CreateProductRequest` |
| 更新入参 | `UpdateXxxRequest` | `UpdateProductRequest` |
| 查询条件 | `XxxQuery` | `ProductQuery` |
| 响应视图 | `XxxVO` | `ProductVO` |
| 列表项视图 | `XxxSummaryVO` | `ProductSummaryVO` |
| 数据库映射 | `XxxEntity` | `ProductEntity` |

命名要表达意图，不要用 `ProductInfo`、`ProductData`、`ProductModel` 这类含糊的名字——读代码的人不知道它属于哪一层。

## 八、分层违规的常见场景

### 8.1 Entity 直接用作 Controller 返回值

```java
// ❌
@GetMapping("/{id}")
public Result<ProductEntity> findById(@PathVariable Long id) {
    return Result.ok(repository.findById(id).orElseThrow());
}
```

问题：Entity 字段（`updatedAt`、敏感信息）暴露给客户端；数据库改动直接破坏接口。

### 8.2 Request DTO 流入 Repository

```java
// ❌
@Repository
public class InMemoryProductRepository {
    public ProductEntity save(CreateProductRequest request) { // DTO 进入了 Repository
        ...
    }
}
```

问题：Repository 层依赖了上层的 DTO，分层倒置；后续如果要从其他来源（消息队列、定时任务）创建商品，Repository 无法复用。

### 8.3 在 Entity 上加 JSON 注解

```java
// ❌
public record ProductEntity(
        Long id,
        @JsonIgnore String supplierSecret,   // Entity 参与了序列化
        ...
) {}
```

如果 Entity 需要 `@JsonIgnore`，说明它已经在序列化链路里了，根本原因是 Entity 被直接用作响应对象。正确做法是用 VO 隔离，而不是打补丁。

### 8.4 Service 返回 Entity，Controller 做转换

```java
// ❌
@GetMapping("/{id}")
public Result<ProductVO> findById(@PathVariable Long id) {
    ProductEntity entity = productService.getEntityById(id); // Service 暴露了 Entity
    return Result.ok(new ProductVO(entity.id(), ...));        // Controller 知道 Entity
}
```

Controller 耦合了 Entity 结构。Entity 字段一改，Controller 也要改。

### 8.5 转换逻辑写在 Entity 或 VO 里

```java
// ❌
public record ProductEntity(...) {
    public ProductVO toVO() {          // Entity 知道 VO
        return new ProductVO(this.id(), ...);
    }
}
```

对象不应该知道如何转换成另一层的形态。转换是跨层的职责，属于 Service，不属于任何一方的数据对象。

## 九、分层与测试的关系

清晰的分层让测试更简单：

- **Repository 层**：只测数据访问逻辑，不需要启动 Spring 容器；
- **Service 层**：Mock 掉 Repository，只测业务逻辑——SKU 是否重复检查、Entity 到 VO 的转换等；
- **Controller 层**：用 MockMvc 测 HTTP 行为——路径、状态码、响应格式，不需要真实 Service；
- **集成测试**：全链路验证，相对较少。

如果层与层之间没有清晰的边界，Service 里夹杂 HTTP 知识，Controller 里直接操作 Repository，就无法做到独立测试——这是分层违规的直接代价之一。第 08 章测试时会感受到这一点。

## 十、小结

| 知识点 | 记住这一句 |
|---|---|
| Entity | 数据库行的 Java 表示，不出现在 API 边界 |
| Request DTO | 客户端入参，带校验注解，只含允许设置的字段 |
| Response VO | 服务端出参，只含安全字段，不加校验注解 |
| Query | 封装查询条件，替代多个 @RequestParam |
| 转换位置 | Service 层做 DTO→Entity 和 Entity→VO，Controller 不碰 Entity |
| 违规代价 | 接口改动级联扩散、安全漏洞、无法独立测试 |
| 命名约定 | CreateXxxRequest / XxxVO / XxxQuery / XxxEntity，不用含糊的 XxxInfo |
