> **对应讲义**：[M01-03 · 配置体系](../学习/03-配置体系.md)  
> **预计耗时**：3～5 小时  
> **难度**：中等  
> **正式交付位置**：`homework/delivered/product-service/`  
> **Review 模式**：默认“只指出错误，不直接给答案”

> 在现有 `product-service` 上继续迭代，不要另起工程。  
> 临时外部配置、启动日志和试验脚本可以放在章节实验区，但不要把真实密钥或构建产物提交到正式交付目录。

---

## 一、背景设定

商品服务要部署到开发和生产环境。两个环境共用同一个 JAR，但配置不同：

- 开发环境使用本地对象存储地址、较短缓存时间和 DEBUG 日志；
- 生产环境通过外部注入提供对象存储地址，缓存更久，日志收敛为 INFO；
- 商品分页上限、计价币种、缓存时间和允许上传的图片类型必须类型安全；
- 非法配置必须让应用在启动阶段失败；
- 运维临时覆盖某项配置时，团队必须能判断最终值来自哪里。

本章不要求接入真实对象存储，也不要求真正加密凭据。重点是配置建模、覆盖验证和安全边界。

---

## 二、必做任务

### 任务一：统一为 YAML，并划分环境差异

把当前 `src/main/resources/application.properties` 迁移为以下结构：

```text
src/main/resources/
├── application.yml
├── application-dev.yml
└── application-prod.yml
```

要求：

1. 保留现有 `spring.application.name` 和 Actuator 暴露配置，不能因迁移丢失；
2. `application.yml` 只放公共配置和安全默认值；
3. `application-dev.yml` 只放开发环境差异；
4. `application-prod.yml` 只放生产环境差异；
5. 不在公共配置中写死 `spring.profiles.active`；
6. 删除旧 `application.properties`，避免同一位置混用两种格式；
7. 所有自定义 key 使用小写 kebab-case。

至少配置这些字段，具体前缀自行设计，但必须统一：

| 字段 | Java 目标类型 | dev | prod |
|---|---|---|---|
| 服务展示名 | `String` | 自定 | 自定 |
| 计价币种 | 枚举或 `String` | `CNY` | `CNY` |
| 最大分页条数 | `int` | `100` | `50` |
| 价格缓存时间 | `Duration` | `10s` | `5m` |
| 存储 endpoint | `String` 或 `URI` | 本地地址 | 必须由环境注入 |
| 允许图片类型 | `List<String>` | 至少 3 种 | 至少 2 种 |

**验收标准：**

- 分别激活 dev、prod 时应用能读取到不同配置；
- 公共配置没有大段复制进 Profile 文件；
- 仓库中只保留一种应用配置文件格式；
- prod 的存储 endpoint 没有真实地址或凭据硬编码。

---

### 任务二：建立类型安全配置对象

新建一个专门的 `@ConfigurationProperties` 配置类，承载任务一的自定义配置。

要求：

1. 优先使用 Java `record`，保持配置不可变；
2. 至少包含两层嵌套对象；
3. 至少包含 `Duration` 和 `List<String>`；
4. 通过 `@ConfigurationPropertiesScan` 或 `@EnableConfigurationProperties` 正确注册；
5. 业务类通过构造器注入配置对象；
6. 不允许在业务代码里用多个 `@Value` 拼出同一组配置；
7. 配置类只描述配置，不注入 Repository、Service 或远程客户端。

新增一个只返回**非敏感信息**的接口，例如：

```text
GET /api/config-info
```

响应至少体现：

- 当前激活的 Profile；
- 服务展示名；
- 币种；
- 最大分页条数；
- 缓存时间；
- 允许图片类型。

禁止返回：密码、Token、AccessKey、SecretKey、完整连接串中的凭据。

**验收标准：**

- 应用启动时配置绑定成功；
- 接口响应与当前 Profile 对应；
- 自定义配置 key 不散落在多个业务类中；
- 没有打印完整配置对象来“验证”。

---

### 任务三：配置校验与失败验证 ⭐

给配置类增加 Jakarta Validation 校验。

最低约束：

- 服务展示名非空；
- 币种非空，或限制为你支持的枚举值；
- 最大分页条数范围为 `1～500`；
- 缓存时间不能为空；
- 存储 endpoint 非空；
- 允许图片类型列表不能为空；
- 嵌套对象必须触发级联校验。

必须完成三次反向实验：

1. 把最大分页条数改成 `0`；
2. 把缓存时间改成无法转换的字符串；
3. 在 prod 模式下不提供必需的存储 endpoint。

每次记录：

- 启动是否失败；
- 异常类型或关键错误信息；
- 错误定位到了哪个配置字段；
- 这是“绑定失败”还是“校验失败”。

**验收标准：**

- 三种非法配置都不能让应用带病启动；
- 能区分类型转换失败和约束校验失败；
- 不是在 Controller 里手写 `if` 才发现配置错误。

---

### 任务四：配置优先级实验 ⭐

选择一个无敏感风险的属性，例如“计价币种”或“最大分页条数”，依次使用以下来源设置不同值：

1. `application.yml`；
2. `application-dev.yml`；
3. 操作系统环境变量；
4. Java 系统属性 `-D...`；
5. 命令行参数 `--...`。

至少执行四组启动实验，并调用 `/api/config-info` 获取最终值。

在交付说明中填写：

| 实验 | 同时存在的配置来源 | 最终值 | 获胜来源 | 是否符合预期 |
|---|---|---|---|---|
| 1 | 基础文件 + dev 文件 | | | |
| 2 | dev 文件 + 环境变量 | | | |
| 3 | 环境变量 + `-D` | | | |
| 4 | `-D` + `--` | | | |

要求：

- 自己推导并写出该属性对应的环境变量名；
- 保存每组实验的启动命令和关键响应；
- 实验结束后不要把临时覆盖值写回源码；
- 解释为什么最终值胜出，不能只写“测试通过”。

**验收标准：**

- 实验结果能证明常用来源的覆盖关系；
- 环境变量命名转换正确；
- 命令和证据可由 reviewer 复现。

---

### 任务五：敏感配置边界

为“对象存储访问凭据”设计配置入口，但不接入真实凭据。

要求：

1. 设计 access key / secret key 对应的配置字段或凭据引用；
2. 生产配置只能通过外部来源提供，仓库中不得出现真实值；
3. `/api/config-info` 不得返回这些字段；
4. 日志中不得打印完整配置对象；
5. 在交付说明中回答：
   - 为什么 `ENC(...)` 不能自动代表安全？
   - 解密密钥和密文放在同一仓库有什么问题？
   - 本项目到本机、CI/CD、Kubernetes 三个阶段分别应怎样注入 Secret？
   - 如果凭据误提交 Git，为什么仅删除当前文件不够？

可以使用明显假值说明 key 名，但不得伪造一套“看起来能加密”的自研方案。

**验收标准：**

- Git 跟踪文件中无真实敏感信息；
- 接口和日志无敏感值；
- 文字答案能说清存储密文与管理密钥的区别。

## 三、进阶任务（按需选做）

### 任务六：外部配置文件覆盖

打包应用，在 JAR 外创建一个临时 `config/application-dev.yml`，覆盖一个非敏感属性。

要求：

- 不修改 JAR 内文件；
- 记录目录结构和启动命令；
- 证明外部 Profile 文件覆盖 JAR 内对应值；
- 删除外部文件后，证明配置恢复；
- 说明 `spring.config.location` 和 `spring.config.additional-location` 的区别。

**验收标准：**同一 JAR 在不重新编译的情况下表现出不同配置。

### 任务七：配置元数据与 IDE 提示

为自定义配置增加 Spring Boot configuration metadata 支持。

要求：

- 查阅官方文档，选择正确的配置处理器；
- 如需修改 `pom.xml`，说明该依赖只参与什么阶段；
- 验证 IDE 对自定义 key 至少能提供名称或说明提示；
- 不要手写一大份与代码重复、容易漂移的元数据。

**验收标准：**能说明元数据如何生成，以及它是否影响运行时绑定。

## 四、挑战任务（面试 / 答辩级）

### 任务八：List 与 Map 的覆盖实验

分别设计一个 List 配置和一个 Map 配置，让基础文件与 dev 文件都提供部分值。

回答并用结果证明：

1. 高优先级 List 是追加、按索引合并，还是整体替换？
2. Map 中不同 key 和相同 key 分别如何处理？
3. 为什么“我只是想在 dev 增加一个元素”可能得到意外结果？
4. 你会如何重新设计配置，降低覆盖歧义？

不得只引用文档结论，必须提供实际绑定后的结果。

### 任务九：配置来源诊断方案

不暴露 Secret 的前提下，设计一套“配置未生效”的排错流程。

至少覆盖：

- 本地 IDE；
- `java -jar`；
- 容器环境；
- Actuator 可用和不可用两种情况；
- 如何确认值的来源，而不把敏感值打印出来。

只需提交方案，不要求实现通用诊断框架。
