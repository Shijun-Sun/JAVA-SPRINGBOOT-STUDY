> **本章目标**

## 一、为什么配置不能写死在代码里

### 1.1 写死配置会发生什么

```java
public class ImageStorageClient {
    private final String endpoint = "https://dev-storage.example.com";
    private final int timeoutSeconds = 3;
}
```

一旦开发、测试、生产环境不同，你只能：

1. 修改源码；
2. 重新编译；
3. 为不同环境打不同的 JAR；
4. 祈祷没有把测试地址发到生产。

这破坏了一个重要原则：

> **同一份构建产物，应通过外部配置适配不同运行环境。**

配置外部化后，代码只声明“我需要哪些参数”，参数值由运行环境提供：

```text
同一个 product-service.jar
        ├── dev：本地存储、短缓存、详细日志
        ├── test：测试存储、测试凭据
        └── prod：对象存储、长缓存、受控日志
```

### 1.2 什么属于配置

适合外部化：

- 数据库、Redis、消息队列地址；
- 超时时间、线程数、批大小；
- 功能开关；
- 环境相关域名；
- 日志级别；
- 密钥的**引用或注入方式**。

不适合伪装成配置：

- 核心业务规则，例如“已支付订单不能删除”；
- 为了逃避设计而制造的几十个布尔开关；
- 需要审计、版本化、审批的复杂业务流程。

### 1.3 外部化配置的代价

外部化不是白赚：

- 配置来源增多后，容易不知道最终值来自哪里；
- 字符串需要转换成数字、时间、枚举等类型，可能绑定失败；
- 配置错误可能让应用在启动时直接失败；
- 配置和密钥可能通过 Git、日志、Actuator 或异常信息泄露。

所以配置体系的真正目标不是“会写 YAML”，而是做到：

> **来源可追踪、覆盖可预测、类型可校验、敏感信息不泄露。**

## 二、Spring Boot 如何看待配置

### 2.1 `Environment`：统一配置视图

Spring Boot 会把文件、环境变量、JVM 系统属性、命令行参数等来源包装成多个 `PropertySource`，再按优先级放进 `Environment`。

```text
application.yaml ─┐
环境变量 ─────────┼──> PropertySource 链 ──> Environment ──> Bean
-D 系统属性 ──────┤
-- 命令行参数 ────┘
```

业务代码通常不应到处直接读取 `Environment`。它更适合框架代码、通用组件或排错工具。业务配置优先绑定为专门的配置对象。

### 2.2 后来的高优先级来源覆盖前面的值

Spring Boot 的完整来源很多，本章先记住最常用的实战顺序。下面从低到高排列：

```text
JAR 内 application.yaml
    < JAR 内 application-{profile}.yaml
    < JAR 外 application.yaml
    < JAR 外 application-{profile}.yaml
    < 操作系统环境变量
    < Java 系统属性（-Dkey=value）
    < 命令行参数（--key=value）
```

例如基础配置是：

```yaml
product:
  pricing:
    currency: CNY
```

即使文件写了 `CNY`，以下命令仍会把最终值改成 `USD`：

```bash
java -jar target/product-service.jar --product.pricing.currency=USD
```

不要只背一张优先级表。真正排错时要问：

1. 这个 key 出现在哪些来源？
2. 哪个来源优先级最高？
3. 当前激活了哪些 Profile？
4. 启动命令和部署平台注入了什么？

> 测试相关的 `@SpringBootTest(properties=...)`、`@DynamicPropertySource`、`@TestPropertySource` 还有更高优先级。本章先聚焦运行时配置，测试配置在第 08 章展开。

## 三、`application.properties` 与 `application.yaml`

### 3.1 两者表达的是同一棵配置树

Properties：

```properties
product.pricing.currency=CNY
product.pricing.max-page-size=100
product.storage.allowed-types[0]=jpg
product.storage.allowed-types[1]=png
```

YAML：

```yaml
product:
  pricing:
    currency: CNY
    max-page-size: 100
  storage:
    allowed-types:
      - jpg
      - png
```

Spring 最终会把 YAML 展平成类似 `product.storage.allowed-types[0]` 的 key。

### 3.2 怎么选

| 维度 | `.properties` | `.yaml` |
|---|---|---|
| 扁平、少量配置 | 简单直接 | 可能显得啰嗦 |
| 层级配置 | key 重复较多 | 结构清晰 |
| 缩进风险 | 无 | 有，Tab 和错位会出错 |
| 重复 key | 容易发现 | 可能被后值覆盖或解析失败 |
| `@PropertySource` | 支持 | 不支持直接加载 YAML |

本课程从第 03 章开始统一使用 `application.yml`。不要在同一位置同时保留 `application.properties` 和 YAML；官方规则是同位置两者并存时 `.properties` 优先，这会制造“明明改了 YAML 却不生效”的错觉。

### 3.3 YAML 常见坑

#### 布尔值、数字和字符串要表达清楚

```yaml
feature:
  enabled: true          # boolean
  code: "00123"         # 保留前导 0，明确写成字符串
  timeout: 3s            # 交给 Duration 转换
```

#### 包含特殊字符时加引号

```yaml
storage:
  endpoint: "https://storage.example.com:9443/api"
  placeholder: "${STORAGE_ENDPOINT:https://localhost:9000}"
```

#### 不要用 Tab 缩进

YAML 依赖空格层级。一个缩进错误就可能改变 key 的完整路径。

## 四、占位符与默认值

Spring 配置支持 `${名称:默认值}`：

```yaml
product:
  storage:
    endpoint: "${PRODUCT_STORAGE_ENDPOINT:http://localhost:9000}"
    access-key: "${PRODUCT_STORAGE_ACCESS_KEY:}"
```

含义：

- 存在环境变量 `PRODUCT_STORAGE_ENDPOINT`：使用环境变量；
- 不存在：endpoint 使用本地默认值；
- access-key 不存在：得到空字符串，后续应由校验阻止不安全环境启动。

默认值不是越多越好：

- 本地开发地址可以有安全默认值；
- 生产数据库密码、访问密钥不应该内置默认值；
- 缺失后会造成严重后果的配置，应该**启动失败**，而不是静默兜底。

占位符中的属性名优先使用小写 kebab-case：

```yaml
description: "${product.display-name:Product Service}"
```

这样更符合 Spring Boot 的规范化命名与宽松绑定规则。

## 五、Profile：环境差异，不是环境复制

### 5.1 基础配置与差异配置

推荐结构：

```text
src/main/resources/
├── application.yml
├── application-dev.yml
└── application-prod.yml
```

`application.yml` 放所有环境共享的安全默认值：

```yaml
spring:
  application:
    name: product-service

product:
  pricing:
    currency: CNY
    max-page-size: 100
```

`application-dev.yml` 只写开发环境差异：

```yaml
product:
  storage:
    endpoint: http://localhost:9000
  pricing:
    cache-ttl: 10s

logging:
  level:
    com.study.mall.product: DEBUG
```

`application-prod.yml` 也只写差异，并从环境读取敏感或部署相关配置：

```yaml
product:
  storage:
    endpoint: "${PRODUCT_STORAGE_ENDPOINT}"
  pricing:
    cache-ttl: 5m

logging:
  level:
    com.study.mall.product: INFO
```

Profile 专用文件覆盖基础文件中的同名属性。不要复制整份基础配置，否则公共配置改一次，要在多个文件同步修改，迟早漂移。

### 5.2 激活 Profile

命令行：

```bash
java -jar target/product-service.jar --spring.profiles.active=dev
```

环境变量：

```bash
SPRING_PROFILES_ACTIVE=prod java -jar target/product-service.jar
```

IDE 运行配置也应通过环境变量或启动参数设置，不要为了方便把 `spring.profiles.active=dev` 永久写死并提交。

没有显式激活 Profile 时，Spring 使用名为 `default` 的默认 Profile。

### 5.3 多 Profile 与最后生效者

```bash
java -jar target/product-service.jar --spring.profiles.active=common,prod
```

多个 Profile 同时定义相同属性时，后面的 Profile 通常覆盖前面的同名值，即 `prod` 可以覆盖 `common`。

这不代表应该用多个互相冲突的环境 Profile。更合理的做法是按维度拆分，例如 `prod`、`metrics`，而不是同时激活 `dev` 和 `prod`。

### 5.4 Profile Group

当一个逻辑环境需要激活多个细粒度 Profile，可以在**非 Profile 专用文档**中定义组：

```yaml
spring:
  profiles:
    group:
      production:
        - prod-db
        - prod-mq
        - prod-observability
```

随后只需要：

```bash
java -jar target/product-service.jar --spring.profiles.active=production
```

不要把 `spring.profiles.active`、`spring.profiles.include` 或 `spring.profiles.group` 放进已由 Profile 激活的文档中。官方文档明确限制了这一点，否则会形成难以推断甚至非法的激活链。

### 5.5 `@Profile` 要克制

```java
@Configuration(proxyBeanMethods = false)
@Profile("dev")
public class DevOnlyConfiguration {
}
```

`@Profile` 可以控制 Bean 是否注册，但不要让业务代码到处充满：

```java
if (profile.equals("prod")) { ... }
```

环境差异优先由配置值、接口实现和条件装配表达。Profile 是部署维度，不应该侵入核心业务规则。

## 六、`@Value`：适合少量值，不适合配置模型

```java
@Component
public class BannerService {

    private final String displayName;

    public BannerService(
            @Value("${product.display-name:Product Service}") String displayName) {
        this.displayName = displayName;
    }
}
```

`@Value` 的优点：

- 读取一个简单值很直接；
- 支持 SpEL；
- 适合一次性的框架接入。

缺点：

- key 散落在多个类中；
- 缺少配置对象的整体结构；
- 重构和 IDE 元数据支持较弱；
- 校验多项配置之间的关系很麻烦；
- 绑定集合、嵌套对象时可读性差。

结论：

> 只有一两个独立值时可以用 `@Value`；属于同一业务前缀的一组配置，用 `@ConfigurationProperties`。

## 七、`@ConfigurationProperties`：类型安全配置

### 7.1 用 record 建立不可变配置模型

```java
package com.study.mall.product.config;

import jakarta.validation.Valid;
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotEmpty;
import jakarta.validation.constraints.NotNull;
import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.validation.annotation.Validated;

import java.time.Duration;
import java.util.List;

@Validated
@ConfigurationProperties(prefix = "product")
public record ProductProperties(
        @NotBlank String displayName,
        @Valid @NotNull Pricing pricing,
        @Valid @NotNull Storage storage
) {
    public record Pricing(
            @NotBlank String currency,
            @Min(1) @Max(500) int maxPageSize,
            @NotNull Duration cacheTtl
    ) {
    }

    public record Storage(
            @NotBlank String endpoint,
            @NotEmpty List<String> allowedTypes
    ) {
    }
}
```

对应 YAML：

```yaml
product:
  display-name: 商品服务
  pricing:
    currency: CNY
    max-page-size: 100
    cache-ttl: 30s
  storage:
    endpoint: http://localhost:9000
    allowed-types:
      - jpg
      - png
```

Spring 会完成：

- `cache-ttl: 30s` → `Duration`；
- YAML List → `List<String>`；
- `max-page-size` → Java 参数 `maxPageSize`；
- 约束不满足时，在启动阶段报错。

配置错误应尽早失败。生产服务启动后才在第一笔请求里发现 endpoint 为空，代价远高于启动失败。

### 7.2 注册配置类

方式一，在启动类开启扫描：

```java
@SpringBootApplication
@ConfigurationPropertiesScan
public class ProductServiceApplication {
    public static void main(String[] args) {
        SpringApplication.run(ProductServiceApplication.class, args);
    }
}
```

方式二，显式注册指定类型：

```java
@Configuration(proxyBeanMethods = false)
@EnableConfigurationProperties(ProductProperties.class)
public class ProductConfiguration {
}
```

业务类像普通 Bean 一样构造器注入：

```java
@Service
public class PricingService {

    private final ProductProperties properties;

    public PricingService(ProductProperties properties) {
        this.properties = properties;
    }
}
```

配置类只负责描述配置，不要在其中注入 Repository、远程客户端等业务 Bean。它是环境到类型对象的边界，不是另一个 Service。

### 7.3 宽松绑定

下面几种写法可以映射到 Java 的 `maxPageSize`：

```text
product.pricing.max-page-size       # YAML/properties 推荐
product.pricing.maxPageSize
product.pricing.max_page_size
PRODUCT_PRICING_MAXPAGESIZE         # 环境变量
```

环境变量转换规则要会推导：

1. `.` 替换为 `_`；
2. 删除 `-`；
3. 转成大写。

因此：

```text
product.pricing.cache-ttl
→ PRODUCT_PRICING_CACHETTL
```

不要凭感觉乱加下划线。部署平台里环境变量名写错，应用可能悄悄继续使用低优先级默认值。

### 7.4 类型转换

Spring Boot 可直接绑定常见类型：

```yaml
product:
  pricing:
    cache-ttl: 30s
  upload:
    max-file-size: 10MB
```

Java 可以使用：

```java
Duration cacheTtl;
DataSize maxFileSize;
```

相比把 `30` 当成毫秒还是秒写在注释里，显式单位更不容易出事故。

### 7.5 List 覆盖不是逐项合并

假设基础配置：

```yaml
product:
  storage:
    allowed-types:
      - jpg
      - png
```

Profile 又配置：

```yaml
product:
  storage:
    allowed-types:
      - webp
```

高优先级 List 通常会替换整份 List，结果不是 `jpg, png, webp`，而是只有 `webp`。Map 更可能按 key 合并，但同名 key 仍由高优先级值覆盖。

这是生产中常见的误判：你以为是“补一个值”，框架理解成“换整张表”。

## 八、配置校验：让错误停在启动阶段

### 8.1 单字段校验

常用约束：

- `@NotBlank`：字符串不能是 null、空串或纯空白；
- `@NotNull`：对象必须存在；
- `@Min` / `@Max`：数值范围；
- `@NotEmpty`：集合不能为空；
- `@Pattern`：格式约束。

当前工程已有 `spring-boot-starter-validation`，可以直接使用 Jakarta Validation 注解。

### 8.2 嵌套对象要使用 `@Valid`

配置根对象加了 `@Validated`，嵌套对象还应加 `@Valid`，让内部约束被递归检查。

### 8.3 配置缺失时不要急着给默认值

错误做法：

```yaml
product:
  storage:
    access-key: "${PRODUCT_STORAGE_ACCESS_KEY:123456}"
```

这会让生产忘记注入密钥时仍能启动，并使用仓库里公开的弱默认值。

更合理的策略：

- 本地安全配置可以默认；
- 敏感配置不提供默认值；
- 用校验让缺失配置启动失败；
- 在部署模板中声明需要注入哪些 key。

## 九、外部配置文件

打包后可以在 JAR 外提供配置。常见默认搜索位置包括当前目录及其 `config/` 子目录。外部配置通常覆盖 JAR 内同名配置。

```text
run/
├── product-service.jar
└── config/
    └── application-prod.yml
```

启动：

```bash
java -jar product-service.jar --spring.profiles.active=prod
```

也可以追加额外位置：

```bash
java -jar product-service.jar \
  --spring.config.additional-location=optional:file:./secrets/
```

注意区别：

- `spring.config.location`：替换默认搜索位置；
- `spring.config.additional-location`：保留默认位置，再追加；
- `optional:`：位置不存在时不阻止启动。

`spring.config.location`、`spring.config.additional-location` 和 `spring.config.name` 在配置加载早期就要使用，因此应通过环境变量、JVM 系统属性或命令行参数提供，不能指望把它们藏在一个尚未被加载的普通配置文件里。

## 十、敏感配置与“配置加密”

### 10.1 Spring Boot 不会自动解密任意 `ENC(...)`

看到这种配置：

```yaml
password: ENC(xxxxx)
```

不要默认 Spring Boot 能解密。`ENC(...)` 不是 Spring Boot 原生通用协议，通常依赖第三方库或公司自研机制。

更关键的问题是：**解密密钥放在哪里？**

如果密文和解密密钥都提交到同一仓库，加密只增加复杂度，没有建立真正的安全边界。

### 10.2 正确优先级

从简单到成熟：

1. 本地开发：未跟踪的本地文件或临时环境变量；
2. CI/CD：平台的加密变量/Secret；
3. 容器平台：Kubernetes Secret、Docker Secret，以文件或环境变量注入；
4. 成熟生产环境：Vault、云厂商 Secret Manager、动态凭据与轮换。

Spring Boot 官方文档对安全凭据给出的方向也是使用外部 Secret 存储，例如 Spring Cloud Vault，而不是在仓库里自创一套可逆加密。

### 10.3 必须遵守的边界

- 不提交密码、AccessKey、Token、私钥；
- 不在接口响应中返回敏感配置；
- 不把完整配置对象直接打印到日志；
- 不公开 Actuator 的 `env`、`configprops` 端点；
- 泄露后立即轮换，删除 Git 最新版本不等于清除历史；
- 示例值使用明显的假值，不要复制真实凭据。

## 十一、如何排查“配置没生效”

按这个顺序，不要一上来乱改：

### 11.1 确认 key 是否一致

- YAML 层级是否正确？
- prefix 是否一致？
- `max-page-size` 是否映射到 `maxPageSize`？
- 环境变量是否按规则转换？

### 11.2 确认 Profile

- 启动日志显示哪些 Profile？
- 是否误把 `dev` 写死？
- 是否同时激活互相冲突的 Profile？
- Profile 文件名是否真的是 `application-prod.yml`？

### 11.3 枚举所有来源

检查：

- JAR 内基础与 Profile 文件；
- JAR 外 `application*.yml`；
- IDE Run Configuration；
- Shell 环境变量；
- `JAVA_TOOL_OPTIONS`；
- `-D...` JVM 参数；
- `--...` 应用参数；
- 容器或部署平台注入。

### 11.4 看绑定异常的根因

常见异常：

| 现象 | 常见原因 | 排查方向 |
|---|---|---|
| `Could not bind properties` | 类型转换失败 | 检查数字、枚举、Duration、DataSize 格式 |
| `BindValidationException` | 校验不通过 | 看具体字段和约束信息 |
| `${KEY}` 无法解析 | 没有来源也没有默认值 | 检查环境变量与占位符 |
| 改 YAML 不生效 | 被高优先级来源覆盖 | 查环境变量、命令行、外部文件 |
| 配置类无法注入 | 未扫描/未启用 | 检查 `@ConfigurationPropertiesScan` 或 `@EnableConfigurationProperties` |
| 嵌套约束没触发 | 缺少级联校验 | 检查 `@Valid` |

### 11.5 Actuator 只在受控环境辅助排查

`env` 和 `configprops` 端点能帮助判断最终值及来源，但可能暴露配置结构甚至敏感信息。只能在本地或受认证、受网络隔离的环境临时使用；验证后恢复最小暴露面。

当前项目已暴露 `conditions,beans,mappings`。不要为了方便直接改成 `*`。

## 十三、小结

| 知识点 | 记住这一句 |
|---|---|
| 外部化配置 | 同一个 JAR，通过运行环境改变行为 |
| `Environment` | 多个 `PropertySource` 组成的统一配置视图 |
| 覆盖原则 | 高优先级来源覆盖低优先级同名属性 |
| YAML | 适合层级结构，但要防缩进和类型陷阱 |
| Profile | 基础文件放公共项，Profile 文件只放差异 |
| `@Value` | 少量独立值可用，不要承载整套业务配置 |
| `@ConfigurationProperties` | 一组配置绑定成类型安全、可校验对象 |
| 宽松绑定 | 文件用 kebab-case，环境变量按转换规则推导 |
| 配置校验 | 严重配置缺失时应启动失败 |
| Secret | 外部注入和专用 Secret 管理优先于仓库内自制加密 |

## 十四、踩坑预警

1. **同一位置混用 `.properties` 和 YAML**：`.properties` 优先，容易改错文件。
2. **把 `spring.profiles.active=dev` 提交到公共基础配置**：生产可能带着开发 Profile 启动。
3. **把整个配置对象打印到日志**：`record` 自动生成的 `toString()` 可能把密钥一起打印。
4. **给敏感配置弱默认值**：忘记注入时不会失败，反而带着错误配置运行。
5. **认为 List 会合并**：高优先级 List 往往整体替换低优先级 List。
6. **公开 Actuator 配置端点**：排错工具会变成信息泄露入口。
7. **只删除 Git 当前文件里的密钥**：历史提交仍然存在，必须轮换凭据并清理历史。
8. **把 Profile 当业务条件**：环境判断散落在业务代码中，测试和维护都会恶化。
