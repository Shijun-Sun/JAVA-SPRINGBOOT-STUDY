## 必做题

### 1-1 生成工程

要求：
- 用 start.spring.io 生成（**不要手写 pom**），Maven + Java 17
- Boot 版本自己去核实当前可用版本，不要照抄讲义里的 `4.0.4`
- `groupId=com.study.mall`，`artifactId=product-service`，`packageName=com.study.mall.product`
- 依赖只要三个：`web`、`validation`、`actuator`（多一个都不要，我们要看清每个依赖带来了什么）
- 放到 `homework/交付/product-service/`

验收：`mvn spring-boot:run` 能起来，控制台看到 Tomcat 端口。

### 1-2 建立分层包结构

按讲义第 2.4 节建好目录。空目录 Git 不会跟踪，每个包下先放一个占位类或 `package-info.java` 都可以。

**注意**：不是照抄，你要能解释每一层的职责。review 时我会问"为什么需要 `vo` 这一层，直接用 `dto` 不行吗"。

### 1-3 第一个接口

写一个 `GET /api/ping`，返回：

```json
{ "code": 200, "message": "ok", "data": "pong" }
```

要求：
- 响应结构用一个泛型类承载（先叫 `Result<T>`），**不要**在 Controller 里手拼 Map
- `Result` 提供静态工厂方法（`success` / `fail`），构造器不对外开放
- 不许用 `@Data`（Lombok 还没引），想想 Java 17 的 **record** 适不适合做 `Result`
  —— 适合还是不适合都要给出理由，这是本题真正的考点

### 1-4 依赖树分析

```bash
mvn dependency:tree > tree.txt
```

回答：
1. 你只声明了 3 个依赖，最终引入了多少个 jar？
2. Tomcat 是通过哪条依赖路径进来的？完整路径写出来
3. `jackson` 是谁带进来的？如果我想换成 Gson，需要做什么？

### 1-5 自动配置探查 ★ 本次作业的核心

**(a) 找出自动配置清单文件**

在依赖 jar 里找到 `AutoConfiguration.imports` 文件。提示：

```bash
# 先定位 jar 的位置
mvn dependency:build-classpath -Dmdep.outputFile=cp.txt
# 然后在 jar 里翻，jar tf 可以列出 jar 内容
```

回答：
1. 你在**哪几个** jar 里找到了这个文件？（Boot 4 模块化的直接体现，Boot 3 只有一个）
2. 挑一个 jar，它的 imports 文件里有多少行（即多少个候选自动配置类）？

**(b) 拿到条件评估报告**

```bash
mvn spring-boot:run -Dspring-boot.run.arguments=--debug > startup.log 2>&1
```

从 `CONDITIONS EVALUATION REPORT` 里各挑 **2 个**，说明原因：
- Positive matches：生效的，说明它为你的应用注册了什么 Bean、因为什么条件通过
- Negative matches：没生效的，说明缺了什么

**(c) 用 Actuator 交叉验证**

开启 `conditions`、`beans`、`mappings` 端点，访问并回答：
1. `/actuator/mappings` 里你的 `/api/ping` 长什么样？除了你写的映射，还有哪些是框架自带的？
2. `/actuator/beans` 里搜 `objectMapper`，它是哪个自动配置类创建的？

> ⚠️ 顺手想一个问题（review 时会问）：这些端点开在生产环境会泄露什么？

### 1-6 覆盖一个默认 Bean

自己定义一个 `ObjectMapper` Bean，配置：日期序列化为 `yyyy-MM-dd HH:mm:ss`，忽略 null 字段。

然后回答：
1. 你的 Bean 和自动配置里的 `ObjectMapper` 冲突了吗？为什么没报"Bean 重复定义"？
2. 重启后再看 `/actuator/beans`，`objectMapper` 的来源变了吗？
3. **反向验证**：如果框架那个 `@Bean` 方法上没有 `@ConditionalOnMissingBean`，会发生什么？

## 进阶题

### 2-1 手写一个自动配置

需求：做一个"应用启动信息打印"的自动配置，应用启动完成后在日志里输出应用名、端口、
激活的 Profile、启动耗时、JDK 版本。

要求：
- 用 `@AutoConfiguration` + `AutoConfiguration.imports` 文件的正规方式，**不是**简单 `@Component`
- 通过 `@ConditionalOnProperty` 提供开关，配置项 `mall.banner.enabled`，默认开启
- 提供 `@ConfigurationProperties` 让用户能自定义输出内容
- 加 `@ConditionalOnMissingBean`，允许用户替换

思考题（比代码重要）：
1. 放在同一个工程里 `@Component` 也能实现，为什么要用自动配置的方式？什么场景下差别才显现？
2. 如果这是公司的内部 starter，`artifactId` 该怎么命名？（有官方约定，去查）

### 2-2 启动流程插桩

在启动流程的**四个不同阶段**各打一行日志，用实际输出验证讲义第三节的顺序：
- `EnvironmentPostProcessor` 里
- `ApplicationContextInitializer` 里
- 某个 Bean 的构造器里
- `ApplicationRunner` 里

回答：
1. 实际日志顺序和讲义描述一致吗？
2. 在 `EnvironmentPostProcessor` 里能拿到你自己的 Service Bean 吗？为什么？
3. "启动后预热商品缓存"为什么必须放在最后一个阶段？放在 Bean 构造器里会出什么问题？（想想缓存服务依赖 Redis 连接池）

### 3-1 拆解 Fat Jar

```bash
mvn clean package
```

1. `jar tf target/product-service-*.jar | head -30` 看结构，画出目录树

3. **核心问题**：标准 JVM 不支持"jar 里嵌套 jar"的类加载，Spring Boot 是怎么解决的？
4. 用 `java -cp` 而不是 `java -jar` 直接跑你的启动类，会成功吗？动手试，解释结果
5. 如果要把这个 jar 放进 Docker 镜像，直接 `COPY app.jar` 有什么问题？
