## 一、先回答"为什么"

你有 Spring MVC + JSP 的经验，那你应该记得当年启动一个 Web 项目要做什么：

```
1. 装一个 Tomcat，配 server.xml
2. 写 web.xml，注册 DispatcherServlet、CharacterEncodingFilter、listener
3. 写 applicationContext.xml，声明 dataSource、sessionFactory、transactionManager
4. 写 spring-mvc.xml，配 <mvc:annotation-driven/>、视图解析器、静态资源映射
5. 手动挑 spring-core / spring-web / spring-webmvc / jackson 的版本，祈祷不冲突
6. 打成 war，丢进 Tomcat 的 webapps，重启
```

这里面**没有一行是业务代码**。Spring Boot 干掉的就是这一整套。它只做三件事：

| 做的事 | 干掉了什么 | 本质 |
|--------|-----------|------|
| **依赖管理**（starter + BOM） | 手挑版本、解决 jar 冲突 | 一份官方维护的版本兼容矩阵 |
| **自动配置**（auto-configuration） | applicationContext.xml、spring-mvc.xml | 按 classpath 上有什么，条件化地注册 Bean |
| **内嵌容器** | 装 Tomcat、配 server.xml、打 war | Tomcat 变成一个普通依赖，`main` 方法直接启动 |

**代价是什么？** 这点比优点更值得记住，因为它就是你以后要排查的问题：

- **"约定优于配置"意味着大量行为是隐式的**。出问题时你看不到配置在哪，只能去翻自动配置类。
- **依赖传递链变长**。引一个 starter 进来十几个 jar，安全漏洞和意外的 Bean 都可能跟着进来。
- **容易写出"能跑但不能扩展"的代码**。框架把门槛降得太低，很多人跳过分层直接在 Controller 里写 SQL。

所以这个模块的重点不是"用起来"，而是**让隐式的东西对你变成显式的**。

## 二、工程骨架

### 2.1 用 start.spring.io 生成，不要手写 pom

命令行方式（不用开浏览器，参数一目了然）：

```bash
curl https://start.spring.io/starter.zip \
  -d type=maven-project \
  -d language=java \
  -d bootVersion=4.0.4 \
  -d javaVersion=17 \
  -d groupId=com.study.mall \
  -d artifactId=product-service \
  -d name=product-service \
  -d packageName=com.study.mall.product \
  -d dependencies=web,validation,actuator \
  -o product-service.zip
```

> `bootVersion` 别写死，先 `curl https://start.spring.io/metadata/client` 看当时的可用版本列表。
> 这个习惯很重要：**版本靠核实，不靠记忆**。

### 2.2 pom.xml 的关键结构

```xml
<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>4.0.4</version>
    <relativePath/>
</parent>
```

`spring-boot-starter-parent` 内部继承了 `spring-boot-dependencies`，后者是一个巨大的 `<dependencyManagement>`，
声明了几百个第三方库的**兼容版本**。所以你的依赖不写版本号：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
    <!-- 没有 version：由 BOM 统一管控 -->
</dependency>
```

**这是架构层面的价值**：几十个模块的大项目里，版本统一由一处控制，避免"A 模块用 Jackson 2.15、B 模块用 2.17，运行时随机报 NoSuchMethodError"。

看一下依赖树，理解"引一个进来十几个"：

```bash
mvn dependency:tree
```

### 2.3 Spring Boot 4 的重要变化：自动配置模块化

这是从 Boot 3 升上来最容易踩的坑，先讲清楚。

Boot 3 时代，几乎所有自动配置类都塞在一个巨大的 `spring-boot-autoconfigure` jar 里 —— 哪怕你只写一个纯 Web 应用，
这个 jar 里 Kafka、MongoDB、Redis 的自动配置类也都在 classpath 上躺着（靠 `@ConditionalOnClass` 不生效而已）。

Boot 4 把它拆成了一堆细粒度模块（`spring-boot-webmvc`、`spring-boot-data-jpa` 等）。
带来的实际影响：**一些原来"顺带就有"的东西，现在需要显式引入对应模块**。
典型例子是测试相关的 `@AutoConfigureMockMvc`，在 Boot 4 里需要配套 `spring-boot-starter-webmvc-test`。

参考：[Modularizing Spring Boot（Spring 官方博客，2025-10）](https://spring.io/blog/2025/10/28/modularizing-spring-boot/)（内容已改写以符合引用规范）

> 作业里会让你亲手到 classpath 上把这些模块和自动配置清单翻出来，眼见为实。

### 2.4 分层包结构（这个骨架要撑到 M11）

```
com.study.mall.product
├── ProductServiceApplication.java   启动类（必须在根包）
├── config/                          配置类：@Configuration
├── controller/                      接入层：只做参数校验、协议转换
├── service/                         业务层：业务规则、事务边界
│   └── impl/
├── repository/  (或 mapper/)        数据访问层
├── domain/                          领域对象
│   ├── entity/                      数据库映射对象，不出 service 层
│   ├── dto/                         入参对象（外 → 内）
│   └── vo/                          出参对象（内 → 外）
├── common/                          统一响应、错误码、常量
│   ├── result/
│   └── exception/
└── support/                         横切：AOP、拦截器、工具
```

三条铁律，现在建立习惯，后面省无数事：

1. **依赖方向严格单向**：`controller → service → repository`。反向依赖（service 引 controller）一旦出现，
   就意味着以后没法把这个模块单独拆出去。
2. **Entity 不许出现在 Controller 的签名里**。理由在验收清单里要你答 3 个，先自己想。
3. **启动类放在根包**，因为 `@ComponentScan` 默认扫描它所在的包及子包。

## 三、启动流程：`main` 方法里发生了什么

```java
@SpringBootApplication
public class ProductServiceApplication {
    public static void main(String[] args) {
        SpringApplication.run(ProductServiceApplication.class, args);
    }
}
```

这一行背后的主干链路（记住阶段和顺序，不用背方法名）：

```
SpringApplication.run()
│
├─ 1. 推断应用类型
│     classpath 上有 Servlet API + Spring MVC → SERVLET 类型
│     只有 WebFlux → REACTIVE；都没有 → NONE（普通命令行应用）
│
├─ 2. 加载 SpringApplicationRunListeners、ApplicationContextInitializer
│     从 META-INF/spring.factories 等扩展点读取，这是框架留给你的插入口
│
├─ 3. 准备 Environment
│     加载 application.yml / 环境变量 / 命令行参数 / Profile → 形成配置的优先级链
│     ★ 这一步在容器创建之前，所以配置能影响后面所有环节
│
├─ 4. 打印 Banner，创建 ApplicationContext
│
├─ 5. prepareContext：注册启动类为 Bean Definition
│
├─ 6. refreshContext ← 真正的核心
│     ├─ 扫描 @ComponentScan 范围，注册所有 Bean Definition
│     ├─ 处理 @EnableAutoConfiguration：把符合条件的自动配置类也注册进来
│     ├─ 执行 BeanFactoryPostProcessor（可以改 Bean Definition）
│     ├─ 实例化所有非懒加载单例 Bean，注入依赖，执行初始化回调
│     └─ 启动内嵌 Web 容器（Tomcat），DispatcherServlet 注册到容器
│
└─ 7. 执行 ApplicationRunner / CommandLineRunner，发布 ApplicationReadyEvent
```

**为什么要记这个？** 三个实际用途：

- 需要"应用启动后做一件事"（预热缓存、加载字典表）→ 放第 7 步的 `ApplicationRunner`，不要写在静态代码块或构造器里
- 需要"在容器起来之前改配置"→ 第 3 步的 `EnvironmentPostProcessor`
- 启动慢、启动报 Bean 循环依赖 → 问题一定在第 6 步，去看 Bean 的创建顺序

## 四、`@SpringBootApplication` 拆解

它是一个复合注解，等价于三个：

```java
@SpringBootConfiguration   // 本质是 @Configuration：这个类本身是配置类
@EnableAutoConfiguration   // 打开自动配置
@ComponentScan             // 扫描当前包及子包的 @Component/@Service/@Controller...
public class ProductServiceApplication { }
```

三者职责完全不同，别混：

- `@ComponentScan` 管的是**你自己写的 Bean**
- `@EnableAutoConfiguration` 管的是**框架和第三方库提供的 Bean**
- `@SpringBootConfiguration` 让启动类自己也能定义 `@Bean`

## 五、自动配置机制（本讲最重要的部分）

### 5.1 生效流程

```
@EnableAutoConfiguration
   ↓
读取所有 jar 里的
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
   ↓（这是一个纯文本文件，每行一个自动配置类的全限定名）
拿到候选自动配置类清单（几十上百个）
   ↓
逐个执行 @Conditional 判断 —— 不满足的直接淘汰，连类都不加载
   ↓
存活下来的注册为 Bean Definition，参与容器初始化
```

### 5.2 条件注解：自动配置的灵魂

| 注解 | 含义 | 典型用途 |
|------|------|---------|
| `@ConditionalOnClass` | classpath 上有某个类才生效 | 有 `DataSource` 类才配数据源 |
| `@ConditionalOnMissingClass` | 没有某个类才生效 | |
| `@ConditionalOnBean` | 容器里已有某个 Bean 才生效 | 依赖别的自动配置的结果 |
| `@ConditionalOnMissingBean` | 容器里**没有**某个 Bean 才生效 | ★ 让用户配置能覆盖默认配置 |
| `@ConditionalOnProperty` | 配置项匹配才生效 | `xxx.enabled=true` 开关 |
| `@ConditionalOnWebApplication` | 是 Web 应用才生效 | |

`@ConditionalOnMissingBean` 是理解 Spring Boot 设计哲学的钥匙：

```java
@AutoConfiguration
@ConditionalOnClass(ObjectMapper.class)
public class JacksonAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean          // ← 你自己定义了 ObjectMapper，这里就自动让位
    ObjectMapper jacksonObjectMapper() { ... }
}
```

**"默认给你一个，但你随时能替换"** —— 这就是自动配置能既开箱即用又不失控的原因。
以后你自己写公司内部 starter，这是必须掌握的模式。

### 5.3 排查手段（必须掌握，这是硬技能）

场景：某个 Bean 你以为会自动有，结果启动报 `NoSuchBeanDefinitionException`。

**手段一：条件评估报告**

```bash
mvn spring-boot:run -Dspring-boot.run.arguments=--debug
# 或
java -jar app.jar --debug
```

输出里找 `CONDITIONS EVALUATION REPORT`，它分三块：

```
Positive matches:   生效了的自动配置，附带原因
Negative matches:   没生效的，附带"因为缺什么"
Exclusions:         被显式排除的
```

**手段二：Actuator 端点**（更直观，建议开发环境常开）

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,conditions,beans,configprops,env,mappings
```

- `/actuator/conditions` —— 条件评估报告的 JSON 版
- `/actuator/beans` —— 容器里所有 Bean 及其依赖关系
- `/actuator/configprops` —— 所有 `@ConfigurationProperties` 的实际生效值
- `/actuator/mappings` —— 所有 URL 映射（排查 404 的第一站）

> ⚠️ **生产环境安全**：Actuator 端点会暴露配置、环境变量、Bean 结构，属于敏感信息。
> 生产环境必须做到：只暴露 `health`（且用 `never` 隐藏细节）、
> 换到独立管理端口且不对外网开放、加上认证鉴权。
> 2026 年 3 月 Spring Boot 就修过 Actuator 相关的认证绕过 CVE，这不是理论风险。
> 这块到 M04（安全）和 M10（可观测性）会详细讲。

### 5.4 排除自动配置

```java
@SpringBootApplication(exclude = { DataSourceAutoConfiguration.class })
```

或配置文件：

```yaml
spring:
  autoconfigure:
    exclude: org.springframework.boot.jdbc.autoconfigure.DataSourceAutoConfiguration
```

> 类的包路径在 Boot 4 里可能和 Boot 3 不同（模块化的直接后果），
> **别照抄网上 Boot 2/3 的教程，去 classpath 上核实实际路径**。

## 六、内嵌容器

```
spring-boot-starter-web
   └── spring-boot-starter-tomcat
         └── tomcat-embed-core   ← Tomcat 变成一个普通 jar 依赖
```

启动时 Boot 创建一个 `TomcatWebServer`，监听端口，把 `DispatcherServlet` 注册进去。
所以**部署产物是一个可执行 jar，不是 war** —— 这是容器化时代的前提：镜像里只需要 JRE，不需要装 Tomcat。

Boot 4 的相关基线：Jakarta EE 11 / Servlet 6.1 / Tomcat 11。
换容器可以把 tomcat starter 排掉换成 Jetty；**Undertow 在 Boot 4 里已被移除**，别再找它的教程。

Fat jar 的结构（作业里要你验证）：

```
app.jar
├── META-INF/MANIFEST.MF          Main-Class 指向 Boot 的启动器，不是你的启动类
├── org/springframework/boot/loader/...   Boot 自己的 ClassLoader
└── BOOT-INF/
    ├── classes/                  你的代码
    └── lib/                      所有依赖 jar（jar 里嵌 jar，标准 JVM 不支持，靠上面的 loader）
```

## 七、踩坑预警

| 坑 | 症状 | 原因 |
|----|------|------|
| 启动类不在根包 | `@Service` 全都注入不上 | `@ComponentScan` 默认只扫启动类所在包及子包 |
| 手写依赖版本号 | 运行时 `NoSuchMethodError` / `ClassNotFoundException` | 绕过了 BOM 的版本兼容矩阵 |
| 照抄 Boot 2/3 的自动配置类全限定名 | `ClassNotFoundException` | Boot 4 模块化后包路径变了 |
| 生产开放全部 Actuator 端点 | 配置、环境变量泄露 | 默认只有 health/info 暴露，别自己改成 `include: "*"` |
| 用 `@Autowired` 字段注入 | 循环依赖、无法单测、字段可为 null | 下一讲细说 |
| 复制别人的 yml 却不看优先级 | "我改了配置怎么没生效" | 环境变量/命令行优先级高于 yml，第 03 讲细说 |
