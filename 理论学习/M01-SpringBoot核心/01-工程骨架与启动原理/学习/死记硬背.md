## Maven（mvn）

> 你需要知道的核心：Maven 是 **依赖管理 + 构建工具**。
> 你 90% 的时间只用这几件事：拉依赖、编译、运行、打包、看依赖树。

---

### 一、生命周期（背这张表）

Maven 有三条独立的生命周期，每条都是**从头顺序执行**，执行靠后的阶段会自动执行前面所有阶段。

**最常用的是 `default` 生命周期：**

```
validate → compile → test → package → verify → install → deploy
```

| 阶段 | 做什么 | 常用场景 |
|------|--------|---------|
| `compile` | 编译 `src/main/java` | 看编译报错 |
| `test` | 编译并运行测试 | 跑单测 |
| `package` | 打成 jar/war 放到 `target/` | 构建产物 |
| `install` | 打包 + 安装到本地 `~/.m2` 仓库 | 多模块项目互相依赖时用 |
| `deploy` | 推送到远程仓库 | CI/CD 发布 |

> **关键推论**：`mvn package` = 自动先跑 compile + test + package。
> 想跳过测试：加 `-DskipTests`。

**另外两条生命周期（偶尔会用）：**

| 命令 | 做什么 |
|------|--------|
| `mvn clean` | 删除 `target/` 目录，清理上次构建产物 |
| `mvn site` | 生成项目文档站点（基本不用） |

---

### 二、最常用命令（直接抄）

```bash
# ① 编译
mvn compile

# ② 跳过测试打包（最常用）
mvn package -DskipTests

# ③ 清理后打包（推荐，避免旧 class 文件干扰）
mvn clean package -DskipTests

# ④ 安装到本地仓库（多模块项目必用）
mvn clean install -DskipTests

# ⑤ 查看依赖树（排查版本冲突第一步）
mvn dependency:tree

# ⑥ 搜索依赖树中的某个 jar
mvn dependency:tree | grep jackson

# ⑦ Spring Boot 直接运行（开发阶段）
mvn spring-boot:run

# ⑧ 只跑测试
mvn test

# ⑨ 跳过测试编译（不跑但会编译测试代码）
mvn test -DskipTests

# ⑩ 完全跳过测试代码连编译都不编译（更快）
mvn package -Dmaven.test.skip=true
```

### 三、`mvn dependency:tree` 看懂输出

```
[INFO] com.study.mall:product-service:jar:0.0.1-SNAPSHOT
[INFO] +- org.springframework.boot:spring-boot-starter-web:jar:4.0.4:compile
[INFO] |  +- org.springframework.boot:spring-boot-starter:jar:4.0.4:compile
[INFO] |  |  +- org.springframework.boot:spring-boot:jar:4.0.4:compile
[INFO] |  \- org.springframework.boot:spring-boot-starter-tomcat:jar:4.0.4:compile
[INFO] \- com.fasterxml.jackson.core:jackson-databind:jar:2.17.0:compile
```

**符号含义：**

| 符号 | 含义 |
|------|------|
| `+-` | 有后续兄弟节点 |
| `\-` | 最后一个子节点 |
| `\|` | 树的连接线 |

**scope 含义（冒号后面那个词）：**

| scope | 含义 | 打进 jar？ |
|-------|------|-----------|
| `compile` | 编译+运行都需要（默认） | ✅ |
| `test` | 只在测试时需要（如 JUnit） | ❌ |
| `provided` | 编译需要，运行时由容器提供（如 Servlet API） | ❌ |
| `runtime` | 编译不需要，运行需要（如 MySQL 驱动） | ✅ |

**看到 `omitted for conflict` 说明版本冲突，Maven 自动选了一个：**

```
\- (com.fasterxml.jackson.core:jackson-databind:jar:2.15.0:compile - omitted for conflict with 2.17.0)
```

> 解决冲突：在自己的 `pom.xml` 里显式声明你要的版本，优先级最高。

### 四、`pom.xml` 关键结构（快速定位）

```xml
<project>
  <!-- ① 继承 Spring Boot BOM，统一管理所有依赖版本 -->
  <parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>4.0.4</version>
  </parent>

  <!-- ② 本项目坐标 -->
  <groupId>com.study.mall</groupId>
  <artifactId>product-service</artifactId>
  <version>0.0.1-SNAPSHOT</version>

  <!-- ③ 覆盖 BOM 中的某个版本（需要时用） -->
  <properties>
    <jackson.version>2.17.0</jackson.version>
  </properties>

  <!-- ④ 依赖声明（有 parent BOM 时不写 version） -->
  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-web</artifactId>
    </dependency>

    <!-- test scope 示例 -->
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-test</artifactId>
      <scope>test</scope>
    </dependency>
  </dependencies>

  <!-- ⑤ 打包插件（Spring Boot fat jar 必须有） -->
  <build>
    <plugins>
      <plugin>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-maven-plugin</artifactId>
      </plugin>
    </plugins>
  </build>
</project>
```

### 五、排除某个传递依赖

场景：`starter-web` 带进来了 Tomcat，但我想换成 Jetty。

```xml
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
  <exclusions>
    <exclusion>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-tomcat</artifactId>
    </exclusion>
  </exclusions>
</dependency>

<!-- 换成 Jetty -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-jetty</artifactId>
</dependency>
```

### 七、多模块项目（结构速览）

```
mall/                          ← 父模块（只有 pom.xml，不写业务代码）
├── pom.xml                    ← packaging: pom，声明 <modules>
├── mall-common/               ← 子模块（通用工具）
│   └── pom.xml                ← parent 指向父模块
├── mall-product/              ← 子模块（商品服务）
│   └── pom.xml
└── mall-order/                ← 子模块（订单服务）
    └── pom.xml
```

**父模块 pom.xml 关键片段：**

```xml
<packaging>pom</packaging>  <!-- 必须是 pom，不是 jar -->

<modules>
  <module>mall-common</module>
  <module>mall-product</module>
  <module>mall-order</module>
</modules>
```

**在父模块根目录执行，所有子模块一起构建：**

```bash
mvn clean install -DskipTests   # 按 modules 声明顺序构建所有子模块
```

### 八、常见报错速查

| 报错关键词 | 原因 | 解决 |
|-----------|------|------|
| `Could not resolve dependencies` | 依赖下载失败 | 检查网络/镜像，或删 `~/.m2/repository` 中对应目录重新下载 |
| `NoSuchMethodError` | jar 版本冲突，运行时用了错误版本 | `mvn dependency:tree` 找冲突，显式指定版本 |
| `ClassNotFoundException` | classpath 上没有这个类，依赖没引进来 | 检查 pom.xml 是否有对应依赖 |
| `BUILD FAILURE` + `Tests run: X, Failures: Y` | 单测失败 | 加 `-DskipTests` 先跳过，或修复测试 |
| `Port 8080 already in use` | 端口被占用 | `lsof -i :8080` 找进程 kill，或改 `server.port` |

## SpringApplication.run() 启动 7 步

> 背住阶段名和顺序，不用背方法名。
> 核心口诀：**推断 → 加载扩展 → 准备环境 → 建容器 → 注册主类 → 刷新容器 → 发布就绪**

---

### 一张图记住顺序

```
SpringApplication.run()
│
├─ 1. 推断应用类型          ← classpath 上有什么就是什么
│
├─ 2. 加载扩展点            ← 从 spring.factories 读监听器、初始化器
│
├─ 3. 准备 Environment      ← 加载所有配置，形成优先级链
│
├─ 4. 打印 Banner，创建 ApplicationContext
│
├─ 5. prepareContext        ← 把主类注册为 Bean Definition
│
├─ 6. refreshContext ★      ← 真正核心：扫描+自动配置+实例化+启动 Tomcat
│
└─ 7. 发布 ApplicationReadyEvent，执行 Runner
```

---

### 每步展开讲（看懂才能背）

---

#### 第 1 步：推断应用类型

**做了什么：** Spring Boot 检查 classpath 上有没有特定的类，来决定这是什么类型的应用。

| classpath 上有什么 | 推断为 | 含义 |
|-------------------|--------|------|
| Servlet API + Spring MVC | `SERVLET` | 普通 Web 应用，启 Tomcat |
| WebFlux（Reactor Netty） | `REACTIVE` | 响应式 Web 应用 |
| 两者都没有 | `NONE` | 普通命令行应用，不启 Web 容器 |

**为什么要推断：** 后面第 4 步要根据这个类型创建不同的 `ApplicationContext`（容器的实现类不一样）。

**记法：** 你加了 `spring-boot-starter-web` → 带进了 Tomcat + MVC → 推断为 SERVLET。

---

#### 第 2 步：加载扩展点（SpringApplicationRunListeners、ApplicationContextInitializer）

**做了什么：** 从 `META-INF/spring.factories`（旧版）或 `META-INF/spring/xxx.imports`（新版）文件里，读取框架预先注册好的监听器和初始化器，加载到内存。

**这两个东西是什么：**

| 扩展点 | 作用 | 类比 |
|--------|------|------|
| `SpringApplicationRunListener` | 监听启动过程本身（比如"环境准备好了"、"容器刷新了"这些事件） | 工地上的"监理"，全程跟着 |
| `ApplicationContextInitializer` | 容器创建后、刷新前，对容器做一些定制化处理 | 新房装修前，先做一道"基础处理" |

**为什么要在这么早的阶段加载：** 后续每一步都要通知监听器（"第3步开始了"、"第5步开始了"），所以必须最先把监听器准备好。

**记法：** 这一步是**框架给你留的插入口**。你自己写了 `ApplicationContextInitializer` 放到 `spring.factories` 里，就会在这一步被发现。

---

#### 第 3 步：准备 Environment（配置优先级链）

**做了什么：** 把所有配置来源全部加载进来，合并成一个 `Environment` 对象，并建立优先级顺序。

**配置来源（从高到低优先级）：**

```
命令行参数                    ← 最高（java -jar xxx.jar --server.port=9090）
  ↓
系统环境变量                  ← 比如 SERVER_PORT=9090
  ↓
application-{profile}.yml    ← 激活的 Profile 专属配置
  ↓
application.yml / .properties ← 默认配置文件
  ↓
@PropertySource 注解          ← 最低
```

**最重要的一句话：这一步在容器创建之前。** 所以你的 `application.yml` 里配置 `spring.datasource.url` 之类的东西，在容器创建时就已经读进来了，后面 Bean 初始化时直接用。

**记法：** 优先级口诀：**命令行 > 环境变量 > Profile > 默认配置文件**。

---

#### 第 4 步：打印 Banner，创建 ApplicationContext

**做了什么：** 两件事，顺序发生。

1. **打印 Banner**：就是启动时控制台那个 Spring 字符画。可以在 `src/main/resources/banner.txt` 自定义，设 `spring.main.banner-mode=off` 可关闭。

2. **创建 ApplicationContext**：根据第 1 步推断的类型，new 出对应的容器实例。

| 应用类型 | 创建的容器 |
|---------|-----------|
| SERVLET | `AnnotationConfigServletWebServerApplicationContext` |
| REACTIVE | `AnnotationConfigReactiveWebServerApplicationContext` |
| NONE | `AnnotationConfigApplicationContext` |

**注意：** 这里只是 new 出容器对象，还没有扫描 Bean，容器是空的。真正扫描是第 6 步。

---

#### 第 5 步：prepareContext（注册主类为 Bean Definition）

**做了什么：** 把你写的启动类（带 `@SpringBootApplication` 的那个类）作为第一个 Bean Definition 注册进容器。

**Bean Definition 是什么：** 可以理解成"Bean 的图纸"。它描述这个 Bean 叫什么、是什么类、怎么创建、有什么依赖，但此时还没有真正 new 出对象。

**为什么要先注册主类：** `@SpringBootApplication` = `@ComponentScan` + `@EnableAutoConfiguration` + `@Configuration`。第 6 步 refresh 时，Spring 会从这个主类开始，顺着 `@ComponentScan` 去扫描其他所有 Bean。所以主类必须是"扫描的起点"，要提前注册。

**记法：** prepareContext = 给容器"播一粒种子"（主类），第 6 步才开始"发芽"。

---

#### 第 6 步：refreshContext ★ 真正的核心

**做了什么：** 这是最重量级的一步，里面包含 5 个子阶段：

```
refreshContext
│
├─ ① 扫描 @ComponentScan 范围，注册所有 Bean Definition
│    （找到所有 @Component、@Service、@Repository、@Controller 的类，登记造册）
│
├─ ② 处理 @EnableAutoConfiguration
│    （从 spring.factories 读自动配置类，过滤掉不满足 @Conditional 条件的，剩下的也注册为 Bean Definition）
│
├─ ③ 执行 BeanFactoryPostProcessor
│    （在 Bean 实例化之前，允许修改 Bean Definition，比如占位符 ${} 的替换就在这里发生）
│
├─ ④ 实例化所有非懒加载单例 Bean，注入依赖，执行初始化回调
│    （真正 new 对象，@Autowired 注入，@PostConstruct 执行）
│
└─ ⑤ 启动内嵌 Web 容器（Tomcat），DispatcherServlet 注册到容器
     （端口开始监听，服务可以接受请求了）
```

**理解口诀：先登记造册 → 过滤自动配置 → 改图纸 → 造对象 → 开门营业**

**关键理解：**
- 步骤 ①② 是"登记"（Bean Definition），还没实例化
- 步骤 ④ 才是真正"造对象"
- `@Lazy` 注解的 Bean 跳过步骤 ④，第一次被调用时才造
- Tomcat 在步骤 ⑤ 启动，所以在此之前打的日志你还访问不了接口

---

#### 第 7 步：发布 ApplicationReadyEvent，执行 Runner

**做了什么：** 容器全部就绪后，做两件收尾事：

1. **发布 `ApplicationReadyEvent`**：通知所有监听这个事件的监听器"应用启动完了"。你可以实现 `ApplicationListener<ApplicationReadyEvent>` 来做一些"启动后初始化"的工作（比如预热缓存）。

2. **执行 Runner**：按顺序执行所有 `ApplicationRunner` 和 `CommandLineRunner` 的实现类。

**ApplicationRunner vs CommandLineRunner 区别：**

| 接口 | 方法签名 | 参数 |
|------|---------|------|
| `ApplicationRunner` | `run(ApplicationArguments args)` | 封装好的参数对象，方便取 `--key=value` |
| `CommandLineRunner` | `run(String... args)` | 原始字符串数组 |

**使用场景：** 应用启动后执行一次性任务，比如检查配置、预加载数据、打印启动信息。

```java
@Component
@Order(1)  // 多个 Runner 时控制顺序
public class StartupRunner implements ApplicationRunner {
    @Override
    public void run(ApplicationArguments args) {
        System.out.println("应用启动完成，开始预热缓存...");
    }
}
```

### 速记版（考试/面试用）

```
1. 推断类型        classpath 有 MVC → SERVLET，有 WebFlux → REACTIVE，都没有 → NONE
2. 加载扩展点      从 spring.factories 读监听器、初始化器（框架插入口）
3. 准备 Environment 命令行 > 环境变量 > Profile > 配置文件，容器创建前就绪
4. 建 ApplicationContext  根据类型 new 对应容器，Banner 在这里打印
5. prepareContext  把主类注册为第一个 Bean Definition（扫描起点）
6. refreshContext  ★扫描→自动配置→BeanFactoryPostProcessor→实例化→启 Tomcat
7. 发布 ReadyEvent  执行 ApplicationRunner / CommandLineRunner
```

## classpath 是什么

> 一句话：**classpath = JVM 能看到的所有类和文件的范围**，跟 Tomcat 无关，是 JVM 自己的概念。

---

### classpath 里有什么

一个 Spring Boot 项目运行起来，classpath 包含这三块：

```
classpath
├── 你自己写的代码编译产物       ← src/main/java  编译后的 .class
├── 你的资源文件                ← src/main/resources 下的所有文件
│                                  application.yml、banner.txt、mapper/*.xml 等
└── 所有依赖的 jar 包内容       ← pom.xml 里声明的每一个依赖
                                   spring-mvc.jar、tomcat-embed.jar、jackson.jar ...
```

---

### "classpath 上有 Servlet API"是什么意思

就是：在上面三块里，能不能找到 `jakarta.servlet.Servlet` 这个类。

你在 `pom.xml` 加了 `spring-boot-starter-web`，它传递依赖了 `tomcat-embed-core.jar`，这个 jar 里就有 `Servlet` 这个类。所以 classpath 上"有 Servlet API"。

Spring Boot 的检测方式：用类加载器试着加载这个类，加载成功 = 有，抛异常 = 没有。

---

### 不是扫源码，是扫依赖

容易误解成"扫源码判断类型"，实际上 Java 运行时根本没有源码，只有编译后的 `.class` 和 jar 包。

**Node.js 类比（错误版）：**
```
node server.js  →  读 server.js 文本  →  看你 require 了什么   ← 这是扫源码
```

**Node.js 类比（正确版）：**
```
不是扫 server.js 源码
而是扫 node_modules 里有没有装 express
  → 装了 express    → 判断是 HTTP 服务
  → 装了 socket.io  → 判断是 WebSocket 服务
  → 什么都没装      → 判断是命令行工具
```

**Java 的实际顺序：**
```
你写了 pom.xml → 声明依赖 spring-boot-starter-web
        ↓
Maven 把 tomcat.jar 下载下来，打进 fat jar
        ↓
JVM 启动，tomcat.jar 的内容进入 classpath
        ↓
Spring Boot 去 classpath 里找有没有 Servlet 这个类
  → 找到了 → 推断 SERVLET 类型 → 第 6 步启动 Tomcat
```

**结论：你的意图通过 `pom.xml` 声明依赖来表达，不是通过写代码来表达。**

## Spring Boot Controller 常用知识点

> 对应作业 1-3：写 `GET /api/ping`，返回统一响应结构。
> 这一节只讲"会用"，不讲源码原理。

---

### 一、最小可用 Controller 模板

```java
package com.study.mall.product.controller;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController                      // ① 声明这是 Controller，且所有方法返回值直接写进响应体
@RequestMapping("/api")              // ② 给这个 Controller 的所有接口加统一前缀
public class PingController {

    @GetMapping("/ping")             // ③ 处理 GET /api/ping
    public String ping() {
        return "pong";               // 直接返回字符串，Jackson 序列化成 JSON
    }
}
```

**三个注解必须会用：**

| 注解 | 作用 | 等价于 |
|------|------|--------|
| `@RestController` | Controller + 所有方法自动加 `@ResponseBody` | `@Controller` + `@ResponseBody` |
| `@RequestMapping("/api")` | 给 Controller 加路径前缀 | — |
| `@GetMapping("/ping")` | 处理 GET 请求 | `@RequestMapping(method = RequestMethod.GET)` |

**其他 HTTP 方法注解（同理）：**

```java
@PostMapping("/products")       // POST
@PutMapping("/products/{id}")   // PUT
@DeleteMapping("/products/{id}")// DELETE
@PatchMapping("/products/{id}") // PATCH
```

---

### 二、统一响应结构 Result\<T\>

> 作业要求：不要在 Controller 里手拼 Map，用泛型类承载响应。

**为什么要有 Result\<T\>：** 前端需要一个固定的 JSON 结构，方便统一处理成功/失败。

```json
{ "code": 200, "message": "ok", "data": "pong" }
{ "code": 500, "message": "商品不存在", "data": null }
```

**标准写法：**

```java
package com.study.mall.product.common;

public class Result<T> {

    private final int code;
    private final String message;
    private final T data;

    // 构造器私有，不对外开放（作业要求）
    private Result(int code, String message, T data) {
        this.code = code;
        this.message = message;
        this.data = data;
    }

    // 静态工厂方法：成功
    public static <T> Result<T> success(T data) {
        return new Result<>(200, "ok", data);
    }

    // 静态工厂方法：失败
    public static <T> Result<T> fail(String message) {
        return new Result<>(500, message, null);
    }

    // Getter（Jackson 序列化需要）
    public int getCode() { return code; }
    public String getMessage() { return message; }
    public T getData() { return data; }
}
```

**Controller 里这样用：**

```java
@GetMapping("/ping")
public Result<String> ping() {
    return Result.success("pong");
    // 序列化结果：{"code":200,"message":"ok","data":"pong"}
}
```

**关键点：**
- 构造器 `private`，外部只能通过 `Result.success()` / `Result.fail()` 创建
- 泛型 `<T>` 让 `data` 字段可以是任意类型（String、对象、List 都行）
- 必须有 Getter，Jackson 靠 Getter 来序列化字段

---

### 三、静态工厂方法 vs 构造器

作业要求"提供静态工厂方法，构造器不对外开放"，这是一种设计习惯，理由：

| 对比点 | 构造器 `new Result(...)` | 静态工厂 `Result.success(...)` |
|--------|------------------------|-------------------------------|
| 可读性 | 不知道这次调用的语义 | 方法名直接表达意图 |
| 灵活性 | 每次都 new 新对象 | 可以内部缓存、复用对象 |
| 控制性 | 外部随意构造，容易传错参数 | 强制走固定逻辑，更安全 |

---

### 四、Java record 适不适合做 Result\<T\>（作业考点）

> 作业要求你自己给出判断和理由，这里把两面都列出来，你自己选边站。

**什么是 record：** Java 16 正式引入，专门用来做"纯数据载体"，自动生成构造器、Getter、equals、hashCode、toString。

```java
// record 写法
public record Result<T>(int code, String message, T data) {}

// 自动生成了：
// - public Result(int code, String message, T data) {}  ← 全参构造器，且是 public
// - public int code() {}                                ← 注意是 code()，不是 getCode()
// - public String message() {}
// - public T data() {}
```

**不适合的理由（作业要求这个方向）：**

1. **构造器强制 public，无法私有化。** record 的规范构造器必须是 public，无法满足"构造器不对外开放"的要求。你没法阻止外部 `new Result<>(500, "随便", null)` 绕过工厂方法。

2. **Getter 方法名不符合 Jackson 默认约定。** record 生成的是 `code()`，Jackson 默认识别 `getCode()` 风格，需要额外配置 `JacksonAnnotationIntrospector` 或加模块才能正确序列化，增加复杂度。

3. **静态工厂方法可以写，但构造器私有化做不到**，所以工厂方法存在的意义被削弱了。

**适合的理由（了解即可）：**
- 如果你不在意构造器是否公开，只是想少写 Getter/equals/toString，record 确实更简洁。
- Jackson 2.12+ 加了 `jackson-module-parameter-names` 后可以正确处理 record。

**结论（背这一句）：** record 适合做"只读数据快照"，不适合做需要控制构造过程的响应封装类。`Result<T>` 有"构造器私有 + 静态工厂"的设计意图，用普通 class 更合适。

## 作业 1-6：覆盖一个默认 Bean（ObjectMapper）

> 这道题考的是 `@ConditionalOnMissingBean` 的工作原理，是理解自动配置"可覆盖"设计的核心题目。

---

### 一、先搞清楚"Bean 是怎么注册的"

Spring 容器里每一个 Bean 在实例化之前，都有一张"图纸"，叫 **BeanDefinition**。
它记录了：类名、作用域、构造参数、依赖谁、怎么初始化……

注册 Bean 有两种方式：

| 方式 | 谁在用 | 例子 |
|------|--------|------|
| `@Component` / `@Service` 等注解，靠 `@ComponentScan` 扫描发现 | 你自己写的 Bean | `@Service ProductServiceImpl` |
| `@Configuration` 类里的 `@Bean` 方法 | 框架自动配置 / 你自己的配置类 | `JacksonAutoConfiguration` 里的 `jacksonObjectMapper()` |

---

### 二、`@ConditionalOnMissingBean` 是什么

这是一个**条件注解**，挂在框架的 `@Bean` 方法上：

```java
// 框架源码（简化）
@AutoConfiguration
@ConditionalOnClass(ObjectMapper.class)      // classpath 上有 Jackson 才考虑
public class JacksonAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean                // ← 核心：容器里没有 ObjectMapper 时，才创建这个 Bean
    ObjectMapper jacksonObjectMapper() {
        return new ObjectMapper();
    }
}
```

**执行顺序：**

```
refreshContext 阶段
│
├─ ① 扫描你的代码（@ComponentScan）
│      → 发现你 @Configuration 类里的 @Bean ObjectMapper
│      → 注册为 BeanDefinition，名字叫 "customObjectMapper"（或你自己起的名字）
│
├─ ② 处理自动配置（@EnableAutoConfiguration）
│      → 读到 JacksonAutoConfiguration
│      → 检查 @ConditionalOnMissingBean(ObjectMapper.class)
│      → 容器里已经有 ObjectMapper 类型的 BeanDefinition 了（第①步注册的）
│      → 条件不满足 → 这个 @Bean 方法直接跳过，不注册
│
└─ ③ 实例化 Bean
       → 只实例化你的 ObjectMapper，框架那个根本不存在
```

**关键结论：** 从来没有"两个 ObjectMapper 争着注册"这件事，框架那个在登记阶段就被排除掉了。所以不报"Bean 重复定义"。

---

### 三、实际写一个自定义 ObjectMapper Bean

**在 `config/` 目录下新建配置类：**

```java
package com.study.mall.product.config;

import com.fasterxml.jackson.annotation.JsonInclude;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.fasterxml.jackson.databind.SerializationFeature;
import com.fasterxml.jackson.datatype.jsr310.JavaTimeModule;
import com.fasterxml.jackson.datatype.jsr310.ser.LocalDateTimeSerializer;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

import java.time.LocalDateTime;
import java.time.format.DateTimeFormatter;

@Configuration
public class JacksonConfig {

    private static final String DATE_TIME_FORMAT = "yyyy-MM-dd HH:mm:ss";

    @Bean
    public ObjectMapper objectMapper() {
        ObjectMapper mapper = new ObjectMapper();

        // ① 忽略 null 字段（不序列化 null）
        mapper.setSerializationInclusion(JsonInclude.Include.NON_NULL);

        // ② 处理 Java 8 时间类型（LocalDateTime 等）
        JavaTimeModule javaTimeModule = new JavaTimeModule();
        // 注册 LocalDateTime 序列化格式
        javaTimeModule.addSerializer(
            LocalDateTime.class,
            new LocalDateTimeSerializer(DateTimeFormatter.ofPattern(DATE_TIME_FORMAT))
        );
        mapper.registerModule(javaTimeModule);

        // ③ 禁用默认的时间戳序列化（不用 [2024,1,1,12,0,0] 这种数组格式）
        mapper.disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS);

        return mapper;
    }
}
```

> **注意**：如果你用的是 `java.util.Date`（老式日期），用下面的方式设置格式：
> ```java
> mapper.setDateFormat(new SimpleDateFormat("yyyy-MM-dd HH:mm:ss"));
> ```
> 推荐用 `LocalDateTime`（Java 8+），`Date` 是旧 API，不要用。

### 五、反向验证：如果框架没有 `@ConditionalOnMissingBean`

> 作业第 3 问：反向验证，如果框架那个 `@Bean` 方法上没有 `@ConditionalOnMissingBean`，会发生什么？

**会报这个错：**

```
APPLICATION FAILED TO START

The bean 'objectMapper', defined in class path resource
[...JacksonAutoConfiguration.class], could not be registered.
A bean with that name has already been defined in
[com.study.mall.product.config.JacksonConfig]
and overriding is disabled.

Action: Consider renaming one of the beans or enabling overriding by setting
spring.main.allow-bean-definition-overriding=true
```

**原因：**

没有 `@ConditionalOnMissingBean`，框架在注册自动配置时**不检查是否已有同类 Bean**，直接尝试再注册一个同名 Bean Definition。
Spring Boot 默认禁止 Bean Definition 覆盖（`allow-bean-definition-overriding=false`），所以直接报错启动失败。

**这个错误的完整逻辑：**

```
① 你的 @Bean objectMapper() 先注册     → BeanDefinition "objectMapper" 入库
② 框架的 @Bean jacksonObjectMapper()   → 也叫 "objectMapper"（Bean 名默认取方法名，
                                           Spring Boot 的命名策略会对齐到 "objectMapper"）
                                        → 发现已有同名 BeanDefinition
                                        → allow-bean-definition-overriding=false
                                        → 启动失败！
```

**如果强行开启 `allow-bean-definition-overriding=true`，会怎样？**

```
spring.main.allow-bean-definition-overriding=true
```

不报错了，但结果不确定：后注册的覆盖先注册的，框架的自动配置类注册顺序晚于你的 `@ComponentScan`，
所以**框架的 Bean 会把你的覆盖掉**，你的自定义配置等于白写。

**结论（一句话背下来）：**
`@ConditionalOnMissingBean` 是"用户优先"机制的实现：框架主动礼让，在登记阶段检查容器里是否已有同类 Bean，有则跳过自己，用户永远赢。

---

### 六、三道题的完整答案（复制进作业答案区）

**Q1：你的 Bean 和自动配置里的 ObjectMapper 冲突了吗？为什么没报"Bean 重复定义"？**

没有冲突。框架的 `JacksonAutoConfiguration` 里那个 `@Bean` 方法上挂了 `@ConditionalOnMissingBean(ObjectMapper.class)`，条件注解在处理自动配置阶段（`refreshContext` 的第 ② 步）被求值，发现容器里已经有 `ObjectMapper` 类型的 BeanDefinition（来自我的 `JacksonConfig`），条件不满足，该 `@Bean` 方法直接被跳过，根本不会注册。所以从始至终只有一个 ObjectMapper BeanDefinition，不存在冲突。

**Q2：重启后再看 `/actuator/beans`，`objectMapper` 的来源变了吗？**

变了。覆盖前 `resource` 字段指向 `JacksonAutoConfiguration`，覆盖后指向 `com.study.mall.product.config.JacksonConfig`，证明容器里的 `objectMapper` Bean 确实是我定义的那个。

**Q3：反向验证，如果框架那个 `@Bean` 方法上没有 `@ConditionalOnMissingBean`，会发生什么？**

会在启动时报 `BeanDefinitionOverrideException`：`The bean 'objectMapper' could not be registered... overriding is disabled`。原因是框架会无条件尝试注册同名 Bean，与我已注册的产生命名冲突。Spring Boot 默认 `allow-bean-definition-overriding=false`，直接启动失败。

### 七、速记版

```
ConditionalOnMissingBean 工作原理：
  你的 @Bean → 先扫描注册（ComponentScan 先于 AutoConfiguration）
  框架的 @Bean → 看条件 → 容器有同类型 Bean → 跳过 → 不注册
  结果：只有你的 Bean，不冲突，不报错

没有这个条件注解：
  → 两个同名 BeanDefinition → 覆盖被禁止 → 启动失败

验证方式：
  /actuator/beans 里看 objectMapper 的 resource 字段
  覆盖后变成你自己的配置类路径
```

## 依赖注入注解

> Spring 管理 Bean 的生命周期，你只需要告诉它"我要用某个 Bean"，它负责把实例塞给你。
> 这个过程叫**依赖注入（DI）**。

---

### 一、三种注入方式

#### 方式 1：字段注入（Field Injection）—— 不推荐

```java
@Service
public class OrderService {

    @Autowired                        // 直接注入到字段
    private ProductService productService;
}
```

**为什么不推荐：**
- 字段是 `private`，Spring 靠反射强行赋值，绕过了封装
- 没有 Spring 容器就没法实例化（写单测时很痛苦，没法 `new OrderService()` 然后手动传依赖）
- 字段不是 `final` 的，运行时可能被意外修改
- 隐藏了依赖关系，你看构造器就能知道这个类依赖什么，字段注入则要扫全类

---

#### 方式 2：Setter 注入 —— 可选依赖才用

```java
@Service
public class OrderService {

    private ProductService productService;

    @Autowired
    public void setProductService(ProductService productService) {
        this.productService = productService;
    }
}
```

**适用场景：** 可选依赖（这个 Bean 不一定存在，不注入也能运行）。
用 `@Autowired(required = false)` 表达"有就注入，没有拉倒"。

```java
@Autowired(required = false)
public void setMetricsService(MetricsService metricsService) {
    this.metricsService = metricsService;
}
```

---

#### 方式 3：构造器注入 —— 推荐，项目里统一用这个

```java
@Service
public class OrderService {

    private final ProductService productService;   // final！编译期保证不为 null
    private final InventoryService inventoryService;

    // Spring 发现只有一个构造器，自动注入，@Autowired 可以省略
    public OrderService(ProductService productService,
                        InventoryService inventoryService) {
        this.productService = productService;
        this.inventoryService = inventoryService;
    }
}
```

**为什么推荐：**
- 字段可以是 `final`，保证注入后不变
- 构造器签名就是依赖清单，一眼看出这个类依赖什么
- 单测时直接 `new OrderService(mockProduct, mockInventory)`，不需要 Spring 容器
- **能暴露循环依赖**：A 依赖 B，B 依赖 A，构造器注入会在启动时直接报错，而字段注入会悄悄用代理绕过去，留下隐患

> **只有一个构造器时，`@Autowired` 可以省略**（Spring 4.3+），代码更干净。

---

### 二、`@Autowired` vs `@Resource` vs `@Inject`

| 注解 | 来自哪里 | 默认匹配方式 | 指定 Bean 名 |
|------|---------|------------|------------|
| `@Autowired` | Spring 自己的 | **按类型**（type） | 配合 `@Qualifier("beanName")` |
| `@Resource` | Jakarta EE 标准 | **按名称**（name） | `@Resource(name = "beanName")` |
| `@Inject` | Jakarta EE 标准 | 按类型（同 `@Autowired`） | 配合 `@Named("beanName")` |

**实际项目里：** 用 `@Autowired` 就够了，`@Resource` 偶尔会见到，`@Inject` 基本不用。

---

### 三、同类型多个 Bean 时怎么办（最容易踩的坑）

场景：容器里有两个 `DataSource` Bean（主库 + 从库），注入时 Spring 懵了：

```
NoUniqueBeanDefinitionException:
No qualifying bean of type 'javax.sql.DataSource' available:
expected single matching bean but found 2: primaryDataSource, replicaDataSource
```

**解法一：`@Qualifier` 指定 Bean 名**

```java
@Service
public class OrderService {

    private final DataSource dataSource;

    public OrderService(@Qualifier("primaryDataSource") DataSource dataSource) {
        this.dataSource = dataSource;
    }
}
```

**解法二：`@Primary` 标记默认首选**

```java
@Bean
@Primary                          // 不加 @Qualifier 时，默认用这个
public DataSource primaryDataSource() { ... }

@Bean
public DataSource replicaDataSource() { ... }
```

**解法三：注入所有同类型 Bean（用 List 或 Map）**

```java
@Service
public class NotificationService {

    // 把容器里所有 MessageSender 实现都注入进来
    private final List<MessageSender> senders;

    public NotificationService(List<MessageSender> senders) {
        this.senders = senders;
    }

    public void send(String msg) {
        senders.forEach(s -> s.send(msg));   // 全部触发
    }
}
```

---

### 四、`@Value` —— 注入配置值

```java
@Service
public class PaymentService {

    @Value("${payment.timeout:5000}")    // 读配置，默认值 5000
    private int timeout;

    @Value("${payment.gateway.url}")     // 没有默认值，配置不存在则启动报错
    private String gatewayUrl;
}
```

**`application.properties` 里：**

```properties
payment.timeout=3000
payment.gateway.url=https://pay.example.com
```

**冒号后面是默认值：** `${key:defaultValue}`，配置不存在时用默认值，不报错。

> `@Value` 只能注入简单类型（String、int、boolean 等）。
> 一个类有很多配置项时，改用 `@ConfigurationProperties`（见下一节）。

---

### 五、`@ConfigurationProperties` —— 批量绑定配置

场景：支付配置有 5 个字段，不想写 5 个 `@Value`。

```properties
# application.properties
payment.timeout=3000
payment.gateway.url=https://pay.example.com
payment.retry-count=3
payment.enabled=true
```

```java
@ConfigurationProperties(prefix = "payment")   // 前缀统一，字段名自动对应
@Component                                      // 或者在 @Configuration 类上用 @EnableConfigurationProperties
public class PaymentProperties {

    private int timeout;
    private String gatewayUrl;      // properties 里 gateway.url → 驼峰 gatewayUrl，自动转换
    private int retryCount;
    private boolean enabled;

    // 需要 Getter + Setter（Spring 靠 Setter 绑定值）
    public int getTimeout() { return timeout; }
    public void setTimeout(int timeout) { this.timeout = timeout; }
    // ... 其他字段同理
}
```

**在需要用的地方注入这个 Properties 类：**

```java
@Service
public class PaymentService {

    private final PaymentProperties props;

    public PaymentService(PaymentProperties props) {
        this.props = props;
    }

    public void pay() {
        int timeout = props.getTimeout();   // 直接用
    }
}
```

**`@Value` vs `@ConfigurationProperties` 怎么选：**

| | `@Value` | `@ConfigurationProperties` |
|--|---------|--------------------------|
| 适合场景 | 1-2 个零散配置 | 一组相关配置 |
| 类型转换 | 手动，只支持简单类型 | 自动，支持 List、Map、Duration |
| IDE 提示 | ❌ | ✅（加 `spring-boot-configuration-processor` 后） |
| 可测试性 | 差（依赖 Spring 环境） | 好（可以直接 new 对象赋值测试） |

---

### 六、常见坑速查

#### 坑 1：注入的是 null，启动没报错

**原因：** 你自己 `new` 了这个对象，而不是从 Spring 容器里拿。

```java
// ❌ 错误：自己 new 出来的，Spring 不管它，里面的 @Autowired 字段全是 null
OrderService service = new OrderService();
service.doSomething();  // NullPointerException

// ✅ 正确：从容器里拿
@Autowired
private OrderService orderService;  // Spring 注入的，依赖都已经注入好了
```

---

#### 坑 2：循环依赖

A 的构造器需要 B，B 的构造器需要 A，Spring 没法先创建谁：

```
BeanCurrentlyInCreationException:
Error creating bean 'serviceA': Requested bean is currently in creation
```

**解法（按优先级）：**

1. **重新设计**：循环依赖通常是职责划分问题，A 和 B 互相依赖说明它们应该合并，或者抽出第三个类 C 承担公共逻辑。
2. 把其中一个改成 Setter 注入（Spring 可以先创建 Bean，再注入 Setter）。
3. 其中一个加 `@Lazy`（懒加载，第一次用到时才创建，打破循环）。

```java
public ServiceA(@Lazy ServiceB serviceB) {   // 注意：@Lazy 加在参数上
    this.serviceB = serviceB;
}
```

> 不要用 `spring.main.allow-circular-references=true` 强行关掉报错，这是掩盖设计问题。

---

#### 坑 3：`@Transactional` 自调用失效

同类里的方法 A 调方法 B，B 上的 `@Transactional` 不生效：

```java
@Service
public class OrderService {

    public void createOrder() {
        this.saveOrder();   // ❌ 直接调，绕过了 Spring 的代理，事务不生效
    }

    @Transactional
    public void saveOrder() { ... }
}
```

**原因：** Spring 的事务靠 AOP 代理实现，代理包在对象外面。`this.saveOrder()` 直接调内部方法，绕过了代理层。

**解法：** 把 `saveOrder` 拆到另一个 Bean 里，跨 Bean 调用才会经过代理。

---

#### 坑 4：`@Async` 同理，自调用也失效

和 `@Transactional` 一样的原因，异步方法被同类内部调用时不会异步执行。

---

#### 坑 5：注入接口还是实现类

```java
// ✅ 推荐：注入接口
private final ProductRepository productRepository;

// ❌ 不推荐：注入具体实现类
private final ProductRepositoryImpl productRepositoryImpl;
```

注入接口的好处：以后换实现（比如换成 Mock 实现做测试，或者换缓存实现），调用方代码不用改。

---

### 七、速记版

```
三种注入方式：
  字段注入    @Autowired 直接加字段上   → 不推荐，反射赋值，没法单测
  Setter 注入 @Autowired 加 Setter 上  → 可选依赖时用
  构造器注入  推荐，字段 final，依赖清晰，能暴露循环依赖

多个同类型 Bean 时：
  @Qualifier("beanName")   指定用哪个
  @Primary                 标记默认首选
  List<T> 注入             全部拿到

配置注入：
  @Value("${key:默认值}")  简单单个配置
  @ConfigurationProperties(prefix="xx")  一组配置，推荐

常见坑：
  自己 new 的对象，@Autowired 字段是 null
  循环依赖：重新设计 > @Lazy > Setter 注入
  @Transactional / @Async 自调用失效：因为绕过了代理
  注入接口，不注入实现类
```
