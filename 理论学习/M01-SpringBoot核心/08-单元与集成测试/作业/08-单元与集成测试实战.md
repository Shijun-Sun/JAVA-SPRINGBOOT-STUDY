## 一、背景设定

`product-service` 已经具备完整的 CRUD、配置绑定、统一响应、全局异常、分层边界、traceId 与访问日志。但目前测试只有一个上下文加载冒烟测试（`ProductServiceApplicationTests`）。

M01 模块的产出要求里写着"带 MockMvc 测试"。这一章就是把它补齐：给 `product-service` 建立一张**回归安全网**，覆盖 Service 逻辑、Web 层契约、真实链路，为 M02 换 MySQL 时"敢改"打底。

**版本关键点**：本项目是 Spring Boot 4.1，`@MockBean` 已被移除，一律用 `@MockitoBean`（`org.springframework.test.context.bean.override.mockito.MockitoBean`）。

### 任务一：ProductService 单元测试

> - 性质：正式交付
> - 实现位置：`homework/delivered/product-service/src/test/java/com/study/mall/product/service/ProductServiceTest.java`
> - 级别：必做
> - 是否阻塞推进：是
> - 前置交付：作业 02（构造器注入）、06（分层与 Service）
> - 验证方式：`./mvnw -o test -Dtest=ProductServiceTest` 全绿

不启动 Spring，用 Mockito 造假 `InMemoryProductRepository` 和 `ProductConfig`，`new` 出 `ProductService` 测其逻辑。至少覆盖以下用例：

1. `create`：SKU 已存在时抛 `ResourceConflictException`，且 `repository.save` 从未被调用（`verify(..., never())`）；
2. `create`：SKU 不存在时正常保存，返回的 `ProductVO` 字段与入参一致；
3. `getById`：id 不存在时抛 `ResourceNotFoundException`；
4. `list`：请求 `size` 超过 `product.pagination.max-size` 时被截断到上限（stub `productConfig.pagination()` 返回固定上限验证）；
5. `deleteById`：调用了 `repository.deleteById(id)`（`verify`）。

要求：

- 用 `@ExtendWith(MockitoExtension.class)` + `@Mock` + `@InjectMocks`；
- 断言统一用 AssertJ（`assertThat` / `assertThatThrownBy`）；
- 每个测试用 `@DisplayName` 写清中文意图。

**验收标准：**

- 5 个用例全部通过；
- 不启动任何 Spring 上下文（类上没有 `@SpringBootTest` / `@WebMvcTest`）；
- 冲突用例用 `verify(repository, never()).save(any())` 证明"短路"，而不是只断言异常。

### 任务二：ProductController Web 切片测试

> - 性质：正式交付
> - 实现位置：`homework/delivered/product-service/src/test/java/com/study/mall/product/controller/ProductControllerTest.java`
> - 级别：必做
> - 是否阻塞推进：是
> - 前置交付：任务一；作业 04（Web 层）、05（错误契约）
> - 验证方式：`./mvnw -o test -Dtest=ProductControllerTest` 全绿

**前置：Boot 4 依赖调整（本任务的第一步）。** 讲义 5.2b 讲过，Boot 4 把 `@WebMvcTest` / `@AutoConfigureMockMvc` 拆到了独立模块，`spring-boot-starter-test` 不再包含。product-service 当前 `pom.xml` 只有 `spring-boot-starter-test`，直接写 `@WebMvcTest` 会编译不过。先在 `pom.xml` 加上（版本由父 BOM 管理，任务三的 `@AutoConfigureMockMvc` 也依赖它）：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-webmvc-test</artifactId>
    <scope>test</scope>
</dependency>
```

> 这是本作业里唯一允许改动的 `pom.xml` 生产配置——它是完成模块"MockMvc 测试"产出的必要构建依赖，属于 delivered 的正当工程配置，不是为演示而加的无用依赖。

用 `@WebMvcTest(ProductController.class)` + `MockMvc`，`@MockitoBean` 顶替 `ProductService`（导入 `org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest`）。至少覆盖：

1. `GET /api/v1/products/{id}` 命中：mock 返回一个 `ProductVO`，断言 200 + `$.code=SUCCESS` + `$.data.name` 正确；
2. `GET /api/v1/products/{id}` 未命中：mock 抛 `ResourceNotFoundException`，断言 404 + `$.code=RESOURCE_NOT_FOUND`（证明 `@RestControllerAdvice` 在切片里生效）；
3. `POST /api/v1/products` 成功：合法 body，断言 201 Created + 响应体结构；
4. `POST /api/v1/products` 校验失败：`name` 为空 / `price` 为 0 / `sku` 不合法（任选并覆盖），断言 400 + `$.code=VALIDATION_FAILED`，且 `$.data` 里有对应字段错误；
5. `DELETE /api/v1/products/{id}`：断言 204 No Content。

要求：

- 请求体用注入的 `ObjectMapper` 序列化对象生成，不手拼易错的 JSON 字符串；
- 断言要测响应体结构（`jsonPath`），不能只测 status；
- Service 的行为一律用 `when(...).thenReturn(...)` / `doThrow(...)` 打桩，不依赖真实 Service。

**验收标准：**

- 5 类用例通过；
- 校验失败用例确实走的是 `MethodArgumentNotValidException` → `VALIDATION_FAILED` 契约；
- 404 用例证明全局异常处理在 `@WebMvcTest` 切片内生效。

### 任务三：端到端集成测试（真实链路）

> - 性质：正式交付
> - 实现位置：`homework/delivered/product-service/src/test/java/com/study/mall/product/ProductApiIntegrationTest.java`
> - 级别：必做
> - 是否阻塞推进：是
> - 前置交付：任务一、二；作业 03（配置/测试 profile）、07（traceId）
> - 验证方式：`./mvnw -o test -Dtest=ProductApiIntegrationTest` 全绿

用 `@SpringBootTest` + `@AutoConfigureMockMvc` 启动完整上下文（依赖 `src/test/resources/application.yml` 提供的测试配置），测切片测不到的真实链路：

1. `GET /api/v1/products` 返回 200，且**响应头存在 `X-Trace-Id`**（证明第 07 章的 Filter 真的挂上链路，这是切片测试测不到的）；
2. 传入自定义 `X-Trace-Id` 头，响应头回传的是同一个值（复用而非重新生成）；
3. `GET /api/v1/products/99999`（真实不存在）端到端返回 404 + `$.code=RESOURCE_NOT_FOUND`（错误契约经真实链路）。

要求：

- 说明为什么这些用例必须放集成测试、切片测试测不到（写在测试类注释或交付说明里）；
- 集成测试用例保持少而精，不要把任务一/二已覆盖的逻辑在这里重测一遍。

**验收标准：**

- 3 个用例通过；
- traceId 相关用例真实断言了响应头，而不是断言日志；
- 不因缺少 profile 而启动失败（正确依赖测试配置）。

## 三、进阶任务（按需选做）

### 任务五：`@MockitoBean` vs 手工 mock 对比实验

> - 性质：知识点实验
> - 实现位置：`homework/experimental/testing-lab/`（出题时提供最小脚手架）
> - 级别：进阶
> - 是否阻塞推进：否
> - 验证方式：两种写法都能跑通，能说清区别

在实验脚手架里，用两种方式测同一个简单 Controller：

1. 纯单元：`new Controller(mock(Service.class))`，直接调方法，不启动 Spring；
2. 切片：`@WebMvcTest` + `@MockitoBean`。

回答：

1. 两种方式各能测到什么、测不到什么（路径映射？校验？序列化？）？
2. `@MockitoBean` 把 mock 放进 Spring 上下文，纯单元的 mock 没进上下文——这个区别导致了什么？
3. 什么场景下纯单元就够、什么场景必须上切片？

### 任务六：AssertJ 与 MockMvcTester 体验

> - 性质：知识点实验

> - 级别：进阶
> - 是否阻塞推进：否
> - 验证方式：能跑通并对比可读性

用 AssertJ 的链式断言（`extracting`、`satisfies`、集合断言）改写任务一的部分断言，体会可读性差异。若有余力，试用 Spring 6.2+ 的 `MockMvcTester`（AssertJ 风格的 MockMvc）改写一个切片用例，对比它与经典 `andExpect` 链的差异。
