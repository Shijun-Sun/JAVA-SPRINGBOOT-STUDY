# M01-08 · 单元测试与集成测试：给 product-service 建立回归安全网

> **预计阅读时间**：100～130 分钟
> **配套作业**：[作业 08 · 单元与集成测试实战](../作业/08-单元与集成测试实战.md)

> **本章目标**
> - 说清单元测试、切片测试、集成测试各自测什么、启动多少 Spring、跑多快，能为一段代码选对测试层级

> - 知道 Spring Boot 4 里 `@MockBean` 已被移除，正确用 `@MockitoBean`

## 一、为什么要写测试：不是为了覆盖率，是为了敢改

`product-service` 现在有 CRUD、配置绑定、全局异常、分层边界、traceId 与访问日志。往后 M02 要把内存存储换成 MySQL，M03 要加缓存，M06 要接消息队列——每一步都在**改动已有代码**。

没有测试时，改动的验证方式是"手动 curl 一遍，看着像对的"。这有三个问题：

1. **不可复现**：今天验过，明天别人改了别的地方，没人会再 curl 一遍；
2. **覆盖不全**：手动只会测想得到的正常路径，边界和异常路径全靠运气；
3. **回归无感**：改 A 功能顺手改坏了 B 功能，要等到线上才发现。

测试的真正价值是**回归安全网**：把"这段代码应该有的行为"写成可自动执行的断言，之后每次改动都重跑一遍，改坏了立刻红。**能安心重构、能安心升级依赖，靠的就是这张网。** 覆盖率只是副产品，不是目的。

对架构师而言还有一层：**测试是最诚实的设计反馈**。一段代码难测，往往是因为它耦合太重、职责太杂。第 06 章我们把 Controller、Service、Repository 分了层，把 Entity/DTO/VO 分了边界——现在正好用测试验证这个设计"可测"。

## 二、测试金字塔：三个层级测什么 ⭐

```
        ╱╲          少量  集成测试（@SpringBootTest）
       ╱  ╲               启动整个上下文，测多个组件协作 + 真实链路
      ╱────╲
     ╱      ╲       适量  切片测试（@WebMvcTest 等）
    ╱        ╲            只启动某一层，测该层与框架的集成
   ╱──────────╲
  ╱            ╲    大量  单元测试（纯 JUnit + Mockito）
 ╱──────────────╲        不启动 Spring，测单个类的逻辑，毫秒级
```

| 层级 | 启动 Spring | 速度 | 测什么 | 依赖怎么处理 |
|---|---|---|---|---|
| 单元测试 | 否 | 毫秒 | 单个类的业务逻辑、分支、边界 | 用 Mockito 造假（mock） |
| 切片测试 | 部分（只某一层） | 百毫秒 | 该层与框架的集成（参数绑定、序列化、状态码） | 该层之外用 `@MockitoBean` 造假 |
| 集成测试 | 全部 | 秒级 | 多组件协作、真实请求链路、配置是否兜得住 | 尽量用真实组件 |

选层原则：**能用低层级测清楚的，就不要用高层级。** 一条 Service 的分支逻辑，用单元测试一个方法几毫秒就测完；非要用 `@SpringBootTest` 启动整个应用去测，慢几百倍且噪声大。金字塔"底大顶小"就是这个意思：绝大多数行为用最快的单元测试覆盖，少量关键链路用集成测试兜底。

## 三、测试的三件套：JUnit 5 + AssertJ + Mockito

`spring-boot-starter-test` 已经把这三个带进来了（`pom.xml` 里的 test 依赖），不用单独引。

### 3.1 JUnit 5：测试的骨架

```java
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.DisplayName;

class SampleTest {

    @Test
    @DisplayName("两数相加返回和")   // 报告里显示中文描述，比方法名可读
    void add_returnsSum() {
        int result = 1 + 2;
        // 断言见下文
    }
}
```

常用注解：`@Test`（一个测试）、`@BeforeEach`（每个测试前跑，初始化）、`@AfterEach`（每个测试后跑，清理）、`@DisplayName`（可读描述）、`@Nested`（把相关测试分组）。

> 注意：JUnit 5 的测试类和方法**不需要 public**，包级可见即可。

### 3.2 AssertJ：流式断言，读起来像句子

```java
import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

assertThat(result).isEqualTo(3);
assertThat(list).hasSize(2).contains("a");
assertThat(vo.name()).isEqualTo("iPhone");

// 断言抛异常
assertThatThrownBy(() -> service.getById(999L))
        .isInstanceOf(ResourceNotFoundException.class)
        .hasMessageContaining("不存在");
```

比起 JUnit 自带的 `assertEquals(expected, actual)`（参数顺序容易记反），AssertJ 的 `assertThat(actual).isEqualTo(expected)` 更接近自然语序，链式断言也更清晰。本课程统一用 AssertJ。

### 3.3 Mockito：给依赖造替身

单元测试要"只测一个类"，就得把它依赖的其它类换成**可控的假货**（测试替身）。Mockito 负责造这种假货：

```java
import static org.mockito.Mockito.*;
import static org.mockito.ArgumentMatchers.any;

// 造一个假的 repository
InMemoryProductRepository repository = mock(InMemoryProductRepository.class);

// 规定它的行为：当 existsBySku("SKU-1") 被调用，返回 true
when(repository.existsBySku("SKU-1")).thenReturn(true);

// 用它调被测方法……然后验证交互
verify(repository).save(any(ProductEntity.class));   // 验证 save 被调用过
verify(repository, never()).save(any());             // 验证 save 从没被调用
```

三个核心动作：

- **stub（打桩）**：`when(...).thenReturn(...)` 规定假货被调用时返回什么；
- **verify（验证交互）**：`verify(...)` 检查假货的某方法是否按预期被调用；
- **argument matcher（参数匹配）**：`any()`、`eq()` 等，用于放宽或精确匹配调用参数。

> 为什么要 mock repository？因为单元测试 `ProductService` 时，我们只关心"Service 的逻辑对不对"，不关心 repository 真的存没存进去。把 repository 换成可控假货，就能精确构造"SKU 已存在""商品不存在"这些场景，而不用真的往存储里塞数据。

## 四、第一层：Service 单元测试（不启动 Spring）

`ProductService` 依赖 `InMemoryProductRepository` 和 `ProductConfig`。单元测试里，这两个都用 Mockito 造假，`ProductService` 自己 `new` 出来——**完全不碰 Spring 容器**，所以极快。

### 4.1 用 `@ExtendWith(MockitoExtension.class)` 管理 mock

```java
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import static org.assertj.core.api.Assertions.*;
import static org.mockito.Mockito.*;

@ExtendWith(MockitoExtension.class)   // 让 Mockito 处理 @Mock / @InjectMocks
class ProductServiceTest {

    @Mock
    InMemoryProductRepository repository;   // 造假的依赖

    @Mock
    ProductConfig productConfig;

    @InjectMocks
    ProductService productService;          // 把上面的 mock 注进来的被测对象

    @Test
    @DisplayName("创建商品时 SKU 已存在，抛 ResourceConflictException")
    void create_whenSkuExists_throwsConflict() {
        // given：打桩，让 repository 说"这个 SKU 已存在"
        when(repository.existsBySku("SKU-1")).thenReturn(true);
        var request = new CreateProductRequest("iPhone", "SKU-1",
                new BigDecimal("5999.00"), "手机");

        // when + then：断言抛对异常，且从没调用 save
        assertThatThrownBy(() -> productService.create(request))
                .isInstanceOf(ResourceConflictException.class)
                .hasMessageContaining("SKU 已存在");
        verify(repository, never()).save(any());
    }
}
```

- `@Mock` 标记的字段由 Mockito 造假；
- `@InjectMocks` 让 Mockito 把这些 mock 通过构造器注入到被测对象（回顾第 02 章：`ProductService` 是构造器注入，所以这里能注进去）；
- `@ExtendWith(MockitoExtension.class)` 让这套注解生效。

### 4.2 单元测试擅长测什么

- **分支**：SKU 存在 / 不存在；商品存在 / 不存在；
- **边界**：`list()` 里 `size` 超过 `product.pagination.max-size` 时被截断——这里就要 stub `productConfig.pagination()` 返回一个固定上限，验证截断逻辑；
- **异常**：`getById(不存在的 id)` 抛 `ResourceNotFoundException`；
- **交互**：`deleteById` 是否调用了 `repository.deleteById`。

这些都不需要真实的 Spring 环境或 HTTP，纯逻辑，最适合放单元测试。

> ⚠️ `MockitoExtension` 默认是 **strict** 模式：打了桩却没用到会报 `UnnecessaryStubbingException`。这是好事——它逼你只写用得到的桩。某个测试里确实不需要某个桩时，就别打。

## 五、第二层：Web 切片测试 `@WebMvcTest` + MockMvc

Service 逻辑测完了，但 Controller 这一层有一堆"框架的活"没测：路径映射对不对、`@Validated` 校验触没触发、返回值被 Jackson 序列化成什么 JSON、状态码是不是 201/204。这些用纯单元测试测不了（它们依赖 Spring MVC），用全量 `@SpringBootTest` 又太重。**切片测试**正好卡在中间。

### 5.1 `@WebMvcTest` 只加载 Web 层

```java
import org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest;   // Boot 4 新包路径，见 5.2
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.test.context.bean.override.mockito.MockitoBean;
import org.springframework.test.web.servlet.MockMvc;

import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.*;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.*;

@WebMvcTest(ProductController.class)     // 只加载这个 Controller + MVC 基础设施
class ProductControllerTest {

    @Autowired
    MockMvc mockMvc;                     // 不启真实 Tomcat，直接调 DispatcherServlet

    @MockitoBean
    ProductService productService;       // Controller 依赖的 Service 用 mock 顶替

    @Test
    @DisplayName("GET /api/v1/products/{id} 命中，返回 200 和统一响应体")
    void findById_found_returns200() throws Exception {
        var vo = new ProductVO(1L, "iPhone", "SKU-1",
                new BigDecimal("5999.00"), "手机", LocalDateTime.now());
        when(productService.getById(1L)).thenReturn(vo);

        mockMvc.perform(get("/api/v1/products/1"))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.code").value("SUCCESS"))
                .andExpect(jsonPath("$.data.name").value("iPhone"));
    }
}
```

要点：

- `@WebMvcTest(ProductController.class)` 只加载 Web 相关的 Bean（Controller、`@RestControllerAdvice`、Jackson、校验器等），**不加载 Service、Repository、你的 `@Configuration`**。所以速度比 `@SpringBootTest` 快很多。
- `MockMvc` 是一个"假的 HTTP 客户端"：它不启动真实端口，直接把请求送进 `DispatcherServlet`，跑完整个 MVC 流程（映射、绑定、校验、序列化、异常处理），再把结果给你断言。
- Controller 依赖的 `ProductService` 在这个切片里不存在，用 `@MockitoBean` 放一个 mock 进上下文顶替。

### 5.2 ⚠️ 版本关键点：Spring Boot 4 用 `@MockitoBean`，不是 `@MockBean`

这是个必须记住的版本变化：

- 老教程和 Boot 3.3 及以前用 `@MockBean`（`org.springframework.boot.test.mock.mockito.MockBean`）；
- Spring Boot **3.4** 起 `@MockBean` 被**弃用**，改用 Spring Framework 6.2 的 `@MockitoBean`（`org.springframework.test.context.bean.override.mockito.MockitoBean`）；
- Spring Boot **4.0** 起 `@MockBean` 已被**移除**——本项目是 Boot 4.1，写 `@MockBean` 直接编译不过。

所以本课程一律用 `@MockitoBean` / `@MockitoSpyBean`。看到老资料写 `@MockBean` 时，脑子里自动替换。
> 来源：`@MockBean` 弃用于 Spring Boot 3.4、移除于 4.0，替代为 Spring Framework 6.2 的 `@MockitoBean`（[Spring 官方文档](https://docs.spring.io/spring-framework/reference/testing/annotations/integration-spring/annotation-mockitobean.html)）。Content was rephrased for compliance with licensing restrictions.

### 5.2b 版本关键点二：Boot 4 把 Web 切片测试拆成了独立模块 ⚠️

还有一个更隐蔽的坑，本机实测确认（Boot 4.1.0）：

- Boot 3.x：`@WebMvcTest` / `@AutoConfigureMockMvc` 在 `spring-boot-test-autoconfigure` 里，包路径是 `org.springframework.boot.test.autoconfigure.web.servlet`，`spring-boot-starter-test` 直接带；
- Boot 4.x：它们被拆到**独立模块** `spring-boot-webmvc-test`，包路径变为 **`org.springframework.boot.webmvc.test.autoconfigure`**，而且 **`spring-boot-starter-test` 不再包含它**。

后果：在 Boot 4 里直接写 `@WebMvcTest`，会遇到"程序包 `org.springframework.boot.test.autoconfigure.web.servlet` 不存在 / 找不到符号 WebMvcTest"。要用切片测试，必须：

1. 在 `pom.xml` 显式加依赖（版本由父 BOM 管理，不写版本号）：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-webmvc-test</artifactId>
    <scope>test</scope>
</dependency>
```

2. 用新包路径导入：`import org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest;`

`MockMvc` 本身、`MockMvcRequestBuilders`、`MockMvcResultMatchers`（`org.springframework.test.web.servlet.*`）以及 `@MockitoBean` 仍在 `spring-test` 里，位置不变——变的只是切片注解所在的模块和包。这就是"版本迁移是架构师必修课"的一个真实切片：升级大版本时，模块重组会让老代码编译不过，得照着新结构调整。

### 5.3 切片测试擅长测什么

- **状态码语义**：创建返回 201、删除返回 204、查询返回 200；
- **校验触发**：POST 一个 `name` 为空的请求，`@Validated` 应触发 400，且响应体是 `VALIDATION_FAILED` 契约；
- **序列化契约**：返回体是不是 `{code, message, data}` 结构；
- **异常映射**：Service 抛 `ResourceNotFoundException`（用 mock 制造），经 `GlobalExceptionHandler` 后是不是 404 + `RESOURCE_NOT_FOUND`。

注意：`@WebMvcTest` 会加载 `@RestControllerAdvice`，所以第 05 章的错误契约在这一层就能测。

### 5.4 构造请求体

POST/PUT 要带 JSON body。手写 JSON 字符串也行，但用 `ObjectMapper` 序列化对象更稳：

```java
@Autowired ObjectMapper objectMapper;   // @WebMvcTest 会自动装配

mockMvc.perform(post("/api/v1/products")
        .contentType(MediaType.APPLICATION_JSON)
        .content(objectMapper.writeValueAsString(request)))
    .andExpect(status().isCreated());
```

## 六、第三层：集成测试 `@SpringBootTest`（真实链路兜底）

切片测试把每层单独测了，但有些东西只有"全部组件一起跑"才测得出来：

- traceId 的 Filter、访问日志的 Interceptor 是不是真的挂上了链路（切片测试默认不加载自定义 Filter/Interceptor）；
- 配置绑定（`ProductConfig`）在真实上下文里能不能兜住；
- 从 HTTP 请求进来到统一响应出去，整条链路串起来对不对。

这就是集成测试的活。

### 6.1 两种 `@SpringBootTest` 形态

```java
// 形态一：不启动真实端口，用 MockMvc 打 DispatcherServlet（推荐，快且够用）
@SpringBootTest
@AutoConfigureMockMvc
@ActiveProfiles("test")          // 用 test profile，加载 src/test/resources/application.yml
class ProductApiIntegrationTest {

    @Autowired MockMvc mockMvc;

    @Test
    void list_returnsTraceIdHeader() throws Exception {
        mockMvc.perform(get("/api/v1/products"))
                .andExpect(status().isOk())
                .andExpect(header().exists("X-Trace-Id"));   // 验证第07章的 traceId 真的挂上了
    }
}

// 形态二：启动真实端口，用 TestRestTemplate / WebTestClient 走真实 TCP（更真，更慢）
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class ProductApiHttpTest {
    @Autowired TestRestTemplate restTemplate;
    // restTemplate.getForEntity("/api/v1/products", ...) 走真实 HTTP
}
```

绝大多数场景形态一就够了：它加载完整上下文（所以 Filter/Interceptor/Config 都在），但用 MockMvc 省掉真实网络开销。只有要测"连接超时、真实 HTTP 头行为"这种网络层细节，才用形态二。

> 注意：`@AutoConfigureMockMvc` 和 `@WebMvcTest` 一样，在 Boot 4 里也来自 `spring-boot-webmvc-test` 模块、`org.springframework.boot.webmvc.test.autoconfigure` 包（见 5.2b）。用 `@SpringBootTest + @AutoConfigureMockMvc` 同样要引入该依赖。

### 6.2 呼应第 03 章：集成测试的配置从哪来

回顾第 03 章的设计：主 `application.yml` 只放公共段，完整的 `product.*` 在 dev/prod profile。测试**不应该依赖某个真实环境的 profile**（否则改了 dev 配置就可能测挂）。所以项目里已经有一份专供测试的 `src/test/resources/application.yml`，提供完整的 `product.*`。

- 用 `@ActiveProfiles("test")` 或直接靠 `src/test/resources/application.yml` 覆盖，让集成测试能启动上下文；
- 这也解释了为什么第 07 章直接 `java -jar` 不带 profile 会启动失败，而 `ProductServiceApplicationTests` 能通过——测试用的是这份测试专用配置。

### 6.3 集成测试擅长测什么

- **traceId 响应头存在**（第 07 章产出的链路能力）；
- **错误契约端到端**：真实请求一个不存在的 id，返回 404 + `RESOURCE_NOT_FOUND`（第 05 章契约，经真实链路）；
- **冒烟**：应用上下文能正常加载（`ProductServiceApplicationTests` 已经在做这件事）。

> 集成测试要"少而精"。每个 `@SpringBootTest` 都要启动完整上下文，很慢。只挑那些"必须全组件在场才测得出"的关键链路放这一层，其余下沉到切片和单元。

## 七、上下文缓存：为什么测试第一个慢、后面快

`@SpringBootTest` / `@WebMvcTest` 启动的 Spring 上下文会被 **缓存并复用**：只要测试类要求的上下文配置（profile、`@MockitoBean` 组合、切片类型等）完全相同，Spring 就复用同一个已启动的上下文，不重复启动。

这带来一个实践准则：**尽量让测试共享同一套上下文配置**。每换一种配置组合（比如东一个 `@ActiveProfiles("test")`、西一个 `@ActiveProfiles("dev")`，或每个测试类 mock 不同的 Bean），Spring 就得**新建并缓存一个上下文**，测试套件整体变慢。配置越统一，缓存命中越高，跑得越快。

## 八、几个常见坑 ⚠️

| 坑 | 现象 | 正确做法 |
|---|---|---|
| Boot 4 里写 `@MockBean` | 编译报错，找不到符号 | 用 `@MockitoBean` |
| Boot 4 里直接用 `@WebMvcTest` | 包不存在 / 找不到符号 WebMvcTest | 加 `spring-boot-webmvc-test` 依赖，从新包 `...webmvc.test.autoconfigure` 导入 |
| 用 `@SpringBootTest` 测纯逻辑 | 套件越来越慢 | 下沉到单元测试 |
| `@WebMvcTest` 里没 mock Service | 上下文启动失败，找不到 Service Bean | 用 `@MockitoBean` 顶替 Controller 的依赖 |
| 期望 `@WebMvcTest` 里 traceId 生效 | 响应头没有 `X-Trace-Id` | 切片默认不加载自定义 Filter，traceId 要放 `@SpringBootTest` 测 |
| 测试依赖 dev/prod profile | 改环境配置就测挂 | 用 `src/test/resources/application.yml` 提供测试专用配置 |
| Mockito strict 报 UnnecessaryStubbing | 打了桩没用到 | 删掉没用的桩，或该测试确实不需要它 |
| 断言只测 status，不测 body | 契约改了测试不红 | 关键接口要断言响应体结构（`jsonPath`） |

---

## 九、小结

| 知识点 | 记住这一句 |
|---|---|
| 测试的价值 | 回归安全网：让你敢改、敢升级、敢重构 |
| 测试金字塔 | 单元多、切片适量、集成少；能低层测清就不上高层 |
| 单元测试 | 不启动 Spring，Mockito 造假依赖，测单类逻辑，毫秒级 |
| 切片测试 | `@WebMvcTest` + MockMvc，只加载 Web 层，测映射/校验/序列化/状态码 |
| 集成测试 | `@SpringBootTest`，全上下文，测真实链路（traceId、错误契约端到端） |
| 版本关键点 | Boot 4 移除 `@MockBean`，用 `@MockitoBean` |
| mock 三动作 | stub(when/thenReturn)、verify、argument matcher |
| 配置来源 | 集成测试用 `src/test/resources/application.yml`，不依赖 dev/prod |
| 上下文缓存 | 配置越统一，缓存命中越高，套件越快 |
