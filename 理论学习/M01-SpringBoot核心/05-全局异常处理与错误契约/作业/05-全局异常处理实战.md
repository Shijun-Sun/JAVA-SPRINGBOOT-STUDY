## 一、背景设定

作业 04 完成后，`product-service` 可以处理正常的商品 CRUD，但错误路径还是一片混乱：

- 传入 `price: -1` 得到 400 但 body 为空（没有字段级错误信息）；
- 重复 SKU 创建得到 500（`IllegalArgumentException` 未处理）；
- 查询不存在的商品靠 Controller 里的模板代码返回 404，每个查询方法都要复制一遍；
- 传入格式错误的 JSON（比如 `"price": "abc"`）得到什么，客户端完全不知道。

本章的目标是用一个全局异常处理器把上面所有情况统一处理，让客户端永远拿到格式一致的 `Result<T>` 响应。

## 二、必做任务

### 任务一：建立业务异常体系 ⭐

在 `common/exception/` 包下创建业务异常基类和三个子类。

**`BusinessException`**（基类）：

```
字段：
  String code          // 业务错误码，如 "PRODUCT_NOT_FOUND"
  HttpStatus status    // 对应 HTTP 状态码

构造器：(String code, String message, HttpStatus status)
getter：getCode()、getStatus()
继承：RuntimeException
```

**三个子类**：

| 类名 | 状态码 | 典型用途 |
|---|---|---|
| `ResourceNotFoundException` | 404 | 资源不存在 |
| `ResourceConflictException` | 409 | 业务冲突（SKU 重复等） |
| `InvalidBusinessArgumentException` | 422 | 格式合法但语义非法 |

`ResourceNotFoundException` 的构造器要接受资源名和 ID，自动拼装 `code` 和 `message`：

```java
// 使用方式
throw new ResourceNotFoundException("商品", 42L);
// → code = "PRODUCT_NOT_FOUND"（或 "RESOURCE_NOT_FOUND"，命名规则自己选，保持一致）
// → message = "商品 不存在：42"
```

要求：

1. 子类构造器尽量简洁，把 `code`、`status` 封装进去，不让调用方传；
2. 不在异常类里注入任何 Spring Bean 或调用数据库；
3. 异常类本身不加 `@ResponseStatus`，状态码由全局处理器从 `getStatus()` 取。

**验收标准：**

- 四个类编译通过；
- `BusinessException` 是 `RuntimeException` 的子类；
- 三个子类在 Service 层可以直接 `throw new XxxException(...)` 使用。

### 任务二：升级 Service 层，替换粗糙的异常抛出

把第 04 章 Service 层里的 `IllegalArgumentException` 和 `NoSuchElementException` 替换为对应的业务异常子类。

**`ProductService` 需要修改的地方：**

1. `create` 方法：SKU 重复时抛 `ResourceConflictException`，错误码 `PRODUCT_SKU_CONFLICT`；
2. `findById` 保持返回 `Optional<ProductVO>`（给 Controller 灵活性）；
3. 新增 `getById(Long id)` 方法：找不到时抛 `ResourceNotFoundException`，返回 `ProductVO`（不是 Optional）；
4. `update` 方法：找不到时抛 `ResourceNotFoundException`；
5. `deleteById` 保持幂等行为（找不到时不抛异常，直接忽略）。

**验收标准：**

- Service 层没有 `IllegalArgumentException`、`NoSuchElementException`；
- 异常消息包含足够的上下文信息（资源名、ID、重复的 SKU 值等）；
- Service 没有引入任何 `jakarta.servlet` 或 Spring Web 类。

---

### 任务三：实现全局异常处理器 ⭐

在 `common/exception/` 包下新建 `GlobalExceptionHandler`，加 `@RestControllerAdvice` 注解。

**必须实现的处理器方法（按优先级从高到低排列）：**

| 处理器 | 捕获异常 | 响应状态码 | 响应体 |
|---|---|---|---|
| 校验失败 | `MethodArgumentNotValidException` | 400 | `Result<Map<String,String>>`，`data` 为字段名→错误信息映射 |
| 约束违反 | `ConstraintViolationException` | 400 | 同上 |
| JSON 格式错误 | `HttpMessageNotReadableException` | 400 | `Result<Void>`，`code = "INVALID_FORMAT"` |
| 业务异常 | `BusinessException` | 动态（从 `ex.getStatus()` 取） | `Result<Void>` |
| 兜底 | `Exception` | 500 | `Result<Void>`，`code = "INTERNAL_ERROR"`，不暴露 `ex.getMessage()` |

要求：

1. 校验失败处理器（前两个）需要提取**字段级**错误，`data` 中每个 key 是字段名，value 是 message；
2. 业务异常处理器用 `ResponseEntity` 而不是 `@ResponseStatus`，因为状态码是动态的；
3. 兜底处理器必须打 `ERROR` 级别完整日志（含堆栈），日志内容包含请求方法和路径；
4. 兜底处理器不把 `ex.getMessage()` 返回给客户端；
5. 四个"已知"处理器（非兜底）按情况选择 `@ResponseStatus` 或 `ResponseEntity`，逻辑写在注释里；
6. 同时处理两种校验异常——不能只写其中一个。

**验收标准：**

- 传入非法入参时响应包含字段级错误 Map，不再是 400 空 body；
- 重复 SKU 时响应是 409，不再是 500；
- 兜底处理器触发时日志有 ERROR 级别条目；
- 所有错误响应都是 `Result<T>` 格式，没有 Spring 默认的 `{"timestamp":...,"error":...}` 格式混入。

---

### 任务四：升级 `Result<T>`

在作业 04 升级的基础上，确认 `Result` 支持以下四个工厂方法：

```java
Result.ok(T data)                          // 成功，有数据
Result.ok()                                // 成功，无数据
Result.fail(String code, String message)   // 失败，无详情
Result.fail(String code, String message, T data)  // 失败，有详情（校验错误 Map 用这个）
```

同时确认：

1. `@JsonInclude(JsonInclude.Include.NON_NULL)` 已加，`data` 为 null 时不出现在 JSON；
2. `code` 字段类型是 `String`，不是 `int`；
3. 使用 `record` 实现，不用 `class` + Lombok。

**验收标准：**

- `GET /api/ping` 响应：`{"code":"SUCCESS","message":"ok","data":"pong"}`
- `GET /api/config-info` 响应中无 `"data":null` 字样（若没有数据字段）
- 校验失败时 `data` 字段出现且为字段→错误信息的 Map

### 任务五：重构 Controller，移除错误处理模板代码 ⭐

有了全局异常处理器，`ProductController` 里手动处理 404 的模板代码可以清除。

**修改要求：**

1. `findById` 方法改用 `productService.getById(id)`（抛异常版本），直接返回 `Result<ProductVO>`，不再返回 `ResponseEntity`；
2. `update` 方法同样改用直接调用，找不到时由 Service 抛异常，Controller 不处理；
3. 检查 Controller 中是否还有 `try-catch`、`if == null`、手动判断 404 的逻辑，全部移除；
4. Controller 只保留：接收参数 → 调用 Service → 包装 `Result` → 返回。

**修改前后对比（仅用于理解，不要把注释提交进代码）：**

```java
// 修改前
@GetMapping("/{id}")
public ResponseEntity<Result<ProductVO>> findById(@PathVariable Long id) {
    return productService.findById(id)
            .map(vo -> ResponseEntity.ok(Result.ok(vo)))
            .orElse(ResponseEntity.status(404)
                    .body(Result.fail("PRODUCT_NOT_FOUND", "商品不存在：" + id)));
}

// 修改后
@GetMapping("/{id}")
public Result<ProductVO> findById(@PathVariable Long id) {
    return Result.ok(productService.getById(id));
}
```

**验收标准：**

- `ProductController` 里没有 `ResponseEntity`（DELETE 方法本来就是 `void`，不受影响）；
- 查询不存在商品仍然返回 404 + 正确的 `Result` 格式（由全局处理器处理）；
- Controller 代码量明显减少，每个方法只有 1～2 行核心逻辑。


```bash
# 预期：200，{"code":"SUCCESS","message":"ok","data":{...}}

# 11. 确认响应格式统一：成功和失败的 code、message、data 结构一致
```

- 场景二：两个请求返回 400，`code = "INVALID_FORMAT"`；

## 三、进阶任务（按需选做）

### 任务七：`MethodArgumentTypeMismatchException` 处理

当路径变量类型转换失败时（例如 `GET /api/v1/products/abc`，`abc` 无法转为 `Long`），Spring 默认返回 400 空 body。

要求：

1. 在全局处理器里显式处理 `MethodArgumentTypeMismatchException`；
2. 响应体为 `Result<Void>`，`code = "INVALID_PATH_VARIABLE"`，`message` 指明是哪个参数、期望什么类型；
3. 验证：`GET /api/v1/products/abc` 返回 400 + 有意义的 `Result` body。

**验收标准：**

- 路径变量类型错误有对应的结构化响应，不再是 400 空 body。

### 任务八：`MissingServletRequestParameterException` 处理

当必填的 `@RequestParam` 未传时（`required = true`，默认值），Spring 默认返回 400。

要求：

1. 在全局处理器里显式处理 `MissingServletRequestParameterException`；
2. 响应指明缺少哪个参数名；
3. 结合任务七，验证路径变量和查询参数两种 400 响应格式一致。

### 任务九：`HttpRequestMethodNotSupportedException` 处理

当请求方法不匹配时（例如 `DELETE /api/v1/products` 而没有对应路由），Spring 默认返回 405。

要求：

1. 在全局处理器里处理 `HttpRequestMethodNotSupportedException`；
2. 响应 405，`code = "METHOD_NOT_ALLOWED"`，`message` 包含允许的方法列表（`ex.getSupportedMethods()`）；
3. 说明：这个异常是否真的有必要显式处理，Spring 默认行为是否够用？
