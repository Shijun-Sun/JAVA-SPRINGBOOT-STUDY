## 一、问题：第 04 章留下了哪些坑

完成作业 04 后，`product-service` 能跑通基本 CRUD，但有几个问题悬而未决。

**坑一：校验失败返回 500**

```bash
POST /api/v1/products
{"name":"","sku":"TEST","price":-1,"category":"测试"}
```

期望返回 400，实际可能返回 500。原因：`MethodArgumentNotValidException` 未被捕获，Spring 把它当作未处理异常，走到了 `DefaultHandlerExceptionResolver`，而该 Resolver 对 `MethodArgumentNotValidException` 的默认行为是返回 400 但不带任何 body。结果客户端拿到一个空 body 的 400，前端完全不知道哪个字段出了问题。

**坑二：重复 SKU 返回 500**

```java
// Service 层抛的
throw new IllegalArgumentException("SKU 已存在：" + request.sku());
```

没有人捕获 `IllegalArgumentException`，Spring 包装成 500 响应。前端看到的只是"Internal Server Error"。

**坑三：每个 Controller 方法都要手动处理 404**

```java
return productService.findById(id)
        .map(vo -> ResponseEntity.ok(Result.ok(vo)))
        .orElse(ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(Result.fail("PRODUCT_NOT_FOUND", "商品不存在：" + id)));
```

这段模板代码会出现在每一个"查单条"接口里，重复且容易漏写。

**坑四：错误响应格式不统一**

- 有的错误返回 `Result.fail(...)`
- 有的直接被 Spring 返回空 body
- 有的被 Spring 包装成 `/error` 重定向

这三种形式同时存在，客户端无法统一解析。

本章的目标就是用一个全局异常处理器把这四个坑全部填掉。

## 二、`@ControllerAdvice` 的工作原理

### 2.1 组合注解展开

```java
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Documented
@Component
@ResponseBody
public @interface RestControllerAdvice { ... }
```

`@RestControllerAdvice` = `@ControllerAdvice` + `@ResponseBody`。

`@ControllerAdvice` 是一个 `@Component`，Spring 启动时扫描到它并注册为特殊的 Bean。它的职责是跨 Controller 地提供三类增强：

1. `@ExceptionHandler`：全局异常处理
2. `@ModelAttribute`：全局模型数据
3. `@InitBinder`：全局数据绑定

本章只用第一个。

### 2.2 异常处理的分发链

当一个 Controller 方法抛出异常时，Spring MVC 的处理顺序是：

```text
Controller 方法抛出异常
        ↓
① Controller 内部有没有 @ExceptionHandler 方法？有 → 调用，结束
        ↓
② @ControllerAdvice 里有没有匹配的 @ExceptionHandler？有 → 调用，结束
        ↓
③ HandlerExceptionResolver 链（Spring 内置）
   - ResponseStatusExceptionResolver  （处理 @ResponseStatus 标注的异常）
   - DefaultHandlerExceptionResolver  （处理 Spring MVC 标准异常）
        ↓
④ 都没有 → /error 端点（BasicErrorController），通常返回 Whitelabel Error Page
```

优先级：Controller 内部 > `@ControllerAdvice` > Spring 内置 Resolver。

实际情况下，只要写了合适的 `@RestControllerAdvice`，绝大多数异常都会在第 ② 步被截住，不会流到第 ③、④ 步。

### 2.3 `@ExceptionHandler` 方法签名

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    // 处理单个异常类型
    @ExceptionHandler(NoSuchElementException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public Result<Void> handleNotFound(NoSuchElementException ex) {
        return Result.fail("NOT_FOUND", ex.getMessage());
    }

    // 处理多个异常类型
    @ExceptionHandler({IllegalArgumentException.class, IllegalStateException.class})
    @ResponseStatus(HttpStatus.CONFLICT)
    public Result<Void> handleConflict(RuntimeException ex) {
        return Result.fail("CONFLICT", ex.getMessage());
    }

    // 捕获所有未处理异常（兜底）
    @ExceptionHandler(Exception.class)
    @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
    public Result<Void> handleUnexpected(Exception ex, HttpServletRequest request) {
        log.error("未处理异常 path={}", request.getRequestURI(), ex);
        return Result.fail("INTERNAL_ERROR", "服务内部错误，请稍后重试");
    }
}
```

方法参数可以是：
- 具体异常类（Spring 自动注入）
- `HttpServletRequest` / `HttpServletResponse`（获取请求信息）
- `WebRequest`（更抽象的请求包装）
- `Locale`、`Model` 等

返回值可以是：
- 任意对象（会被 Jackson 序列化，因为 `@ResponseBody` 已通过 `@RestControllerAdvice` 生效）
- `ResponseEntity<T>`（精确控制状态码和响应头）

### 2.4 `@ExceptionHandler` 的精确匹配规则

当异常继承链上有多个 Handler 匹配时，Spring 选择最具体（最近的父类）的那个：

```text
抛出 ProductNotFoundException（extends NoSuchElementException extends RuntimeException）

① 有 @ExceptionHandler(ProductNotFoundException.class) → 选它
② 没有 ①，但有 @ExceptionHandler(NoSuchElementException.class) → 选它
③ 没有 ①②，但有 @ExceptionHandler(RuntimeException.class) → 选它
④ 都没有，有 @ExceptionHandler(Exception.class) → 选它（兜底）
```

结论：**兜底处理器用 `Exception.class`，具体业务异常用具体类，精确匹配**。

## 三、业务异常体系设计

### 3.1 为什么不直接用 `RuntimeException`

上面说"重复 SKU 时抛 `IllegalArgumentException`"，这是临时方案。它的问题是：

- `IllegalArgumentException` 语义太宽泛，不知道是参数类型错了还是业务规则冲突；
- 无法携带业务错误码，只能传 message 字符串；
- 无法映射到特定 HTTP 状态码，全局处理器只能通过 `instanceof` 猜；
- 不同业务场景抛同一个异常，处理器难以区分。

### 3.2 设计一个业务异常基类

```java
package com.study.mall.product.common.exception;

import org.springframework.http.HttpStatus;

public class BusinessException extends RuntimeException {

    private final String code;
    private final HttpStatus status;

    public BusinessException(String code, String message, HttpStatus status) {
        super(message);
        this.code = code;
        this.status = status;
    }

    public String getCode() { return code; }
    public HttpStatus getStatus() { return status; }
}
```

### 3.3 定义具体业务异常

```java
// 资源不存在 → 404
public class ResourceNotFoundException extends BusinessException {
    public ResourceNotFoundException(String resourceName, Object id) {
        super(
            resourceName.toUpperCase() + "_NOT_FOUND",
            resourceName + " 不存在：" + id,
            HttpStatus.NOT_FOUND
        );
    }
}

// 业务规则冲突 → 409
public class ResourceConflictException extends BusinessException {
    public ResourceConflictException(String code, String message) {
        super(code, message, HttpStatus.CONFLICT);
    }
}

// 非法业务参数 → 422（格式合法但语义错误）
public class InvalidBusinessArgumentException extends BusinessException {
    public InvalidBusinessArgumentException(String code, String message) {
        super(code, message, HttpStatus.UNPROCESSABLE_ENTITY);
    }
}
```

使用方式：

```java
// Service 层
public ProductVO create(CreateProductRequest request) {
    if (repository.existsBySku(request.sku())) {
        throw new ResourceConflictException(
            "PRODUCT_SKU_CONFLICT",
            "SKU 已存在：" + request.sku()
        );
    }
    ...
}

public Optional<ProductVO> findById(Long id) {
    return repository.findById(id)
            .map(this::toVO);
    // 不找到时抛异常的版本：
}

// 或者提供一个 getById 方法（不返回 Optional，直接抛异常）
public ProductVO getById(Long id) {
    return repository.findById(id)
            .map(this::toVO)
            .orElseThrow(() -> new ResourceNotFoundException("商品", id));
}
```

### 3.4 错误码命名规范

错误码设计原则：

- 全大写，用下划线分隔；
- 前缀是资源名：`PRODUCT_`、`ORDER_`、`USER_`；
- 后缀是错误类型：`_NOT_FOUND`、`_CONFLICT`、`_INVALID`；
- 通用错误用通用前缀：`VALIDATION_FAILED`、`INTERNAL_ERROR`、`UNAUTHORIZED`。

```text
PRODUCT_NOT_FOUND           商品不存在
PRODUCT_SKU_CONFLICT        SKU 重复
PRODUCT_PRICE_INVALID       价格语义非法
VALIDATION_FAILED           Bean Validation 失败（通用）
INTERNAL_ERROR              未预期的服务端错误
```

前端拿到错误码后可以做精确的 i18n 映射，而不是解析 message 字符串。

## 四、处理 Bean Validation 失败

### 4.1 `MethodArgumentNotValidException` 的结构

`@RequestBody + @Validated` 失败时，Spring 抛出 `MethodArgumentNotValidException`。它继承自 `BindException`，内部有一个 `BindingResult`，包含所有校验失败的详细信息：

```java
@ExceptionHandler(MethodArgumentNotValidException.class)
@ResponseStatus(HttpStatus.BAD_REQUEST)
public Result<Map<String, String>> handleValidation(
        MethodArgumentNotValidException ex) {

    Map<String, String> errors = ex.getBindingResult()
            .getFieldErrors()
            .stream()
            .collect(Collectors.toMap(
                    FieldError::getField,
                    fe -> fe.getDefaultMessage() == null ? "校验失败" : fe.getDefaultMessage(),
                    (a, b) -> a  // 同一字段多条错误时取第一条
            ));

    return Result.fail("VALIDATION_FAILED", "入参校验失败", errors);
}
```

响应示例：

```json
{
  "code": "VALIDATION_FAILED",
  "message": "入参校验失败",
  "data": {
    "name": "商品名称不能为空",
    "price": "价格必须大于 0"
  }
}
```

注意：这里 `Result<Map<String, String>>` 的 `data` 字段携带了字段级别的错误详情。这是一个扩展点——`Result` 的泛型参数允许我们在错误场景携带结构化数据。

### 4.2 `ConstraintViolationException` 的结构

`@RequestParam / @PathVariable + @Validated`（类上加了 `@Validated`）失败时，抛出的是 `ConstraintViolationException`：

```java
@ExceptionHandler(ConstraintViolationException.class)
@ResponseStatus(HttpStatus.BAD_REQUEST)
public Result<Map<String, String>> handleConstraintViolation(
        ConstraintViolationException ex) {

    Map<String, String> errors = ex.getConstraintViolations()
            .stream()
            .collect(Collectors.toMap(
                    cv -> {
                        String path = cv.getPropertyPath().toString();
                        // path 格式是 "methodName.paramName"，提取 paramName
                        int dot = path.lastIndexOf('.');
                        return dot >= 0 ? path.substring(dot + 1) : path;
                    },
                    cv -> cv.getMessage() == null ? "校验失败" : cv.getMessage(),
                    (a, b) -> a
            ));

    return Result.fail("VALIDATION_FAILED", "入参校验失败", errors);
}
```

两者的区别：

| | `MethodArgumentNotValidException` | `ConstraintViolationException` |
|---|---|---|
| 触发场景 | `@RequestBody + @Validated` | `@RequestParam/@PathVariable + @Validated`（类级别） |
| 包含信息 | `BindingResult.getFieldErrors()` | `getConstraintViolations()` |
| 所属包 | `org.springframework.web.bind` | `jakarta.validation` |

不分别处理的话，两者都会流到兜底处理器，返回 500。

### 4.3 `HttpMessageNotReadableException`：JSON 格式错误

当请求体根本不是合法 JSON，或者 JSON 字段类型与 DTO 不匹配时（例如把 `"price"` 传成了 `"abc"`），Spring 在反序列化阶段就会抛出 `HttpMessageNotReadableException`，这发生在 Bean Validation 之前：

```java
@ExceptionHandler(HttpMessageNotReadableException.class)
@ResponseStatus(HttpStatus.BAD_REQUEST)
public Result<Void> handleNotReadable(HttpMessageNotReadableException ex) {
    return Result.fail("INVALID_FORMAT", "请求体格式错误：" + ex.getMostSpecificCause().getMessage());
}
```

## 五、处理业务异常

### 5.1 统一处理 `BusinessException`

有了业务异常基类，全局处理器只需要一个方法：

```java
@ExceptionHandler(BusinessException.class)
public ResponseEntity<Result<Void>> handleBusinessException(BusinessException ex) {
    return ResponseEntity
            .status(ex.getStatus())
            .body(Result.fail(ex.getCode(), ex.getMessage()));
}
```

注意这里用 `ResponseEntity` 而不是 `@ResponseStatus`，因为状态码是动态的（从异常对象上取）。

### 5.2 兜底处理器

```java
@ExceptionHandler(Exception.class)
@ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
public Result<Void> handleUnexpected(Exception ex, HttpServletRequest request) {
    log.error("未处理异常 method={} path={}",
            request.getMethod(), request.getRequestURI(), ex);
    // 不要把异常 message 暴露给客户端，可能包含内部信息
    return Result.fail("INTERNAL_ERROR", "服务内部错误，请稍后重试");
}
```

兜底处理器的两个原则：
1. **打完整日志**，包含请求方法、路径、完整异常栈；
2. **不向客户端暴露内部细节**，`ex.getMessage()` 可能含数据库字段名、内部类名等敏感信息。

## 六、完整全局异常处理器示例

把上述所有处理器组合在一起：

```java
package com.study.mall.product.common.exception;

import com.study.mall.product.common.result.Result;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.validation.ConstraintViolationException;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.http.converter.HttpMessageNotReadableException;
import org.springframework.validation.FieldError;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.ResponseStatus;
import org.springframework.web.bind.annotation.RestControllerAdvice;

import java.util.Map;
import java.util.stream.Collectors;

@RestControllerAdvice
public class GlobalExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

    // ① @RequestBody + @Validated 校验失败
    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public Result<Map<String, String>> handleValidation(MethodArgumentNotValidException ex) {
        Map<String, String> errors = ex.getBindingResult().getFieldErrors().stream()
                .collect(Collectors.toMap(
                        FieldError::getField,
                        fe -> fe.getDefaultMessage() == null ? "校验失败" : fe.getDefaultMessage(),
                        (a, b) -> a
                ));
        return Result.fail("VALIDATION_FAILED", "入参校验失败", errors);
    }

    // ② @RequestParam / @PathVariable + @Validated 校验失败
    @ExceptionHandler(ConstraintViolationException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public Result<Map<String, String>> handleConstraintViolation(ConstraintViolationException ex) {
        Map<String, String> errors = ex.getConstraintViolations().stream()
                .collect(Collectors.toMap(
                        cv -> {
                            String path = cv.getPropertyPath().toString();
                            int dot = path.lastIndexOf('.');
                            return dot >= 0 ? path.substring(dot + 1) : path;
                        },
                        cv -> cv.getMessage() == null ? "校验失败" : cv.getMessage(),
                        (a, b) -> a
                ));
        return Result.fail("VALIDATION_FAILED", "入参校验失败", errors);
    }

    // ③ JSON 格式错误（反序列化失败）
    @ExceptionHandler(HttpMessageNotReadableException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public Result<Void> handleNotReadable(HttpMessageNotReadableException ex) {
        return Result.fail("INVALID_FORMAT", "请求体格式错误：" + ex.getMostSpecificCause().getMessage());
    }

    // ④ 业务异常（统一入口，状态码从异常对象取）
    @ExceptionHandler(BusinessException.class)
    public ResponseEntity<Result<Void>> handleBusinessException(BusinessException ex) {
        return ResponseEntity
                .status(ex.getStatus())
                .body(Result.fail(ex.getCode(), ex.getMessage()));
    }

    // ⑤ 兜底：未预期异常
    @ExceptionHandler(Exception.class)
    @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
    public Result<Void> handleUnexpected(Exception ex, HttpServletRequest request) {
        log.error("未处理异常 method={} path={}", request.getMethod(), request.getRequestURI(), ex);
        return Result.fail("INTERNAL_ERROR", "服务内部错误，请稍后重试");
    }
}
```

**排列顺序很重要**：Spring 按类型精确匹配，不是按方法声明顺序，但把具体异常写在前面是好习惯，也方便阅读。

## 七、`Result<T>` 的升级：携带错误详情

上面的 `Result.fail("VALIDATION_FAILED", "入参校验失败", errors)` 要求 `Result` 能接受第三个参数（错误详情数据）。

把第 04 章的 `Result` 升级成同时支持成功数据和错误详情的形式：

```java
package com.study.mall.product.common.result;

import com.fasterxml.jackson.annotation.JsonInclude;

@JsonInclude(JsonInclude.Include.NON_NULL)
public record Result<T>(
        String code,
        String message,
        T data
) {
    // 成功：有数据
    public static <T> Result<T> ok(T data) {
        return new Result<>("SUCCESS", "ok", data);
    }

    // 成功：无数据
    public static Result<Void> ok() {
        return new Result<>("SUCCESS", "ok", null);
    }

    // 失败：无详情
    public static Result<Void> fail(String code, String message) {
        return new Result<>(code, message, null);
    }

    // 失败：有详情（例如字段级错误）
    public static <T> Result<T> fail(String code, String message, T data) {
        return new Result<>(code, message, data);
    }
}
```

现在 `data` 字段在成功时携带业务数据，在特定失败场景（如校验失败）可以携带错误详情，不失败时因为 `@JsonInclude(NON_NULL)` 不出现在响应里。

## 八、从 Controller 层移除 404 处理模板代码

有了全局异常处理器，Controller 里的 `findById` 可以大幅简化：

```java
// 之前：每个查询方法都要写这段模板
@GetMapping("/{id}")
public ResponseEntity<Result<ProductVO>> findById(@PathVariable Long id) {
    return productService.findById(id)
            .map(vo -> ResponseEntity.ok(Result.ok(vo)))
            .orElse(ResponseEntity.status(HttpStatus.NOT_FOUND)
                    .body(Result.fail("PRODUCT_NOT_FOUND", "商品不存在：" + id)));
}

// 之后：Service 直接抛 ResourceNotFoundException，Controller 只关心正常路径
@GetMapping("/{id}")
public Result<ProductVO> findById(@PathVariable Long id) {
    return Result.ok(productService.getById(id));  // 找不到时 Service 会抛异常
}
```

Service 层：

```java
public ProductVO getById(Long id) {
    return repository.findById(id)
            .map(this::toVO)
            .orElseThrow(() -> new ResourceNotFoundException("商品", id));
}
```

全局处理器捕获 `ResourceNotFoundException`（它继承 `BusinessException`），自动返回 404。Controller 完全不知道"找不到"这件事，它只负责正常路径。

## 九、RFC 9457 ProblemDetail

### 9.1 标准格式

RFC 9457（前身是 RFC 7807）定义了一个标准的 HTTP API 错误响应格式：

```json
{
  "type": "https://example.com/problems/product-not-found",
  "title": "Product Not Found",
  "status": 404,
  "detail": "商品不存在：42",
  "instance": "/api/v1/products/42"
}
```

Spring Framework 6.0（对应 Spring Boot 3.0）引入了 `ProblemDetail` 类，原生支持这个格式。

### 9.2 Spring 的 ProblemDetail 支持

```java
// 配置开启（Spring Boot 默认关闭）
# application.yml
spring:
  mvc:
    problemdetails:
      enabled: true

// 在全局处理器里使用
@ExceptionHandler(ResourceNotFoundException.class)
public ProblemDetail handleNotFound(ResourceNotFoundException ex, HttpServletRequest request) {
    ProblemDetail pd = ProblemDetail.forStatusAndDetail(ex.getStatus(), ex.getMessage());
    pd.setTitle("Resource Not Found");
    pd.setInstance(URI.create(request.getRequestURI()));
    pd.setProperty("errorCode", ex.getCode());  // 扩展字段
    return pd;
}
```

### 9.3 ProblemDetail 还是自定义 `Result<T>`？

| 维度 | `ProblemDetail` | 自定义 `Result<T>` |
|---|---|---|
| 标准化程度 | RFC 9457，跨团队/跨语言可互通 | 自定义约定，需团队内对齐 |
| 字段灵活性 | 可扩展，但有标准字段约束 | 完全自由 |
| 前端解析 | 知道 `type`、`status`、`detail` 的含义 | 需要双方约定 |
| Spring 集成 | `spring.mvc.problemdetails.enabled=true` 自动处理部分内置异常 | 全部手动处理 |
| 适合场景 | 对外开放 API、公司统一规范时 | 内部服务、前后端协作紧密时 |

**本课程使用自定义 `Result<T>`**，原因是：对内部系统来说，`code`（语义字符串）比 `type`（URI）更直观，前端代码可读性更强。了解 `ProblemDetail` 是为了知道"还有另一条路"，遇到需要标准化的场景能做出选择。

## 十、Spring 内置异常与 `DefaultHandlerExceptionResolver`

Spring MVC 内部的 `DefaultHandlerExceptionResolver` 会先于 `@ControllerAdvice` 处理一部分标准异常（这个说法需要修正——实际上 `@ExceptionHandler` 优先级更高，`DefaultHandlerExceptionResolver` 是在没有匹配的 `@ExceptionHandler` 时才介入）。

但有一个特殊情况：如果你的 `@ControllerAdvice` 处理了 `Exception.class`（兜底），并且某个 Spring MVC 内置异常也落进了 `Exception.class` 处理器，状态码会由你的处理器决定，而不是 Spring 的默认行为。

常见的 Spring MVC 内置异常及其默认状态码：

| 异常 | 默认状态码 | 触发场景 |
|---|---|---|
| `MethodArgumentNotValidException` | 400 | `@RequestBody` Bean Validation 失败 |
| `MethodArgumentTypeMismatchException` | 400 | 路径变量类型转换失败（传字母给 Long） |
| `MissingServletRequestParameterException` | 400 | 必填 `@RequestParam` 未传 |
| `HttpMessageNotReadableException` | 400 | 请求体 JSON 格式错误 |
| `HttpRequestMethodNotSupportedException` | 405 | 用 GET 访问只支持 POST 的路径 |
| `NoHandlerFoundException` | 404 | 路径不存在 |

建议：这些常见异常都显式在 `@RestControllerAdvice` 里声明处理器，而不是依赖 Spring 的默认行为。这样你对响应格式的控制更完整，响应格式也更统一。

## 十一、日志规范与异常处理的关系

异常处理器是打日志的最佳位置，因为它是所有异常的汇聚点。

**分级原则：**

```java
// 业务异常（预期错误）：用 WARN，不打堆栈
log.warn("业务异常 code={} message={}", ex.getCode(), ex.getMessage());

// 校验失败（客户端问题）：用 DEBUG 或 INFO，不打堆栈
log.debug("入参校验失败 errors={}", errors);

// 未预期异常（服务端 Bug）：用 ERROR，必须打完整堆栈
log.error("未处理异常 method={} path={}", request.getMethod(), request.getRequestURI(), ex);
```

不要对业务异常（404、409）也打 ERROR 级别的日志——这会让告警频繁触发，淹没真正需要关注的错误。

## 十二、小结

| 知识点 | 记住这一句 |
|---|---|
| `@RestControllerAdvice` | `@ControllerAdvice` + `@ResponseBody`，拦截所有 Controller 的异常 |
| 异常匹配顺序 | 具体类优先，找不到匹配才向上找父类，最后到 `Exception.class` 兜底 |
| `BusinessException` | 自定义基类，携带 `code` + `status`，统一从异常取状态码 |
| `MethodArgumentNotValidException` | `@RequestBody` 校验失败，从 `getBindingResult().getFieldErrors()` 取字段错误 |
| `ConstraintViolationException` | `@RequestParam/@PathVariable` 校验失败，从 `getConstraintViolations()` 取错误 |
| 兜底处理器 | 打完整 ERROR 日志，返回通用错误信息，不暴露内部细节 |
| `ProblemDetail` | RFC 9457 标准格式，Spring Boot 内置支持，对外开放 API 时考虑使用 |
| 日志分级 | 业务异常 WARN，未预期异常 ERROR + 完整堆栈 |
