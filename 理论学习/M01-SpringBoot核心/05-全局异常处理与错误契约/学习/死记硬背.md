# 第05章 · 死记硬背

> 先背会这些，做作业时才不会在细节上卡壳。  
> 标 ⭐ 的是面试/答辩高频考点，标 ⚠️ 的是坑。

---

## `@RestControllerAdvice` 展开 ⭐

```
@RestControllerAdvice = @ControllerAdvice + @ResponseBody
@ControllerAdvice      = @Component（Spring 启动扫描并注册为 Bean）
```

职责：跨所有 Controller 提供统一的异常处理、模型数据、数据绑定增强。  
本章只用 `@ExceptionHandler`——异常处理。

---

## 异常处理优先级（从高到低）⭐

```
① Controller 内部的 @ExceptionHandler 方法
② @ControllerAdvice 里的 @ExceptionHandler 方法（精确类优先）
③ Spring 内置 HandlerExceptionResolver 链
④ /error 端点（最后兜底，通常是 Whitelabel Error Page）
```

`@ExceptionHandler` 匹配规则：**最具体的子类优先**。

```text
抛出 ProductNotFoundException（extends BusinessException extends RuntimeException）

有 @ExceptionHandler(ProductNotFoundException.class)  → 选它
没有上面，有 @ExceptionHandler(BusinessException.class) → 选它
没有上面，有 @ExceptionHandler(RuntimeException.class) → 选它
都没有，有 @ExceptionHandler(Exception.class)          → 兜底（必须有这个）
```

---

## 三类校验异常，必须分别处理 ⭐⚠️

```
场景                                      抛出的异常
@RequestBody + @Validated 失败          → MethodArgumentNotValidException
@RequestParam/@PathVariable + @Validated 失败 → ConstraintViolationException
路径变量类型转换失败（传字母给 Long）    → MethodArgumentTypeMismatchException
请求体 JSON 格式错误                    → HttpMessageNotReadableException
```

⚠️ 只写了 `Exception.class` 兜底而没有分别处理：前两类本来应该返回 400，但兜底处理器加了 `@ResponseStatus(500)`，结果全部返回 500。

## `MethodArgumentNotValidException` 取字段错误 ⭐

```java
// 从 BindingResult 取字段级错误
ex.getBindingResult().getFieldErrors()
    → List<FieldError>
    → FieldError.getField()          // 字段名，如 "name"
    → FieldError.getDefaultMessage() // 校验注解的 message，如 "商品名称不能为空"
```

---

## `ConstraintViolationException` 取字段错误

```java
// 从 ConstraintViolations 取错误
ex.getConstraintViolations()
    → Set<ConstraintViolation<?>>
    → cv.getPropertyPath().toString()  // "methodName.paramName" 格式
    → cv.getMessage()                  // message
```

⚠️ `propertyPath` 格式是 `"list.page"` 这样的，要截取最后一段才是真正的参数名：
```java
String path = cv.getPropertyPath().toString();
int dot = path.lastIndexOf('.');
String paramName = dot >= 0 ? path.substring(dot + 1) : path;
```

## 业务异常基类设计 ⭐

```java
public class BusinessException extends RuntimeException {
    private final String code;      // 业务错误码，如 "PRODUCT_NOT_FOUND"
    private final HttpStatus status; // 对应 HTTP 状态码
}
```

三个常用子类：

| 子类 | HTTP 状态码 | 典型场景 |
|---|---|---|
| `ResourceNotFoundException` | 404 | 商品不存在、订单不存在 |
| `ResourceConflictException` | 409 | SKU 重复、用户名已注册 |
| `InvalidBusinessArgumentException` | 422 | 价格为负（格式合法但语义非法） |

全局处理器只需一个方法：
```java
@ExceptionHandler(BusinessException.class)
public ResponseEntity<Result<Void>> handle(BusinessException ex) {
    return ResponseEntity.status(ex.getStatus())
                         .body(Result.fail(ex.getCode(), ex.getMessage()));
}
```

## `Result<T>` 升级：支持失败时携带详情 ⭐

```java
// 新增重载：失败时可以带结构化的错误详情（如字段级错误 Map）
public static <T> Result<T> fail(String code, String message, T data) {
    return new Result<>(code, message, data);
}
```

使用示例（校验失败响应）：

```json
{
  "code": "VALIDATION_FAILED",
  "message": "入参校验失败",
  "data": {
    "name": "商品名称不能为空",
    "price": "价格必须大于 0"
  }
}
```

## `@ResponseStatus` vs `ResponseEntity` 在处理器里怎么选

```
状态码固定（如 400、404）→ @ResponseStatus(HttpStatus.XXX)（简洁）
状态码动态（从异常对象取） → ResponseEntity.status(ex.getStatus()).body(...)
需要设置响应头            → ResponseEntity（唯一选择）
```

⚠️ 业务异常基类携带了动态状态码，处理器必须用 `ResponseEntity`，不能用 `@ResponseStatus`。

## 兜底处理器的两个铁律 ⭐⚠️

```java
@ExceptionHandler(Exception.class)
@ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
public Result<Void> handleUnexpected(Exception ex, HttpServletRequest request) {
    // 铁律一：必须打 ERROR 级别完整日志（含堆栈）
    log.error("未处理异常 method={} path={}", request.getMethod(), request.getRequestURI(), ex);
    // 铁律二：不把 ex.getMessage() 返回给客户端（可能暴露内部信息）
    return Result.fail("INTERNAL_ERROR", "服务内部错误，请稍后重试");
}
```

---

## 日志分级原则

| 异常类型 | 级别 | 是否打堆栈 | 原因 |
|---|---|---|---|
| 校验失败（客户端问题） | DEBUG / INFO | ❌ | 高频，正常流量，打堆栈会淹没日志 |
| 业务异常（预期错误） | WARN | ❌ | 不是 Bug，是预期内的业务逻辑分支 |
| 未预期异常（服务端 Bug） | ERROR | ✅ | 需要排查，必须完整 |

⚠️ 把所有异常都打 ERROR 是常见错误——告警系统会被 404 淹没，真正的 Bug 淹没在噪音里。

## ProblemDetail 一句话 ⭐

`ProblemDetail` 是 RFC 9457 定义的标准错误响应格式，Spring Boot 3+ 内置支持（`spring.mvc.problemdetails.enabled=true`）。

用自定义 `Result<T>` 还是 ProblemDetail 的判断依据：
- **对外开放 API / 跨团队跨语言** → 考虑 ProblemDetail（标准化，互通性好）
- **内部服务 / 前后端同团队** → 自定义 `Result<T>`（灵活，`code` 字段可读性强）

## Controller 的职责边界（学完本章后的正确姿势）⭐

```
Controller 只处理正常路径：接收参数 → 调用 Service → 包装 Result → 返回

异常路径（资源不存在、业务冲突等）全部由：
  Service 层  →  抛 BusinessException 子类
  全局处理器  →  捕获 BusinessException，设置状态码和错误响应
```

Controller 里不应再出现：
```java
// ❌ 这些都应该移除
.orElse(ResponseEntity.status(404).body(...))
catch (IllegalArgumentException e) { return Result.fail(...); }
if (product == null) { return ResponseEntity.notFound()...; }
```

## Spring 内置异常 → 默认状态码速查

| 异常 | 默认状态码 | 建议：显式在 Advice 处理 |
|---|---|---|
| `MethodArgumentNotValidException` | 400 | ✅ 必须（需要格式化字段错误） |
| `ConstraintViolationException` | 400 | ✅ 必须 |
| `MethodArgumentTypeMismatchException` | 400 | ✅ 建议 |
| `MissingServletRequestParameterException` | 400 | ✅ 建议 |
| `HttpMessageNotReadableException` | 400 | ✅ 建议 |
| `HttpRequestMethodNotSupportedException` | 405 | 可不处理（默认行为够用） |
| `NoHandlerFoundException` | 404 | 可不处理 |

## 高频坑 ⚠️

1. **写了 `@ExceptionHandler(Exception.class)` 但没写具体异常处理器**：校验失败走兜底，返回 500 而不是 400。
2. **`ConstraintViolationException` 没有被触发**：类上忘记加 `@Validated`（必须在 Controller 类上加，不是方法参数上）。
3. **业务异常处理器用了 `@ResponseStatus` 而不是 `ResponseEntity`**：状态码写死成固定值，动态 `ex.getStatus()` 被忽略。
4. **兜底处理器把 `ex.getMessage()` 返回给客户端**：可能暴露数据库表名、内部方法名等敏感信息。
5. **`@ExceptionHandler` 方法没有被触发**：检查类上有没有 `@RestControllerAdvice` 或 `@ControllerAdvice`，以及包扫描范围。
6. **同一异常在 Controller 内和 Advice 里都有处理器**：Controller 内部的优先，可能导致格式不统一。

---

## 一句话总结

> 全局异常处理器是系统的"最后一道防线"：具体异常精确匹配，业务异常由基类统一托管，`Exception` 兜底打日志不泄露细节，Controller 只看正常路径。
